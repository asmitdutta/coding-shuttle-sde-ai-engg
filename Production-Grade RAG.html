part oneWhy basic RAG is not enough

Similar is not the same as relevant

Consider a customer who writes to a food-delivery help desk:

Query“My order says delivered, but I never received it. I paid online. Can I get a refund?”

A basic RAG system embeds the question, retrieves the five most similar chunks and asks an LLM to answer. The corpus used throughout this article is a fictional Zomato support knowledge base (introduced in full in the next section), so the chunks below are the actual records the retriever has to choose from. This is what a plain dense search might return. Scores are illustrative.

All four records talk about refunds, payments or orders, so all four look plausible. Only one describes the situation the customer is in. A model that receives all four may blend them, and the result can look like this:

Failure caseWhat an ungrounded answer might say

“Yes, you will receive a full refund to your original payment method within 5–7 days.”

None of the four records promises a refund for an order marked delivered. ZH-002 only says to check delivery instructions, contact the delivery partner and report the issue from the order page. The 5–7 day figure is not in any retrieved record at all. The answer is fluent, confident and unsupported.

This single query shows the difference between four things that a basic pipeline treats as one:

  • Finding text that looks similar. All four records pass this test.
  • Finding evidence that answers the actual question. Only ZH-002 passes, and only partially: it does not say whether a refund is available.
  • Ranking that evidence correctly. ZH-002 was third.
  • Producing a grounded answer. The right answer states the steps in ZH-002 and says plainly that the available records do not confirm a refund.

part twoDocument preparation and chunking

Chunking decides what can be retrieved

Retrieval quality starts before any search runs. A handbook is split into chunks, each chunk is embedded, and the retriever can only ever return what a chunk contains. The same source below is split four ways in this section. Here is the source, a short fictional payments handbook:

Source documentSource: payments handbook (3 sections)
Section 1 — Late delivery If an order is delayed, check the live status and ETA. If the ETA has passed, contact support from order details. Section 2 — Payment debited, order failed If money was debited but the order failed, check whether payment is pending, reversed or refunded. Raise a support issue if unresolved. Section 3 — Duplicate payment If two charges appear for one order, compare transaction references. Never share full card details or an OTP.
Query“Money was debited but my order failed.”

The relevant section is “Payment debited, order failed”, which matches ZH-010. What matters is whether the chunk the retriever returns still contains a complete rule: the condition (“money was debited but the order failed”), the checks (“pending, reversed or refunded”) and the action (“raise a support issue”).

Fixed-size chunking

Fixed-size chunking splits by a character or token budget, usually with some overlap between neighbours. It needs no knowledge of the document layout, so it is simple, fast and reproducible. Applied to the source above with a 120-character window and 20 characters of overlap, the output is:

ChunksFixed-size: 120 characters, 20 overlap
Chunk 1 · 120 charsSection 1 — Late delivery↵ If an order is delayed, check the live status and ETA.↵ If the ETA has passed, contact support
Chunk 2 · 120 charsed, contact support from order details.↵ ↵ Section 2 — Payment debited, order failed↵ If money was debited but the order fa
Chunk 3 · 120 charsted but the order failed, check whether payment↵ is pending, reversed or refunded. Raise a support issue if unresolved.↵ ↵
Chunk 4 · 120 charssue if unresolved.↵ ↵ Section 3 — Duplicate payment↵ If two charges appear for one order, compare transaction references.↵ N
Chunk 5 · 59 charsaction references.↵ Never share full card details or an OTP.

↵ marks a line break. Overlapping characters appear at the end of one chunk and the start of the next.

Read the boundaries. Chunk 2 ends mid-word, with “the order fa”, and the rest of the condition begins Chunk 3. The checks (“pending, reversed or refunded”) sit in Chunk 3, while the section heading sits in Chunk 2. Chunk 5 holds “Never share full card details or an OTP” without the heading that says it belongs to duplicate payments.

Failure caseWhat the retriever returns for the query

The best-scoring chunk is likely Chunk 2, because it contains “If money was debited but the order fa…”. The model receives a condition with no checks and no action. If Chunk 3 is also returned, it receives the action with no heading, and might attach it to the wrong section.

Overlap helps with facts near a boundary but does not repair a broken structure. The 20 characters repeated between chunks (“ed, contact support”) did not save the rule in Section 2. Heavy overlap also duplicates content and inflates the index.

  • Use it when text has no reliable structure and a reproducible baseline is needed.
  • Watch for tables, lists and policies being cut apart, and chunks that mix two topics.
  • Tune it on an evaluation set. There is no universally best chunk size.

Structure-aware chunking

Structure-aware chunking cuts on meaningful boundaries first (document, section, FAQ item, paragraph, list, table), then enforces a size limit only where a unit is too large. For the same source, the output is:

ChunksStructure-aware: one chunk per section
Chunk 1 · [ZH-001 | Late delivery]If an order is delayed, check the live status and ETA.↵ If the ETA has passed, contact support from order details.
Chunk 2 · [ZH-010 | Payment debited, order failed]If money was debited but the order failed, check whether payment↵ is pending, reversed or refunded. Raise a support issue if unresolved.
Chunk 3 · [ZH-011 | Duplicate payment]If two charges appear for one order, compare transaction references.↵ Never share full card details or an OTP.

Each chunk is a complete rule with its heading, so the query “Money was debited but my order failed” retrieves Chunk 2 whole: the condition, the checks and the action. The heading carries topic information that the body text alone might not.

Document→Section→Subsection→Paragraph→Token split (last resort)

Metadata should travel with every chunk: document_id, section_path, chunk_id, source_version, updated_at, product, locale, status and the applicable access scope.

Semantic chunking

Semantic chunking splits where meaning changes rather than where a character count or heading falls. One common approach embeds adjacent sentences and starts a new chunk when their distance rises sharply. Consider a section with no headings:

Source documentSource paragraph without headings

The restaurant may cancel an order when it cannot fulfil it. The customer should check the order and payment status. A refund’s handling depends on the transaction and applicable policy.

For coupons, the offer may require a minimum order value. Some offers apply only to selected restaurants or payment methods. Expired codes cannot be used.

ChunksIllustrative distances between adjacent sentencesillustrative values
Sentence pairDistanceReading
Restaurant may cancel an order → check order and payment status0.12Related
Check payment status → refund handling depends on the transaction0.16Related
Refund handling → coupon needs a minimum order value0.71Likely topic shift
Minimum order value → only selected restaurants or payment methods0.14Related

The jump to 0.71 sits between the cancellation sentences and the coupon sentences, so a semantic splitter would place a boundary there: Chunk A covers cancellation and refunds, Chunk B covers coupon eligibility. A heading-based splitter could not do this, because there is no heading.

The distances depend on the embedding model and distance definition. 0.71 is not a universal threshold, and a splitter configured with one can over-split or under-split. Semantic chunking costs more compute and is harder to debug. Adopt it only if evaluation shows an improvement over simpler splitting.

The four strategies side by side

The same payments handbook and the same query (“Money was debited but my order failed”) give different outcomes depending on how the source was prepared:

The lesson is not that fixed-size chunking is bad. Boundaries should preserve the unit of meaning needed to answer a question, and which strategy does that is an empirical question for each corpus.

Where each kind of lookup belongs in production

  • Order IDs, customer IDs and live transaction states: look them up in operational databases or authorised APIs. They are not documentation, and they do not belong in the vector store.
  • Error codes and terminology documented in help articles: index those articles, so a code such as PAY-403 is searchable because the article that explains it is searchable.
  • Natural-language questions: use dense retrieval to find conceptually relevant explanations.
  • Queries combining symptoms and technical codes: use hybrid retrieval, then rerank if evaluation justifies it.

The error code is part of the documentation itself here, not an arbitrary operational identifier that someone decided to put into the vector store. That is the case sparse retrieval is for.

Why they behave differently

The two methods store fundamentally different data. Take one sentence, “Refund not received for order ZH-009”, and watch what each representation keeps.

How BM25 scores a document

Term frequency

More occurrences of a query term in a document suggest relevance, with diminishing returns, so the tenth mention adds far less than the second.

Inverse document frequency

Rare terms are worth more. “permission” appears in many articles, while PAY-403 appears in one.

Length normalisation

Longer documents contain more of every term, so counts are normalised downward.

Saturation and tuning

k1 sets how fast repeated terms stop helping and b sets the length penalty. They are tuning knobs, not constants.

BM25 needs no training, no GPU and no re-indexing of vectors when the corpus changes. Reach for it first when queries contain error codes, SKUs, ticket IDs or exact product names that your documentation actually contains.

RRF(d) = Σ over ranked lists r   of   1 / (k + rank_r(d))

rank_r(d) : position of document d in list r (1 = best)
k         : smoothing constant (60 is a common default)

What RRF does and does not establish

  • It rewards documents that several retrieval methods agree on, without needing comparable scores.
  • It does not know which document is correct. If both lists contain irrelevant documents, fusion can promote them, and ZH-010 reaching third place says nothing about whether it answers the query.
  • It is cheap. A cross-encoder (see the reranking section) compares the query and each candidate directly, which RRF never does.

side note

One point, several vectors

A vector-database point is a record, not a mathematical vector. It holds an ID, a payload (text and metadata) and one or more vectors. With named vectors, one point carries several, each a separate embedding of the same record, with its own dimension and distance metric.

InsertCreate the collection with one config per vector name, then upsert one PointStruct whose vector is a dict. Embed each representation separately. The payload is stored once.
QueryEvery search names the vector it targets with using="title", and the query must be embedded for that space. To use several, search each and fuse the rankings with RRF. Never average the vectors.
BenefitOne record can be found several ways, with one ID, one payload and one set of filters. No duplicate records per representation, and the citation still points at a single canonical record.

from pydantic import BaseModel, Field

class QueryVariants(BaseModel):
    queries: list[str] = Field(min_length=1, max_length=3)

def retrieve_multi_query(question, retriever, llm):
    generator = llm.with_structured_output(QueryVariants)
    variants = generator.invoke(
        "Generate up to 3 distinct search queries for this question. "
        "Do not answer it; preserve IDs and named entities.\nQuestion: "
        + question
    )
    queries = list(dict.fromkeys(
        [question] + [q.strip() for q in variants.queries if q.strip()]
    ))

    results = []
    for query in queries:
        results.extend(retriever.invoke(query))
    return deduplicate_documents(results)

Step-back prompting

A very specific question may lack the vocabulary of the policy that governs it. Step-back prompting adds a broader question, retrieves for both and combines the evidence.

Why the cross-encoder can see what retrieval could not

A bi-encoder embeds the query and each document separately and compares vectors, which is what makes searching a large index fast. A cross-encoder processes the query and one candidate together, so it can notice that ZH-010 addresses the start of the problem (debited, order failed) while ZH-009 addresses a later one (a refund that exists but has not arrived).

Costs and trade-offs

  • Latency: every candidate is a model inference. For example, 30 candidates at about 4 ms per pair would add about 120 ms, while 100 candidates would add about 400 ms (illustrative figures, which depend on hardware, batching and model).
  • Candidate count: do not copy a number from a tutorial. Tune it against recall, latency and cost on your own evaluation set.
  • Model fit: a cross-encoder can still be wrong, especially on long documents or specialised language.

Reranking in LangChain

LangChain models reranking as a document compressor wrapped around a retriever. The base retriever returns a wide candidate set; the compressor rescores it and keeps the best few. Everything downstream still receives ordinary Document objects with their metadata intact.

A local cross-encoder needs no API key. Replace the model name with any sentence-transformers cross-encoder you have evaluated:

from langchain_classic.retrievers import ContextualCompressionRetriever
from langchain_classic.retrievers.document_compressors import CrossEncoderReranker

A hosted reranker is the same pattern with a different compressor. LangChain ships integrations for several providers; for an endpoint without one (here OpenRouter’s /rerank), a small custom compressor is enough:

import os, requests
from langchain_core.documents import Document
from langchain_core.documents.compressor import BaseDocumentCompressor

class OpenRouterReranker(BaseDocumentCompressor):
    model: str = "cohere/rerank-v3.5"
    top_n: int = 5

    def compress_documents(self, documents, query, callbacks=None):
        r = requests.post(
            "https://openrouter.ai/api/v1/rerank",
            headers={"Authorization": f"Bearer {os.environ['OPENROUTER_API_KEY']}"},
            json={"model": self.model, "query": query, "top_n": self.top_n,
                  "documents": [d.page_content for d in documents]},
            timeout=30,
        )
        r.raise_for_status()
        out = []
        for hit in r.json()["results"]:
            doc = documents[hit["index"]]
            out.append(Document(page_content=doc.page_content,
                                metadata={**doc.metadata, "rerank_score": hit["relevance_score"]}))
        return out

Pass it as base_compressor and nothing else changes. Verify the model identifier and pricing before relying on it.

  • Fail safe. Wrap the call so a timeout or rate limit falls back to the first-stage order instead of failing the request.
  • Keep scores. Storing the rerank score in metadata lets traces and evaluation compare the order before and after.
  • Filter first. Tenant and authorisation filters belong in the base retriever. A reranker is not an access-control mechanism.

from typing import Literal
from pydantic import BaseModel, Field

class Claim(BaseModel):
    text: str
    source_chunk_ids: list[str] = Field(min_length=1)

class SupportAnswer(BaseModel):
    answer: str
    claims: list[Claim]
    outcome: Literal["answered", "insufficient_evidence", "escalate"]

def validate_citations(answer, selected_docs):
    allowed = {d.metadata["chunk_id"] for d in selected_docs}
    for claim in answer.claims:
        if not set(claim.source_chunk_ids).issubset(allowed):
            raise ValueError("Citation references evidence not supplied to the model")
    if answer.outcome == "answered" and not answer.claims:
        raise ValueError("An answered response must contain evidence-backed claims")
    return answer

        models.FieldCondition(key="tenant_id",

Recall@K asks what fraction of all relevant records appear in the top K. Precision@K asks what fraction of the top K are relevant.

Recall@K    = (relevant records in top K) / (all known relevant records)
Precision@K = (relevant records in top K) / K

def recall_at_k(retrieved_ids, relevant_ids, k):
    found = set(retrieved_ids[:k]) & relevant_ids

    found = set(retrieved_ids[:k]) & relevant_ids
    return len(found) / k

Retrieval and answer evaluation are separate

Retrieval evaluation asks whether the right evidence was found. Answer evaluation asks whether the response used it correctly. A fluent answer can be built on the wrong evidence, and good evidence can still produce a poor answer.

part elevenGraph RAG: when relationships matter

When retrieval needs relationships

Everything so far retrieves chunks. Some questions depend instead on connections between facts that live in separate records: which payment belongs to which refund, which service depends on which database, which accounts share a device. Graph RAG extracts entities and relationships into a knowledge graph and traverses it alongside ordinary vector retrieval.

A graph is made of nodes (customers, orders, payments, refunds), edges that name how they connect, and properties such as a status. The graph below holds the facts behind one question: "Which payment is associated with Customer A's pending refund?" Customer A has two orders, so the answer needs relationship hops and a property check.

Why a graph, and not just a chunk

Suppose the same facts are stored as four separate chunks. A vector retriever returns whichever chunk is most similar to the question, and that is usually the one that mentions a pending refund. It does not say which payment the refund belongs to or whose order it was. A graph keeps the chunks connected, so one traversal reaches all four.

How Graph RAG is built

Documents go through entity and relationship extraction, an LLM or rule-based step that produces the graph. The original chunks are still embedded and indexed, so retrieval can combine graph traversal with the vector and hybrid search from earlier sections, and every graph fact keeps a link back to its source passage so answers stay checkable.

A minimal version needs nothing beyond NetworkX for the graph and the same ChatOpenRouter pattern used earlier. It builds the graph by hand and starts from a known entity, so it shows traversal and grounded generation, not a full extraction pipeline.

import networkx as nx

graph = nx.DiGraph()
graph.add_node("Customer A", type="Customer")
graph.add_node("Order 123", type="Order")
graph.add_node("Payment P1", type="Payment")
graph.add_node("Refund R1", type="Refund", status="pending")
graph.add_edge("Customer A", "Order 123", relation="PLACED")
graph.add_edge("Order 123", "Payment P1", relation="PAID_WITH")
graph.add_edge("Payment P1", "Refund R1", relation="HAS_REFUND")

def retrieve_graph_context(graph, start_entity, max_hops=3):
    reachable = nx.single_source_shortest_path_length(graph, start_entity, cutoff=max_hops)
    nodes = set(reachable)
    facts = [
        f"{s} --{d['relation']}--> {t}"
        for s, t, d in graph.edges(data=True) if s in nodes and t in nodes
    ]
    facts += [
        f"{n} has {k}: {v}"
        for n in nodes for k, v in graph.nodes[n].items() if k != "type"
    ]
    return "\n".join(facts)

context = retrieve_graph_context(graph, "Customer A")
from langchain_openrouter import ChatOpenRouter
from langchain_core.prompts import ChatPromptTemplate

llm = ChatOpenRouter(model="openai/gpt-4.1-mini", temperature=0)
prompt = ChatPromptTemplate.from_messages([
    ("system", "Answer only from the supplied graph facts. "
               "If the facts do not establish an answer, say so. "
               "Do not invent entities or relationships."),
    ("human", "Question: {question}\nRetrieved graph facts:\n{context}"),
])
answer = (prompt | llm).invoke({
    "question": "Which payment is associated with Customer A's pending refund?",
    "context": context,
})
print(answer.content)   # Payment P1, linked to Refund R1, status pending
A production system must extract entities and relationships from documents, resolve duplicate entity names, and connect retrieval to the user's actual question. Neo4j's GraphRAG package covers graph construction and combined vector and graph retrievers once a persistent graph database is justified.

Self-test

Why can’t raw dense and BM25 scores be added?
They are on unrelated scales. RRF fuses rank positions, as the ZM-401 example shows: 0.77 + 12.4 means nothing, while 1/62 + 1/61 does.
Why can’t a reranker fix a bad retriever?
It only re-scores the candidates it receives. If ZH-010 never reaches the shortlist, no ordering recovers it.
Why must tenant filters come from server-side auth?
A client or a model can change any value it sends. Only a verified identity is trustworthy for authorisation, and the filter must apply before retrieval.
Why does a valid citation ID not prove an answer is grounded?
The ID can exist, be retrieved and be permitted while the cited passage says nothing about the claim, as with an invented 24-hour refund promise attributed to ZH-010.
Why keep retrieval and answer evaluation separate?
A correct document can still yield a poor answer, and a fluent answer can sit on the wrong evidence. Mixing them hides which stage failed.
Why can an updated policy make answers worse?
If the superseded version stays searchable, it can be the better match and win. Validity must be a metadata filter, not a ranking hope.
When is RAG the wrong tool?
For live, authenticated state such as order status, and for aggregates over many records. Those need an API or governed query.

  • Qdrant hybrid and multi-stage queries: prefetch, dense and sparse search, RRF.
  • LangChain Qdrant FastEmbedSparse: local sparse embeddings, including the Qdrant BM25 model.
  • Qdrant relevance feedback: native relevance-feedback query from Qdrant 1.17.
  • Qdrant multitenancy: payload filters and tenant-aware indexing.
  • Anthropic Contextual Retrieval: LLM-generated chunk context.
  • LangSmith evaluation: offline datasets, regression tests and online evaluation.
  • Microsoft GraphRAG and Neo4j GraphRAG for Python: optional graph extensions.
The langchain-classic package is documented as receiving security fixes until December 2026. Avoid making a new long-lived service depend on its retriever helpers without a migration plan; the patterns remain useful behind your own interfaces.
