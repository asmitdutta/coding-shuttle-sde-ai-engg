a case study

Three narrow agents and a "Looks Good" button: how Uber's QueryGPT writes SQL

Writing SQL at Uber takes two kinds of knowledge: the syntax, and which of thousands of tables actually means "a completed trip". QueryGPT turns an English question into a query. Its first version was one big prompt, and it got worse as more tables were added. The fix was to split the job: one small agent picks the business area, one picks the tables and asks you to confirm them, one trims the schemas, and only then is the SQL written. This is what Uber published, and how to build the same pipeline yourself.

By Anuj Kumar Sharma about 22 minutes Module 6 · MCP, Context Engineering & Multi-Agent Orchestration
the story

story · 01Why this case study

Most people's first LLM feature is one big prompt: paste the schema, paste some examples, ask, hope. It works in the demo, then quietly stops working as the data grows.

Uber's QueryGPT went through exactly that, and fixed it without a bigger model: it split one hard task into small ones, put a person at the one step they can check in seconds, and chose carefully what the model sees. Those are this module's three ideas: orchestration, a human in the loop, and context engineering.

what you will be able to do

Explain why one text-to-SQL prompt degrades as tables grow, design a pipeline of narrow agents with a human confirmation step, prune context to fit a token budget, evaluate each agent separately, and stop model-written SQL from doing damage.

story · 03Version 1: one prompt, and why it broke

QueryGPT started as a proposal at Uber's Generative AI Hackdays in May 2023.S1 Architecture The first version was retrieval plus few-shot prompting: a k-nearest-neighbour search over SQL samples and table schemas fetched 3 tables and 7 SQL samples, custom instructions were added (how Uber handles dates, for example), and one call returned a SQL query and an explanation. It started with 7 tier 1 tables and 20 SQL queries, on GPT-4 with a 32K-token window.S1 Hackdayz

As more tables and samples were onboarded, accuracy declined. Uber names three reasons:S1 Hackdayz

  1. The search compared the wrong kinds of text. An English question doesn't look like CREATE TABLE … or SELECT …, so similarity search returned poor matches.S1 Better RAG
  2. There was no step for intent. Going straight from a question to the right schemas was too hard; it needed a classification step first.S1 Better RAG
  3. Some schemas were enormous. Some tier 1 tables have 200+ columns and take 40–60K tokens each. Three of them broke the call, because the largest model available at the time took 32K.S1 Better RAG
the lesson in one line

More context in one prompt made it worse. Each problem became an agent with one small job.

story · 04The current design: small agents in a fixed order

Uber says there were "about 20+ iterations" between the hackathon version and the design it runs in production.S1 Architecture It starts with workspaces: curated sets of tables and SQL samples for one business domain, such as Mobility, Ads or Core Services. Then every question runs through three narrow agents before the SQL is written. "Picking a business domain allowed us to drastically narrow the search radius for RAG."S1 Intent Agent

analysis: is this "multi-agent"?

Uber calls these steps agents, and each one is an LLM call with a single job. But they don't negotiate, plan or call each other: plain code runs them in a fixed order, and a person sits between two of them. That is the most common and most reliable shape of "multi-agent" in production: a pipeline. Story · 11 shows the other shape, a supervisor that routes work, from another Uber team.

story · 06The human hand-off: confirm the tables

The table agent exists because users told Uber that the tables QueryGPT picked were sometimes wrong. So an LLM call now picks the tables and sends the list to the user, who either clicks "Looks Good" or edits the list before any SQL is written.S1 Table Agent

story · 07Context engineering: prune the columns

Two moments in the story are easy to blur, so keep them apart:

  1. The early problem. Tier 1 tables with 200+ columns used 40–60K tokens each, so three of them broke a 32K model.S1 Better RAG
  2. The later fix. After a wider rollout, on GPT-4 Turbo with a 128K-token limit (version 1106), Uber still saw intermittent token-limit failures from very wide tables. So it added the column prune agent, an LLM call that removes irrelevant columns.S1 Column Prune

story · 08How they tested it

Uber took real questions from QueryGPT's logs and checked by hand the right intent, the tables needed and a "golden" SQL query for each.S1 Evaluation Then it ran two product flows:

S1 Evaluation

The decoupled flow is the multi-agent lesson: if the table agent is wrong, a vanilla run can't tell you whether the generator is any good. For every question Uber records five signals:S1 Evaluation

  • Intent: right intent or not.
  • Table overlap, 0 to 1: needed [fact_trip_state, dim_city], picked [dim_city, fact_eats_trip], score 0.5.
  • Successful run: does the query execute?
  • Run has output: any records? This catches made-up filters such as status = "Finished" when the data says "Completed".
  • Query similarity, 0 to 1, scored by an LLM against the golden SQL.

One question failed again and again because it lacked a partition filter (a required date filter on a huge table), yet the LLM rated it 85% similar to the golden SQL.S1 Fig. 12 Close is not correct.

story · 10What Uber says it learned

  1. LLMs are excellent classifiers. The intermediate agents "improved our accuracy a lot" over the first version, largely because each one was "asked to work on a single unit of work rather than a broad generalized task".S1 Learnings No number is given.
  2. Hallucinations aren't solved. The model still invents tables and columns. Uber tried prompt changes, added a chat mode to iterate on the query, and is looking to add a "Validation" agent that fixes hallucinations.S1 Learnings
  3. User questions are often thin, down to "a 5 word question (with typos)", so a "prompt enhancer" was needed to enrich them first.S1 Learnings
  4. The bar is high. Many users expect the SQL to "just work", so Uber recommends launching and testing with the right personas first.S1 Learnings

Uber's conclusion names the same two open problems: handling large schemas and reducing hallucinations "persist".S1 Conclusion

story · 11The other shape: a supervisor (Uber's Finch)

In July 2025 a different Uber team, FinTech, published Finch, a data agent that answers finance questions in Slack. It is not QueryGPT's next version, but it shows the other common way to orchestrate agents.S2 Introduction

In Finch, built with LangGraph, a Supervisor Agent routes each question to a sub-agent such as the SQL Writer Agent, which looks up column and value aliases ("US&C" means US and Canada), checks the user's permissions, runs the query, and rewrites it if it fails.S2 Agent flow

practice · 01When to split one prompt into agents

Splitting has a cost: more calls, more latency, more places to fail. Use what you see in your own system to decide. analysis

You see thisShape to tryWhy
A small, stable schema; answers are mostly rightOne call with the schema and a few examplesVersion 1 worked fine at 7 tables.
Accuracy drops as you add tables or documentsPipeline: classify, select, generateEach step narrows the next one's context.
Token limits, or cost and latency climbingA pruning step before generationSend only the needed columns, plus keys.
Users spot a wrong choice faster than the modelA confirmation step at that choiceSeconds for a person, a wrong answer if skipped.
Very different kinds of requestA supervisor routing to specialist agentsFinch's shape; then test routing.

practice · 03Wiring it into your code

A small QueryGPT-style pipeline in plain Python: each agent is one LLM call with one job and a JSON answer that code checks. It is our implementation, not Uber's code; Uber published the design only. Any provider works through one llm(prompt) function:

# pip install openai   (the pipeline itself needs only the standard library)
import os

from openai import OpenAI

client = OpenAI()  # reads OPENAI_API_KEY from the environment


def make_llm(model: str):
    def llm(prompt: str) -> str:
        response = client.chat.completions.create(
            model=model,  # a chat model your account can use
            messages=[{"role": "user", "content": prompt}],
            temperature=0,  # grading wants repeatable output
        )
        return response.choices[0].message.content or ""
    return llm


llm = make_llm(os.environ["QUERYGPT_MODEL"])  # every agent call goes through this one function

1 · Intent and tables: small calls, strict answers

A reply that isn't JSON, or names an unknown workspace or table, is an error, never a guess. The confirm hook is the human hand-off: your UI returns the tables the person accepts.

import json
import re
import sqlite3
from collections.abc import Callable
from dataclasses import dataclass, field
from pathlib import Path

LLM = Callable[[str], str]

class AgentError(ValueError):
    """An agent's answer could not be used (bad JSON, unknown names, empty choice)."""

def ask_json(llm: LLM, prompt: str) -> dict:
    """One LLM call that must return a JSON object. Anything else is an AgentError, never a guess."""
    raw = llm(prompt).strip()
    raw = re.sub(r"^```(?:json)?\s*|\s*```$", "", raw)
    try:
        data = json.loads(raw)
    except json.JSONDecodeError as exc:
        raise AgentError(f"not JSON: {raw[:80]!r}") from exc
    if not isinstance(data, dict):
        raise AgentError("expected a JSON object")
    return data

# ---------- agent 1: intent -> workspace ----------
def intent_agent(llm: LLM, question: str) -> list[str]:
    menu = "\n".join(f"- {w.name}: {w.about}" for w in WORKSPACES.values())
    data = ask_json(llm, f"TASK: intent\nPick the workspaces this question needs.\n{menu}\n"
                         f'Question: {question}\nReturn JSON: {{"workspaces": ["..."]}}')
    picked = [w for w in data.get("workspaces", []) if w in WORKSPACES]  # drop names the model made up
    if not picked:
        raise AgentError("no known workspace fits; ask the user for more context")
    return picked

# ---------- agent 2: tables, then a person confirms or edits them ----------
Confirm = Callable[[list[str]], list[str]]

def accept_as_is(tables: list[str]) -> list[str]:
    return tables

def table_agent(llm: LLM, question: str, workspaces: list[str]) -> list[str]:
    allowed = sorted({t for w in workspaces for t in WORKSPACES[w].tables})
    data = ask_json(llm, f"TASK: tables\nPick the tables needed. Allowed: {', '.join(allowed)}\n"
                         f'Question: {question}\nReturn JSON: {{"tables": ["..."]}}')
    tables = [t for t in data.get("tables", []) if t in allowed]
    if not tables:
        raise AgentError("the table agent picked no known table")
    return tables

2 · Prune, then generate

The pruner can only remove columns, and keys and the date column always survive. The generator sees only the pruned schema, the allowed status values and the workspace's sample queries.

# ---------- agent 3: prune columns, but never the keys ----------
def column_prune_agent(llm: LLM, question: str, tables: list[str]) -> dict[str, list[str]]:
    schema = {t: SCHEMA[t] for t in tables}
    data = ask_json(llm, f"TASK: prune\nKeep only columns needed to answer.\nSchema: {json.dumps(schema)}\n"
                         f'Question: {question}\nReturn JSON: {{"keep": {{"table": ["col"]}}}}')
    keep = data.get("keep", {})
    pruned = {}
    for t in tables:
        wanted = {c for c in keep.get(t, []) if c in SCHEMA[t]}  # invented columns are dropped here
        pruned[t] = [c for c in SCHEMA[t] if c in wanted or c in KEYS[t]]  # joins and partitions survive
    return pruned

# ---------- the generator: SQL + explanation ----------
@dataclass
class Draft:
    sql: str
    explanation: str

def generate_sql(llm: LLM, question: str, pruned: dict[str, list[str]], samples: list[str],
                 error: str = "") -> Draft:
    values = {t: STATUS_VALUES[t] for t in pruned if t in STATUS_VALUES}
    retry = f"\nYour last query failed with: {error}\nFix it." if error else ""
    data = ask_json(llm, f"TASK: sql\nToday is {TODAY}. SQLite. Filter big tables by date_val.\n"
                         f"Tables and columns: {json.dumps(pruned)}\nAllowed status values: {json.dumps(values)}\n"
                         "Example queries from this workspace:\n" + "\n".join(samples) + "\n"
                         f'Question: {question}{retry}\nReturn JSON: {{"sql": "...", "explanation": "..."}}')
    if not isinstance(data.get("sql"), str) or not data["sql"].strip():
        raise AgentError("no SQL in the answer")
    return Draft(data["sql"].strip().rstrip(";"), str(data.get("explanation", "")))

3 · The pipeline

Plain code decides the order; no agent decides what runs next. A failed query goes back to the generator once, with the error message, the way Finch does it.S2 User journey

# ---------- the whole pipeline ----------
@dataclass
class Result:
    workspaces: list[str]
    proposed: list[str]
    tables: list[str]
    pruned: dict[str, list[str]]
    draft: Draft | None = None
    rows: list[tuple] = field(default_factory=list)
    error: str = ""
    attempts: int = 0

def run_pipeline(llm: LLM, conn: sqlite3.Connection, question: str,
                 confirm: Confirm = accept_as_is, max_attempts: int = 2) -> Result:
    workspaces = intent_agent(llm, question)
    proposed = table_agent(llm, question, workspaces)
    tables = [t for t in confirm(list(proposed)) if t in SCHEMA]  # the human hand-off
    pruned = column_prune_agent(llm, question, tables)
    samples = [s for w in workspaces for s in WORKSPACES[w].samples]  # few-shot examples from the workspace
    result = Result(workspaces, proposed, tables, pruned)
    for attempt in range(1, max_attempts + 1):
        result.attempts = attempt
        result.draft = generate_sql(llm, question, pruned, samples, error=result.error)
        try:
            result.rows, result.error = guard_and_run(conn, result.draft.sql, tables), ""
            return result
        except GuardError as exc:
            result.error = str(exc)  # fed back to the generator on the next attempt
    return result

The made-up warehouse (SCHEMA, KEYS, WORKSPACES, build_sample_db) is in the same file and isn't repeated here.

practice · 04Never run raw model SQL

Uber's post doesn't describe how generated SQL is checked before it runs; its validation agent is still a plan. So this part is ours. analysis The rule: the database itself refuses anything dangerous, so no prompt can talk its way past a regex.

  • Read-only connection (mode=ro; in your warehouse, a read-only role).
  • An authorizer: a SQLite callback that allows only SELECT, functions, and reads of the confirmed tables.
  • The plan first: EXPLAIN QUERY PLAN must show big tables searched by their date index, or the query would scan everything.
  • One statement, a row cap, and errors go back to the generator.
class GuardError(ValueError):
    """The guard refused to run a query."""

# ---------- the guard: what may reach the database ----------
ROW_CAP = 1000

def open_read_only(path: Path) -> sqlite3.Connection:
    """The database itself refuses writes: SQLite opened in read-only mode."""
    return sqlite3.connect(f"file:{path.as_posix()}?mode=ro", uri=True)

def guard_and_run(conn: sqlite3.Connection, sql: str, allowed: list[str], row_cap: int = ROW_CAP) -> list[tuple]:
    """Run one SELECT that may only read the confirmed tables, after checking its plan."""
    ok_tables, read = set(allowed), set()

    def authorizer(action, arg1, _arg2, _db, _trigger):
        if action in (sqlite3.SQLITE_SELECT, sqlite3.SQLITE_FUNCTION):
            return sqlite3.SQLITE_OK
        if action == sqlite3.SQLITE_READ and arg1 in ok_tables:
            read.add(arg1)
            return sqlite3.SQLITE_OK
        return sqlite3.SQLITE_DENY  # writes, PRAGMA, ATTACH, other tables: refused while compiling

    conn.set_authorizer(authorizer)
    try:
        plan = " | ".join(row[-1] for row in conn.execute("EXPLAIN QUERY PLAN " + sql))
        for table in read & PARTITIONED.keys():  # like Uber's "missing partition filter" error
            if not re.search(rf"SEARCH \w+ USING (?:COVERING )?INDEX {PARTITIONED[table]} \(date_val", plan):
                raise GuardError(f"{table} is not filtered on date_val: it would scan the whole table")
        rows = conn.execute(sql).fetchmany(row_cap + 1)
    except sqlite3.Error as exc:  # syntax errors, unknown columns, denied actions, several statements
        raise GuardError(str(exc)) from exc
    finally:
        conn.set_authorizer(None)
    if len(rows) > row_cap:
        raise GuardError(f"more than {row_cap} rows: aggregate or filter further")
    return rows
the tests that matter most

18 offline tests with a scripted LLM, including: DROP, UPDATE, PRAGMA, ATTACH, a second statement, an unconfirmed table and a full scan are all refused; a DELETE fails even without the guard because the connection is read-only; a wrong table pick runs and returns a plausible wrong number until a person edits the list; a made-up "Finished" status runs but has no output. analysis

practice · 05Evaluate each agent separately

Uber's signals, as code. The decoupled flow hands the generator the golden tables, so a wrong table pick can't hide whether the generator works; the table agent's own pick is still scored.

# ---------- evaluation: Uber's signals, per question ----------
def table_overlap(required: list[str], picked: list[str]) -> float:
    """Share of the required tables that were picked (0 to 1), as in Uber's example: 1 of 2 -> 0.5."""
    return len(set(required) & set(picked)) / len(set(required)) if required else 1.0

@dataclass(frozen=True)
class Golden:
    question: str
    workspace: str
    tables: tuple[str, ...]

def signals(llm: LLM, conn: sqlite3.Connection, case: Golden, flow: str = "vanilla") -> dict:
    """Vanilla: the agents' own choices all the way. Decoupled: generate from the golden tables, so a
    wrong table pick can't hide whether the generator works (component-level evaluation)."""
    confirm = accept_as_is if flow == "vanilla" else (lambda _proposed: list(case.tables))
    try:
        r = run_pipeline(llm, conn, case.question, confirm=confirm)
    except AgentError as exc:
        return {"intent": False, "overlap": 0.0, "ran": False, "has_output": False, "error": str(exc)}
    ran = r.error == ""  # "has output": Uber checks for > 0 records; we also treat a lone COUNT of 0 as empty
    return {"intent": case.workspace in r.workspaces, "overlap": table_overlap(list(case.tables), r.proposed),
            "ran": ran, "has_output": ran and any(any(v not in (None, 0) for v in row) for row in r.rows),
            "error": r.error}

In the tests, a table agent that forgets trips scores 0.5 in both flows; the vanilla query never runs, the decoupled one returns data. So the problem is the table agent, not the generator.

practice · 06Rules of the road

Keep these in plain code

  • The order of the agents, and which tables each step may use.
  • Checking every agent's JSON against the known workspaces, tables and columns.
  • Keeping keys and partition columns through pruning.
  • Read-only access, the allow-listed tables, the plan check and the row cap.

Let the agents do only this

  • Classify (workspace), choose from a list (tables, columns), and write one query with an explanation.S1 Learnings

Watch out for

  • Made-up tables and columns: Uber still sees them.S1 Learnings
  • Filters on values the data doesn't contain; check "has output", not just "ran".S1 Evaluation
  • Reading a 5% wobble as progress.S1 Limitations
  • Quoting estimates as results.

practice · 08When it breaks: symptoms, causes, fixes

Read a symptom, guess the cause, then open the card. analysis except where a card cites Uber.

Likely cause. The model invented a column, which Uber says still happens.S1 Learnings

Fix. Give the generator only real column names, and send the error back for one rewrite.

Likely cause. A filter on a value that doesn't exist, like "Finished" instead of "Completed".S1 Evaluation

Fix. Show the generator the allowed values, as Finch does with aliases, and track "has output".S2 Architecture

Likely cause. A missing partition filter, Uber's own example.S1 Fig. 12

Fix. Put the rule in the instructions, and check the query plan before running it.

Likely cause. One or more very wide tables in the request.S1 Column Prune

Fix. A column prune step that keeps only the needed columns, plus the keys.

Likely cause. Too little context; Uber saw five-word questions with typos.S1 Learnings

Fix. A prompt enhancer first, or ask the user when no workspace fits.

Likely cause. An intent collision: the question is ambiguous, or two tools overlap.S2 Evaluation

Fix. Measure routing accuracy on its own, and make tool descriptions distinct.

practice · 10Interview prep

Try answering before you open each one. documented = from Uber's posts, analysis = reasoning you would add.

architectureWhy did Uber's first QueryGPT get worse as tables were added?

documented Questions didn't match schema or SQL text in similarity search, there was no intent step, and huge schemas overflowed the 32K model.S1 Better RAG

analysis More candidates, more chances to pick the wrong one.

orchestrationWhy split the work into intent, table and prune agents?

documented LLMs did well as classifiers when each was given "a single unit of work"; the agents improved accuracy a lot over version 1.S1 Learnings

analysis Each step narrows the next one's context, and each can be tested and fixed on its own.

human in the loopWhy ask the user to confirm the tables, and not the final SQL?

documented Users reported wrong tables, so the table agent sends its pick for "Looks Good" or edits.S1 Table Agent

analysis A table list takes seconds to check; checking SQL takes expertise. And a wrong table gives a query that runs and answers a different question.

contextHow does column pruning help, and what can go wrong?

documented It fixed intermittent token-limit errors on a 128K model and cut cost and latency (no numbers). Uber's example keeps city_id as a possible foreign key.S1 Column Prune

analysis Dropping a join key or partition column breaks the query, so keep keys in code.

safetyHow do you stop model-written SQL from doing damage?

analysis A read-only role, confirmed tables enforced by the database, one SELECT, a plan check, a row cap, and permissions checked first, as Finch does.S2 User journey

designFixed pipeline or supervisor: how do you choose?

documented QueryGPT runs fixed steps; Finch's supervisor routes questions to sub-agents and is tested for routing accuracy.S2 Evaluation

analysis Same steps for every request: a pipeline, simpler to debug. Different tools per request: a supervisor, and measure the routing.

wrap-upConclusion: small jobs, one human check

Uber's first version gave the model more context and got worse. The version that worked gave each LLM call one small job, put a person at the step they judge fastest, cut the schema down before generation, and measured each piece on its own.

Four things to carry away

  • Split a hard task into narrow steps an LLM is good at: classify, choose, then generate.
  • Put the human check where a person can verify quickly and a mistake is expensive.
  • Engineer the context: fewer tables, fewer columns, always the keys.
  • Evaluate each agent separately, and never run model-written SQL without a read-only guard.

referenceGlossary

Text-to-SQL
Turning a natural-language question into a SQL query.
Workspace
Uber's curated set of tables and sample queries for one business domain.
Intent agent
An LLM call that classifies a question into a workspace.
Table agent
An LLM call that proposes the tables a query needs, for a person to confirm.
Column pruning
Removing the columns a question doesn't need from the schemas sent to the model.
k-nearest neighbours
Finding the stored items whose vectors are closest to the query's vector.
Golden SQL
A query checked by hand as a correct answer to an evaluation question.
Partition filter
A filter on the column a huge table is split by, usually a date, so the query reads only part of it.
Vanilla / decoupled
Uber's evaluation flows: end to end, or each stage given the correct input.
Authorizer
A SQLite callback that allows or denies each action while a query is compiled.
Supervisor agent
An agent that routes each request to a specialist sub-agent.
Intent collision
A routing mistake when a question is ambiguous or two tools overlap.
