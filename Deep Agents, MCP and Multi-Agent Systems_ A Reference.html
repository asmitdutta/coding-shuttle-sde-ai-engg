A reference to how long-running agents are built: the agent harness, planning and delegation, context management, the Model Context Protocol, and the patterns of multi-agent orchestration. Theory first, with small snippets and the diagrams that explain how the pieces fit.

What this reference covers

Agents that run for minutes or hours need more than a model that can call tools. They need a way to plan, to keep their working memory under control, to delegate, to pause for a person, and to reach the outside world safely. This reference explains how those pieces work and how they fit together. It is organised as a book, from the basic loop up to the patterns that coordinate many agents, and every chapter can be read on its own.

It is deliberately theory first. The aim is to give you an accurate mental model of each mechanism, so that when you meet the code you recognise what it is doing and why. Code appears only as short snippets. The diagrams are the main teaching tool.

part IFoundations

Before the machinery, the problem. This part builds the basic model of an agent, explains why long-running work breaks it, and places the tools you will meet (LangChain, LangGraph, Deep Agents) in a single map.

1.1From model calls to agents

A language model on its own turns text into text. An agent wraps a model in a loop so that it can act: look at the situation, decide what to do, use a tool, see the result, and decide again. Everything in this reference is a refinement of that loop.

The agent loop

The loop has two steps. In the model call, the model receives the conversation so far and a description of the available tools. It returns either a final answer or a request to run one or more tools. In tool execution, the application runs the requested tools and appends their results to the conversation. The loop repeats until the model answers without asking for a tool.

The agent loop. The model chooses; the tools act; observations flow back. The loop ends when the model produces a result instead of an action.

Two properties of this loop matter for everything that follows. First, the state is the message list. Each tool call and each result is appended, so the model sees a growing history on every call. Second, the model decides the control flow. Nothing outside the model says which tool comes next, or when to stop.

Workflows and agents

Anthropic draws a useful line between two ways of using models. In a workflow, code defines the path: the model is called at fixed points. In an agent, the model directs its own process and tool use.

WorkflowAgent
Who decides the next stepYour codeThe model
PredictabilityHigh: the same path every timeLower: the path depends on what is found
Cost and latencyKnown in advanceOpen-ended
Best forTasks that decompose into fixed stepsOpen-ended problems where the number of steps cannot be predicted
Main riskBrittle when the task variesCompounding errors, runaway cost

The two are not rivals. Real systems mix them, using workflows for the parts that must be reliable and agents for the parts that must adapt. The advice that runs through the field is to find the simplest solution that works, and add autonomy only when it measurably helps.

What an agent is made of

LangChain summarises the idea as agent = model + harness. The model supplies the reasoning. The harness is everything around it that turns a model into a working agent.

Middleware: hooks around the loop

If the loop is where an agent works, middleware is where you shape it. LangChain exposes hooks at every point of the loop, so that behaviour such as summarising history, redacting data, retrying failures or pausing for approval can be added without rewriting the loop.

Middleware hooks in the agent loop. Hooks run before and after the agent and each model call, and wrap the model call and the tool call.

HookRunsTypical use
before_agent / after_agentOnce per runLoad memory or skills, save results
before_model / after_modelAround every model callTrim or summarise messages, pause for approval, enforce limits
wrap_model_callAround the model call itselfChange the prompt or tools for one call, retry, fall back to another model
wrap_tool_callAround each tool executionRetry, cache, intercept or log a tool call

Many of the features in the next parts, including to-do lists, summarisation, human approval and limits, are implemented as middleware. That is why they can be switched on, replaced or combined.

  • An agent is a model in a loop with tools. The state is the message list, and the model decides the control flow.
  • A workflow fixes the path in code. An agent lets the model choose it. Mix both, and prefer the simplest that works.
  • Agent = model + harness. The harness is the prompt, tools, context, memory, skills and subagents around the model.
  • Middleware hooks let you shape each step of the loop without rewriting it.

1.2Why long-running tasks are hard

A simple agent handles a question that takes a handful of tool calls. Give it an assignment that needs hundreds, such as researching a topic across dozens of sources, and it starts to fail in predictable ways. Understanding those failures explains most of the design choices in the rest of this reference.

Context is a finite resource

The model can only reason over what is in its context window, and it does not use all of that equally well. Anthropic describes context rot: as the number of tokens grows, the model's ability to recall information from the context declines. It is a gradient, not a cliff. The cause is an attention budget. Self-attention relates every token to every other token, which means a quadratically growing number of pairwise relationships, and models see far fewer long sequences than short ones in training.

The practical rule that follows is to give the model the smallest possible set of high-signal tokens that makes the desired result likely. More context is not better context. LangChain adds a second diagnosis. When an agent fails, either the model was not capable enough, or it was not given the right context, and the second is the far more common reason. Context engineering is the work of providing the right information and tools, in the right format, at each step.

How simple agents fail

FailureWhat happensRoot cause

Mechanisms that address them

Each failure has a corresponding mechanism. The rest of this reference is a tour of them. The pattern in all of them is the same: keep the work outside the conversation, and bring in only what the model needs for the next decision.

Each failure of a simple agent has a matching mechanism in a deep agent.

Three techniques for long horizons

Anthropic names three general techniques for work that outgrows a single context window. They are not exclusive, and a deep agent uses all three.

TechniqueIdeaTrade-offSuits
CompactionSummarise the conversation as it nears the limit and continue in a fresh window with the summary. The lightest form is clearing old tool results.Aggressive summaries can drop details that matter laterLong back-and-forth conversations

  • Most agent failures are context failures: the right information was missing, or buried.
  • Simple agents fail on long tasks in seven predictable ways, and each has a corresponding mechanism.
  • The common remedy is to keep work outside the conversation: compaction, note-taking and subagents.

LangGraph in brief

LangGraph models a workflow as a graph of three parts. State is a shared snapshot of the application. Nodes are functions that read the state, do work and return updates. Edges are fixed or conditional transitions that decide which node runs next. Put simply, nodes do the work and edges decide what runs next.

A tiny graph. The two search nodes run in the same super-step because they were activated together.

Execution is organised in super-steps, in the style of Google's Pregel system. A node becomes active when it receives input on an incoming edge. Nodes that run in parallel share one super-step, and nodes that run in sequence use separate ones. The run ends when every node is inactive and no messages are in flight. This model gives LangGraph a natural place to save state: at the boundary between super-steps.

TermMeaning
StateThe shared data the graph reads and updates. Usually a typed schema.
ReducerA rule for merging updates to a state key, for example appending to a list instead of overwriting it. It is what makes parallel writes safe.
NodeA function from state to a state update. It is also a checkpoint and retry boundary.
EdgeA transition to the next node, fixed or conditional
Super-stepOne round of execution. Parallel nodes share it.
SendRuns one node once per item, in parallel, when the number of items is only known at run time (map-reduce, orchestrator-worker)
CommandLets a node update state and choose the next node in the same step
InterruptA pause that saves state and waits for outside input

You will not build graphs by hand in the chapters that follow. Deep Agents constructs one for you. The graph matters because its properties, checkpoints at super-step boundaries, nodes as retry units, interrupts as pauses, are the properties your agent inherits.

2.1The Deep Agents harness

Deep Agents is an agent harness: an opinionated, batteries-included layer that supplies the tools, prompts and context machinery that long-running agents need. It is an open-source library, and it runs on LangGraph. This chapter describes what it is made of before the following chapters examine each part.

Why deep agents exist

An agent that calls tools in a loop tends to be shallow: it copes with short tasks and struggles to plan and act over long ones. Products that broke through that limit, such as Claude Code, deep-research agents and Manus, turned out to share four ingredients. They still run a model in a loop calling tools, but they add the following.

IngredientWhat it contributes
Detailed system promptLong instructions on how to use the tools, with examples of how to behave in specific situations. Prompting still matters a great deal.
Planning toolA to-do list that keeps the agent on track over long horizons. It performs no real action; its value is in shaping the model's context.
SubagentsFocused workers that let each subtask go deeper, with their own clean context
File systemNotes and artefacts written to files: memory, and a shared workspace for the lead agent and its subagents

The next chapters are, in effect, a closer look at the last three, plus the context-management and control features that surround them.

The capability map

The harness groups its capabilities into four areas. They are the table of contents of Part II.

What is on by default

Some capabilities are always present. Others switch on when you pass the matching option. The harness is assembled from middleware, in a fixed order. This is the order, with the layers that need configuration marked as opt-in:

FilesystemDefault. File tools over a pluggable backend. Enforces permission rules when you set them.
SubagentsDefault. The task tool, with a built-in general-purpose subagent. Added only if at least one synchronous subagent exists.
SummarisationDefault. Compresses history as the window fills.
Tool-call patchingDefault. Repairs the message history after interrupted tool calls.
Async subagentsOpt-in. Background tasks on an Agent Protocol server.
Your middlewareOpt-in. Planning, limits, retries, fallbacks, anything you add.
SkillsOpt-in. Present when you pass skill sources.

MemoryOpt-in. Present when you pass memory files.
Human-in-the-loopOpt-in. Present when you name tools to gate.

How the system prompt is assembled

The harness builds the system message from several layers in a fixed order, so you can reason about what the model sees. Your instructions come first and the harness adds its own sections after them.

1. Your promptThe system_prompt you pass
2. Base promptThe harness's general instructions about how to work
3. MemoryThe contents of the memory files, if any
4. SkillsThe name and description of each skill, not the full text
5. FilesystemHow to use the file tools
6. SubagentsThe list of delegates and how to call them
7. Middleware and approvalSections added by your middleware, and the approval notice when gates are set

Anything that varies per run can be injected with dynamic-prompt middleware, which can read the run's runtime context and store. Everything that is always loaded costs tokens on every model call, which is the reason chapter 2.5 separates always-loaded memory from on-demand skills.

  • Deep agents add four ingredients to the loop: a detailed prompt, a planning tool, subagents and a file system.
  • The harness groups its features into execution environment, delegation, steering and context management.
  • It is assembled from ordered middleware. Planning, skills, memory, async subagents and approval are opt-in.
  • The system prompt is built from layers, and everything always loaded is paid for on every call.

2.2Planning and task decomposition

A broad request has to become a set of smaller tasks, and the agent has to remember which are done. Deep Agents handles this with a structured to-do list. The mechanism is simple, and it is worth understanding why something so simple helps.

Why a to-do list helps

The planning tool does nothing in the environment. It does not run a task or schedule one. When the agent calls it, the tool only records the list. The benefit is entirely in the model's context: writing the plan out, and rewriting it as work completes, keeps the objective and the remaining steps in recent, high-attention context. It is a context-engineering device, an instance of the structured note-taking technique from chapter 1.2, and it is effective even though the tool is effectively a no-op.

How the tool works

The planning capability is provided by TodoListMiddleware, which adds a write_todos tool. Each call supplies the current list, and each item has a status. The list is stored in the agent's state under the key todos, so the application can read it at any time and show progress to a user.

Each task moves through three states. The list is rewritten as the agent learns, so the plan stays honest.

from langchain.agents.middleware import TodoListMiddleware

agent = create_deep_agent(model=MODEL, middleware=[TodoListMiddleware()])
# during a run, result["todos"] holds: [{"content": "...", "status": "in_progress"}, ...]

Step by step

Here is the run in order. Times are offsets from the start. Notice who does what: the model decides, the hooks check and route, the tools act, and the state (messages, to-dos, files) is what carries information from one step to the next.

  1. The query arrives 0:00. The input is a single user message. The agent's state holds that message and an empty to-do list.
  2. The start hook runs. PatchToolCallsMiddleware.before_agent finds no unanswered tool calls and returns at once.
  3. Model call 1 decomposes the task 0:00, 3.9 s. The model receives the system prompt, which includes the planning instructions and the description of write_todos, and the query. It does not search. Its reply has no text, only one tool call: write_todos with four items. The first, researching hiring trends, is in_progress; salary impact, company adoption and supporting evidence are pending. Nothing in the code split the query. The model did it, prompted by the tool and its instructions.
  4. The after-model hook checks the reply. One write_todos call: acceptable. There are tool calls, so the graph routes to tools.
  5. The to-do tool runs 0:03, 1 ms. It replaces the todos key in state with the new list and returns a tool message, "Updated todo list to [...]". No outside system was touched. The only effects are on state and on what the model will read next.
  6. Model call 2 starts on item one 0:03, 1.8 s. The model now sees the plan and the confirmation. It calls search_web with one broad query that covers several of the tasks at once.
  7. The search runs 0:05, 0.44 s. Five results with snippets come back and are appended to the conversation.
  8. Model call 3 acts and updates the plan together 0:06, 5.1 s. Reading the results, the model issues two tool calls in one reply: extract_pages for the five URLs, and write_todos with a new list in which the first task is gone and salary impact is now in_progress. The plan update rode along with real work, so it cost no extra model call.
  9. Both tools run in parallel 0:11. Extraction takes 2.1 s; the list update is instant. The extracted page text, long and unfiltered, is appended to the conversation.
  10. The rhythm repeats. Call 4 0:13, 2.5 s only updates the list (company adoption becomes in_progress). Call 5 0:15 searches again (1.4 s). Call 6 0:19, 4.5 s extracts more pages and updates the list in the same reply. Each pass is the same three beats: the model chooses, the hook checks and routes, the tools run.

When planning helps, and when it does not

It helps when

  • The task has many steps or needs many tool calls.
  • The steps can be split into independent parts.
  • New information may change the plan.
  • A person wants to follow progress.

It adds overhead when

  • The task is a single lookup or a short exchange.
  • The steps are fixed and trivial.
  • Every extra model call matters more than structure.
  • The to-do tool does nothing but record a list, and that is the point: it keeps the objective in recent context.
  • Tasks have three states and the whole list is rewritten as the agent learns. It lives in the todos state key.
  • Plans, to-do lists and task briefs are different artefacts. Independent tasks are what make delegation possible.
  • In a real trace the model decomposes the query in its first call, then loops: choose, check, run. The hooks and the to-do tool cost milliseconds; the model's turns and the growing prompt are what cost time and money.
  • Planning is opt-in from deepagents 0.7. Skip it for short tasks.

2.3Subagents and delegation

Delegation is the most powerful idea in the harness. A lead agent hands a task to a specialist, the specialist works in its own context, and only a short result comes back. This chapter explains the mechanism, what each side can see, how subagents are defined, and the trade-offs between the three ways of running them.

The delegation model

In the subagents pattern, a main agent coordinates specialised subagents by calling them as tools. All routing goes through the main agent: the user talks to it, it decides who does what, and it composes the final answer.

The subagents pattern. Control returns to the main agent after every delegation; subagents rarely talk to the user directly.

In Deep Agents, delegation is one built-in tool, called task. The model calls it with the name of a subagent and a description of the work. A dispatcher looks the subagent up, runs it, and returns its final message as the tool result. From the main agent's side, a subagent is just a tool whose implementation happens to be another agent.

Anatomy of a delegation

Every delegation costs model calls. The sequence below shows the smallest case, one subagent doing one task, and counts them. The main agent needs a call to decide to delegate and another to compose the answer, and the subagent needs its own calls.

One delegation, four model calls. Delegation buys isolation and parallelism, and it is paid for in calls.

Context isolation

The defining property of a subagent is what it does not see. By default it starts with a fresh context that contains only the task description. It does not receive the lead agent's conversation, its earlier tool results or its other subagents' work. Everything the subagent reads and searches stays in its own window. The lead agent receives one thing: the subagent's final message.

Detail stays inside the specialist. The lead agent gets a compact handoff and references to the saved artefacts.

This is context isolation, not merely a way of having more agents. The lead agent's context stays small enough to keep reasoning about the whole task, while each specialist can spend its whole window going deep on one part. Anthropic reports that subagents commonly return a condensed summary of one to two thousand tokens after exploring far more.

Isolated and forked subagents

Isolation is the default, but not the only choice. A forked subagent receives the parent's conversation history as well, with a short preamble that tells it to continue. Use a fork when the subagent must pick up work the parent has already started, for example to write comments about issues the parent has already found. Forks cost more, cannot delegate further, and can reduce prompt-cache reuse, so isolation remains the default.

The task tool is attached only if at least one synchronous subagent exists.

Structured handoffs

When the lead agent must parse the result or pass it to another tool, set response_format to a schema. The lead then receives JSON matching the schema instead of prose. This is how a reviewer returns a verdict the application can act on (chapter 2.9). If a subagent's model refuses, the lead receives a short result saying so rather than an empty one, and an error inside a subagent does not leak its partial state to the parent.

Parallel delegation

Subagents pay off most when independent topics are explored at the same time. The lead agent decomposes the task, issues several delegations in one step, waits for all of them, and then composes. Total latency approaches that of the slowest worker rather than the sum, and each worker's window holds only its own topic.

Fan-out and fan-in with subagents. In LangChain's measurement of this task, the subagents pattern used about 9K tokens against about 15K for the skills pattern, because each subagent saw only its own domain.

Designing the handoff

The quality of delegated work is set by the brief. Anthropic found that vague instructions made subagents duplicate each other's work or leave gaps. A good brief states four things.

ElementQuestion it answersIf missing
ObjectiveWhat exactly should the worker find out or produce?Overlap between workers, or drift
Output formatWhat should it return, and how long?Raw dumps flood the lead's context
Tools and sourcesWhere should it look, with what?Wrong tools, weak sources
BoundariesWhat is out of scope? What must it not touch?Duplicated effort, unintended side effects

Equally important is the return path. Ask the worker to put detail in files and return a summary, key limitations and the file paths. Handing artefacts over by reference avoids the "game of telephone", in which each retelling loses detail and costs tokens. Effort should also scale with the task. Anthropic's guidance for its research system is a single agent with a few tool calls for a simple fact-finding question, two to four subagents for a comparison, and more than ten, each with a clearly divided responsibility, for complex research.

When not to delegate

Do not delegate

  • A single lookup or one quick tool call.
  • A step that needs the lead agent's whole conversation.
  • Tightly coupled work where workers would need each other's intermediate results.
  • Anything where the cost of a model call exceeds the saving.

Do delegate

  • A topic that needs many searches or reads.
  • Output the lead does not need to see in full.
  • Independent topics that can run in parallel.
  • A task that needs a different model, tools or instructions.
  • Delegation is one tool, task. A subagent is a tool implemented by another agent, and its final message is the result.
  • Isolation is the point: a subagent sees only its brief, and the lead sees only its summary. Forks share history and cost more.
  • Define subagents explicitly. A missing tools key means inherited tools, and skills and middleware are not inherited.
  • Synchronous is the default. Asynchronous suits long, steerable or parallel jobs and needs an Agent Protocol server.
  • A good brief states objective, output format, tools and boundaries. Hand detail over by file, not by retelling.
  • In a real trace the lead delegates in one reply, the subagents run in parallel as nested graphs, and only short summaries return. The lead's context stays small, while the subagents spend most of the tokens. Instructions are not guarantees: check the paths, the files read and the to-do list.

2.4The virtual filesystem

Every deep agent has a filesystem. It is not there for convenience. It is where the agent keeps everything that should not live in the conversation: search results, notes, drafts, evidence, reviews. This chapter explains why files are the right working memory, what the tools and backends are, and how access is controlled.

Files as working memory

The conversation is expensive and temporary. Every message in it is resent on every model call, and it disappears with the thread. A file is the opposite: cheap to keep, readable on demand, and inspectable by people. Treating files as the working memory has three consequences.

  • Just-in-time retrieval. The agent holds lightweight identifiers, such as paths, and loads the content only when it needs it. Anthropic describes this as the way agents explore without carrying everything: names, folder structure and timestamps all signal what a file is for.
  • Handoff by reference. One agent writes a file and tells another where it is. Nothing is retold, so nothing is lost or paid for twice.
  • Inspectability. Sources, findings and drafts exist as artefacts that a reviewer can open, diff and check.
The filesystem is the workspace. The conversation is not the database.Messages hold the current interaction. Facts, sources and drafts belong in files.

The default state backend is shared by the lead agent and all its subagents, and files a subagent writes remain after it finishes. That is exactly what makes it a handoff mechanism. Choosing a backend is a decision about persistence scope and trust: how long files should last, who may see them, and what a mistake could reach.

A disk backend gives an agent real read and write access. It can read any file under its root, including secrets such as .env, and combined with a network tool could send them out. Routing with a composite backend

A composite backend maps path prefixes to different backends, so one agent can keep scratch files per thread, durable memories across threads and a project folder on disk, all in one namespace. The longest matching prefix wins, and the prefix is removed before the request reaches the chosen backend. Listings and searches combine results from every route.

Typical set-ups keep the thread-scoped state backend as the default and route one prefix, often /memories/, to a store so that it survives across threads. Seed such a store with backend-relative keys, because the route prefix is stripped.

Offloading large results

The filesystem also protects the context window automatically. When a tool returns a very large result, the harness writes it to the backend and leaves the model a short pointer. The agent can read the file back, or search it, when it needs details. Results larger than about 20,000 tokens are offloaded this way, and the model keeps the path and a ten-line preview.

Offloading a large tool result. The full text goes to the filesystem and a short pointer replaces it in context.

The same idea applies to large inputs. When the agent has written a big file through a tool call, the full content is already on disk, so once the session passes 85% of the model's window the older call is truncated to a pointer. Offloading is the first and cheapest line of defence. It loses nothing, because the original is a file read away.

Permissions

Giving every agent unrestricted file access is rarely what you want. A reviewer should not rewrite the evidence it is reviewing. Permissions are an ordered list of rules, checked before the backend is called, that apply to the built-in file tools.

FieldMeaning
operationsread (ls, read, glob, grep) and write (write, edit, delete)
pathsGlob patterns. ** matches recursively; {a,b} matches alternatives.
modeallow, deny, or interrupt (pause for a person; needs a checkpointer)

Rules are evaluated in order, and the first rule that matches decides. If none match, the operation is allowed. The consequence is that narrow rules must come before broad ones.

permissions = [
    FilesystemPermission(operations=["write"], paths=["/research/*/reviews/**"], mode="allow"),
    FilesystemPermission(operations=["write"], paths=["/**"], mode="deny"),
]

A subagent's own permissions replace the parent's rules rather than adding to them. There are limits to know about. Permissions cover only the built-in file tools: a custom tool or an MCP tool that touches the disk is not covered, and neither are sandbox backends, which can run arbitrary commands. Combine permissions with tool allowlists and, for sensitive paths, the interrupt mode.

Executing code

File tools read and write. Some tasks also need to run things. The harness supports this through backends that add an execute tool, and through interpreters.

OptionWhat it providesRisk
Sandbox backendA shell inside an isolated environmentContained. The right choice for untrusted input and for production.
Local shell backendShell commands on your own machine, with your permissionsHigh. Suited only to trusted local development. Confining paths gives no protection once a shell is available.
InterpreterA restricted JavaScript evaluator with no shell or network accessLow

Where a shell exists, put it behind human approval, keep secrets out of reach, and prefer a sandbox. Skills that include scripts run only in sandbox backends.

  • Files are the agent's working memory: cheap, inspectable and shareable by path. Messages are not a database.
  • Tools call a backend interface. State is the default (per thread). Disk, store, sandbox and composite backends change persistence and trust.
  • A composite backend routes by path prefix, longest match first, so one agent can mix thread-scoped and durable storage.
  • Results over about 20,000 tokens are offloaded to a file, leaving a path and a short preview.
  • Permissions are ordered rules where the first match wins. They cover only built-in file tools.

The filesystem holds facts about one piece of work. Two further mechanisms hold knowledge that outlives it: memory, for rules that are always true, and skills, for procedures needed only sometimes. They look similar and behave differently, and getting the split right is mostly a question of what you are willing to pay for on every model call.

Progressive disclosure

The defining idea of skills is that they are loaded in layers. At start-up the agent sees only a short description of each skill. It reads a skill's body only when a task calls for it, and the scripts and reference files only when the instructions point to them. Adding fifty skills therefore costs fifty short descriptions, not fifty manuals.

Only descriptions are always in context. A body enters context when its skill is activated, and resources only when the instructions reference them.

Three levels of cost follow from this. The metadata level is always paid, so descriptions must be short and precise. The instructions level is paid only on activation, so a skill can be detailed. The resources level is paid per reference, so large material belongs there. Skills load once per thread and persist in state, which means editing a skill file does not affect a thread already running.

2.6Context engineering

Every earlier chapter has been a context technique in disguise: planning restates the goal, subagents isolate detail, files offload it, skills load it late. This chapter pulls them into one framework, so you can decide for any piece of information what the model should see, when, and where it should live otherwise.

What context engineering is

Context engineering is the practice of curating the tokens the model sees on each call, covering instructions, tools, external data and message history. It extends prompt engineering because an agent generates new information every turn, so curation never finishes: it happens each time something is passed to the model. LangChain's diagnosis is that agents mostly fail not because the model is weak but because it was not given the right context, which makes this the central skill of agent engineering.

Three kinds of control

LangChain divides what you can control into three kinds, along the lines of the agent loop from chapter 1.1. The important axis is whether a change is transient, affecting one call, or persistent, saved in state.

Tool contextWhat tools can read and write: state, store, runtime contextPersistentA tool that reads a user's preferences, or records a result in state
Life-cycle contextWhat happens between model and tool callsPersistentSummarisation, guardrails, logging

Context comes from three data sources, with different scopes. Telling them apart prevents most confusion about where something should be kept.

Runtime context is supplied when a run starts. The model does not see it unless a tool or middleware puts it in the prompt, which makes it the right home for credentials and identifiers. It is immutable for the run and propagates to subagents and their tools. Data that must change during a run and be saved with the thread belongs in state instead.

Two details are worth knowing. Summarisation changes only what is sent to the model: the saved message history is unchanged. And because a copy of the conversation goes to a file, the agent can recover a detail the summary dropped. The weakness remains the one from chapter 1.2: an over-aggressive summary can discard something that turns out to matter, which is why the best protection is to have saved the important material in files before compression ever has to guess.

Isolation and just-in-time loading

Compression is a repair. The better strategy is prevention: never put the material in the window in the first place. Isolation keeps exploratory detail inside a subagent. Just-in-time loading keeps skills, files and tool definitions out of context until they are needed. Both follow the principle from chapter 1.2, that the goal is the smallest set of high-signal tokens.

Keeping the prefix stable

Most providers cache the beginning of a prompt, including the list of tool definitions, and charge less for cached tokens. Changing the tools or the early part of the prompt mid-conversation invalidates that cache, and the miss can cost more than the change saved. Deep Agents applies prompt caching automatically on Anthropic and Bedrock models. The practical advice is to keep the prompt prefix and the tool list stable within a conversation, and to add new material at the end.

  • Context engineering is curating what the model sees on each call. Most agent failures are context failures.
  • Control splits into model context (transient), tool context and life-cycle context (persistent).
  • Three data sources: runtime context (per run, read-only), state (per thread), store (across threads).
  • Compression escalates: offload large results first, summarise at about 85% of the window. Neither loses the original.
  • Prevention beats repair: isolate with subagents, load late with skills and files, and keep the prompt prefix stable.

2.7Human oversight and durable execution

An agent that can act can act wrongly, and some actions cannot be undone. Human-in-the-loop control puts a person between the model's decision and its execution for the actions that matter. It rests on a second capability, durable execution: the ability to stop a run, keep its state safely, and continue it later, possibly from a different process.

When to involve a person

Approval costs attention and time, so it should be targeted. A useful rule is to gate by consequence, not by tool type.

Consequence of a wrong callTypical policyExample
None: read-only, cheap, reversibleNo gateSearch, read a file
Moderate: costly or externally visible, but recoverableApprove or rejectStart an expensive batch, send a notification
Severe: destructive or irreversibleApprove, edit or reject, with clear arguments shownDelete data, spend money, publish

The gate must be a mechanism, not a request. If the model merely asks the user a question in its reply, nothing stops the next tool call, and there is no saved state to come back to. A real gate holds the tool call before it runs.

How a pause works

Pausing combines two parts of the runtime. An interrupt stops the graph at a point and surfaces a payload to the caller. A checkpointer saves the full state at that moment, under a thread id. The run that stopped is not waiting in memory: it has ended, and its state is on disk. Resuming starts a new run on the same thread, with the human's answer supplied as the interrupt's return value.

A pause is a saved checkpoint plus an interrupt. The same thread id is the pointer that finds it again.

Three consequences follow. A checkpointer is required: without one, the interrupted run has nowhere to leave its state. The thread id must be reused on resume: it is the only link between the two calls. And the application owns the interface: the harness pauses the run and reports what is pending, but it does not provide an approval screen.

Decisions and policies

A gate is configured per tool. A tool can be gated with all decisions available, not gated, or gated with a restricted set of decisions. When the agent reaches a gated call, the flow is as follows.

DecisionEffectUse it for
approveRuns the tool with the original argumentsThe proposal is right
editRuns the tool with arguments you supply. The model is told a human replaced its call.Right idea, wrong scope. Keep edits small, since large ones make the model re-plan.
rejectSkips the tool and returns your message to the modelDenials. Say whether to stop, ask a follow-up or try something safer.
respondReturns your text as a synthetic tool result, without running the toolOnly when you are answering on the tool's behalf, such as an "ask the user" tool. Never to deny a side-effecting tool: the model may read the message as success.

The configuration for each tool is True (all four decisions), False (no gate) or a dictionary that limits allowed_decisions. When several calls need approval in one step they arrive together, and you must answer each one, in the order received.

interrupt_on = {
    "delete_file": True,                                           # approve, edit, reject, respond
    "send_email": {"allowed_decisions": ["approve", "reject"]},    # no editing
    "read_file": False,
}

What a gate protects

A gate guards the tool you named, and nothing else. This is the point where designs most often have a hole. If an agent can reach the same effect through a different tool, such as delegating to a subagent that has its own copy of the action, the gate on the first tool is not a gate.

MechanismGuardsNotes

The same applies to external tools: the spec for the Model Context Protocol says a human should be able to deny tool invocations, and a gate by tool name works on discovered tools like any other.

Rules for interrupts

The way a pause works has consequences for how code around it must be written. When a node is resumed, the runtime restarts the whole node from its beginning. It does not continue from the line that paused. Everything before the interrupt runs again.

RuleWhy
Make side effects before an interrupt idempotentThey will run again on resume. Use idempotency keys, upserts or read-before-write checks.
Do not wrap an interrupt in a broad try/exceptThe pause is implemented as an exception. Catching it swallows the interrupt.
Do not reorder interrupt calls within a nodeResume values are matched by position. A different order mismatches them.
Keep interrupt payloads simple and serialisableThey are saved and sent to the caller

These rules come from a general fact about LangGraph: checkpoints are saved at super-step boundaries, not in the middle of a node. A node is therefore both a checkpoint and a retry boundary, and any code that can run twice must be safe to run twice.

Durable storage in production

For a demonstration, an in-memory checkpointer is enough: pause and resume work while the process lives. For production, execution state needs durable storage, so that a restart or a different server can resume the run. Keep this separate from the research artefacts, which have their own durability needs.

  • A pause is a checkpoint plus an interrupt. It needs a checkpointer, and the same thread id to resume.
  • Four decisions: approve, edit, reject, respond. Use reject, not respond, to deny.
  • A gate protects only the tool it names. Check for other routes to the same effect.
  • On resume the node restarts from its start, so anything before an interrupt must be idempotent.

2.8Reliability, observability and cost

A deep agent runs for a long time, calls external services and spends real money. Operating one means deciding in advance how it should fail, what it may spend, and how you will see what it did. These controls are separate from the agent's task logic, and most are middleware you add after the task works.

Controls interact. 2.9Review loops and structured judgement

A draft is not trustworthy because it was written confidently. The standard remedy is a second agent whose only job is to challenge the first. Wrapped in a loop with a budget, this is the evaluator–optimiser pattern, and it is the part of a deep-agent application that you have to design yourself, because the harness cannot know what a good result is.

The evaluator–optimiser pattern

One agent produces a result. A second evaluates it against criteria and returns feedback. The producer revises, and the loop repeats until the evaluator approves or a budget runs out. Anthropic recommends it when evaluation criteria are clear and iterative refinement measurably helps.

The evaluator should be a separate agent with a fresh context. A reviewer that shares the author's context inherits its assumptions and tends to approve its reasoning. Separation is what makes the review independent. In Deep Agents the evaluator is simply a subagent, which gives you that isolation for free.

Free-form feedback is hard to act on. Ask the evaluator for structured output with response_format, and the lead agent receives JSON that application code can save, count and branch on. A typical research critique carries these fields.

The schema and the checklist are your design. The harness gives you the mechanism and none of the standards.

Evidence a critic can check

A critic can only review what it can inspect. That is another reason for working in files. Give each important claim a record that names its support, so that the review is a lookup, not a guess.

  "claim": "<one factual statement from the draft>",
  "support": [{"source_id": "w-007", "url": "https://example.com/report",
               "title": "<source title>", "published": "2026-03-12", "quote": "<supporting sentence>"}],
  "confidence": "medium",
  "contradicted_by": []
}

A critic raises the quality of review. It does not guarantee factual correctness. Treat its verdict as one signal, keep every claim traceable to a source, URL and date, and validate the structure of what enters the evidence store.

Bounding the loop

A loop with no limit can run for ever, or until the budget does. Write the limit in code. A sentence in the prompt asking the agent to stop after two rounds is a request, and models do not reliably keep count.

LayerHowReliability
Prompt"At most two rounds"Guidance only
MiddlewareA tool-call limit on the follow-up toolBlocks the call deterministically, but a person may still be asked first

Decide in advance what happens when the budget is spent. A sensible default is to stop researching, finish the report, and disclose the remaining gaps in it, so that the reader knows what is not covered.

Putting a person in the loop

Further research is the expensive step, so the human gate belongs there: after the critic has found gaps and the lead agent has proposed a specific follow-up, but before it is launched. The person then has a real decision: approve the plan, edit its scope, or reject it and accept a limited report.

  • Evaluator–optimiser: produce, evaluate, revise, within a budget. The evaluator must be separate, with fresh context.
  • Ask for structured critiques so code can act on them. The schema and the acceptance bar are your design.
  • Reviews need inspectable evidence: claims linked to sources. A critic improves review quality; it does not guarantee truth.
  • Bound the loop in code, and decide what happens at the limit. Disclosing gaps is a good default.
  • Put the human gate before the expensive follow-up, with three outcomes: approve, edit, reject.

part IIIThe Model Context Protocol

Agents become useful when they can reach beyond their own code: search engines, databases, repositories, internal systems. The Model Context Protocol (MCP) is an open standard for exposing those capabilities to any agent application. This part covers what MCP is, what a server is made of, and a small working demo.

3.1What is MCP

Tools turn a model into an agent, and until recently every tool was wired in by hand, for one framework at a time. MCP is a standard way for an AI application to discover and use tools and data that live in a separate program.

Why a protocol

Without a standard, every pairing of application and service needs its own glue. With N applications and M services that is up to N × M integrations. With MCP, each application implements a client once and each service implements a server once: N + M pieces, and any client works with any server.

Without a standard: N × M

Three applications and four services means twelve custom integrations.

With MCP: N + M

Three clients and four servers is seven pieces, and every client can use every server.

Host, client and server

The host is the AI application. It creates one client for each server it connects to, and each client keeps its own connection. A server is a program that provides tools, data and prompts. "Local" and "remote" describe where a server runs, not what it is.

  • MCP replaces N × M custom integrations with N + M standard pieces.
  • A host runs one client per server. Servers are local (a subprocess) or remote (HTTP).

3.2Anatomy of an MCP server

A server is a small program that exposes up to three kinds of building block, and speaks a standard message format over a transport.

Three primitives

The primitives differ in who decides to use them, and that is the easiest way to remember them.

PrimitiveWhat it isWho controls itExample
ToolsFunctions with typed inputs that perform an actionThe model decides when to callSearch, send an email, add a note
ResourcesRead-only data identified by a URIThe application decides what to fetchA file, a schema, notes://mcp
PromptsReusable, parameterised instruction templatesThe user picks themA "summarise this note" slash command

Two layers and two transports

The protocol separates what is said from how it travels. The messages are JSON-RPC and are the same either way.

Data layerJSON-RPC messages: discovery (tools/list), invocation (tools/call), resources, prompts.
Transport layerHow the messages move. Two standard transports, below.
TransportHow it worksUse for
stdioThe host launches the server as a subprocess and talks over standard input and outputLocal servers, development, demos
Streamable HTTPThe server runs as a web service that many clients can callRemote, shared servers

One tool call, end to end

  • A server offers tools (model-controlled), resources (application-controlled) and prompts (user-controlled).
  • JSON-RPC messages travel over stdio (local subprocess) or Streamable HTTP (remote).
  • A client connects, discovers what the server offers, then calls it.

3.3Demo: a server, a client and a host

The demo is two small files: a server that exposes one tool, one resource and one prompt, and a host, a Deep Agent that connects to it and uses all three. The server uses FastMCP from the Python SDK. Install with pip install "mcp<2" langchain-mcp-adapters deepagents.

The server

Each primitive is an ordinary Python function with a decorator. The SDK builds the definition from the function: the name from the function name, the description from the docstring, and the input schema from the type hints.

# server.py
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("notes-server")

NOTES = {"mcp": "MCP standardises how apps reach tools and data.",
         "agents": "An agent is a model calling tools in a loop."}

@mcp.tool()
def add_note(topic: str, text: str) -> str:
    """Save a note under a topic. Overwrites any existing note for that topic."""
    NOTES[topic] = text
    return f"Saved note '{topic}'."

@mcp.resource("notes://{topic}")
def read_note(topic: str) -> str:
    """Return the note stored for a topic."""
    return NOTES.get(topic, "No such note.")

@mcp.prompt()
def summarise(topic: str) -> str:
    """Ask the model to summarise one note."""
    return f"Read the note on '{topic}' and summarise it in one sentence."

if __name__ == "__main__":
    mcp.run(transport="stdio")
DecoratorPrimitiveWhat the SDK derives
@mcp.tool()ToolName, description and input schema from the signature and docstring
@mcp.resource(uri)ResourceA URI template. {topic} in the URI becomes the function argument.
@mcp.prompt()PromptArguments from the signature. The returned text becomes the prompt message.

The host: a Deep Agent with MCP tools

The host is a Deep Agent. MultiServerMCPClient is the MCP client layer: it launches the server over stdio and keeps one connection per server. Tools are converted to ordinary LangChain tools and handed to the agent. Resources and prompts are not tools, so the host reads them directly from the client.

# host.py
import asyncio, sys
from langchain_mcp_adapters.client import MultiServerMCPClient
from deepagents import create_deep_agent

client = MultiServerMCPClient({
    "notes": {
        "transport": "stdio",
        "command": sys.executable,
        "args": ["server.py"],
    }
})

async def main():
    # Tools: discovered, then given to the agent
    tools = await client.get_tools()
    print("tools:", [t.name for t in tools])

    # Resource: the application decides to fetch it
    blobs = await client.get_resources("notes", uris=["notes://mcp"])
    print("resource:", blobs[0].as_string())

    # Prompt: the user picks it; the result is a list of messages
    messages = await client.get_prompt("notes", "summarise", arguments={"topic": "mcp"})
    print("prompt:", messages[0].content)

    # Put them together: the prompt is the task, the resource is its context
    agent = create_deep_agent(model="anthropic:claude-sonnet-5-5", tools=tools)
    result = await agent.ainvoke({"messages": [
        {"role": "user", "content": f"{messages[0].content}\n\nNote:\n{blobs[0].as_string()}"},
    ]})
    print(result["messages"][-1].content)

asyncio.run(main())

Run python host.py with a model API key set. The first three lines come from the server and do not need a model:

tools: ['add_note']
resource: MCP standardises how apps reach tools and data.
prompt: Read the note on 'mcp' and summarise it in one sentence.

The last line is the agent's answer and depends on the model. If the user also asked the agent to save something, it would call add_note as a normal tool.

PrimitiveClient callWho uses the result
Toolget_tools()The model, through the agent
Resourceget_resources(server, uris=[...])The host, which adds it to the context
Promptget_prompt(server, name, arguments=...)The user's choice, which becomes the task

MCP tools from this client are asynchronous only, so run the agent with ainvoke or astream.

  • FastMCP turns decorated Python functions into tools, resources and prompts.
  • MultiServerMCPClient launches the server and hands its tools to a Deep Agent as ordinary tools.
  • Resources and prompts are read directly from the client and placed in the agent's input.

Step 1: serve over HTTP

Change the last lines of server.py. Reading the transport from an environment variable keeps the same file working locally over stdio.

    # serves at http://host:8000/mcp when set to streamable-http
    mcp.run(transport=os.getenv("MCP_TRANSPORT", "stdio"))

4.1Foundations of multi-agent design

Several agents working together can do things one agent cannot, and can also fail in ways one agent cannot. Before the catalogue of patterns, this chapter sets out when multiple agents are worth their cost and what dimensions every design has to settle.

One agent or several?

The honest starting position is one agent. Multi-agent systems cost more and add moving parts. Anthropic's measurements put an agent at about four times the tokens of a chat and a multi-agent system at about fifteen times. The reason to pay is capability on the right kind of task. In its own research evaluation, a lead agent with parallel subagents outperformed a single agent by 90.2%.

A good fit

  • Open-ended, breadth-first work such as research.
  • Independent subtasks that can be explored in parallel.
  • More information than fits in one context window.
  • High-value tasks where extra cost is justified.

A poor fit

  • Tasks where every agent needs the same shared context.
  • Work with many dependencies between steps, such as most coding tasks.
  • Simple lookups one agent can answer.
  • Cheap, high-volume tasks where cost dominates.
LadderOne model call→Model plus tools→Fixed workflow→Agent with subagents→Custom multi-agent graph

Climb the ladder only when the rung below fails in a way you can name. Many applications need only a single well-prompted call, and frameworks can hide prompts and responses behind abstractions, which makes debugging harder.

Why several agents help

Three distinct mechanisms are at work, and it helps to know which one you are relying on.

MechanismWhat it givesCost
Separate context windowsMore total capacity, and each agent reasons over a small, relevant window. Token use scales with the number of windows, and in Anthropic's analysis token use alone explained most of the performance difference on a browsing benchmark.More tokens, and handoff overhead
ParallelismLower wall-clock time: independent work happens at onceCoordination; cost is not reduced
SpecialisationEach agent has focused instructions, tools and possibly a different modelMore prompts to design and maintain

Prompt chaining

A task is split into a fixed sequence of steps, each using the output of the previous one. Optional programmatic checks, called gates, can verify an intermediate result before continuing. It trades latency for accuracy by making each call an easier task.

Use when the task decomposes cleanly into fixed subtasks, for example write an outline, check it against criteria, then write the document. Watch for brittleness: the path cannot adapt to the input.

Routing

A router classifies the input and sends it to one or more specialised agents. When several agents are chosen they run in parallel, and a final step combines their answers. Routing is stateless: each request is classified afresh.

Use when inputs fall into distinct categories that are better handled separately, and can be classified accurately. A common case is sending easy questions to a cheap model and hard ones to a strong one. Watch for no multi-hop reasoning, a routing call on every request, and misclassification.

Parallelisation

Independent calls run at the same time and their outputs are aggregated. There are two variants. In sectioning, a task is split into different independent subtasks, for example one model answers the query while another screens it. In voting, the same task runs several times and the results are combined, which raises confidence, as when several prompts each review code for vulnerabilities.

Use when subtasks are independent and speed matters, or several perspectives raise confidence. The same shape is called concurrent orchestration, fan-out and fan-in, or map-reduce. Watch for cost, which is multiplied rather than reduced, and for how to resolve disagreement among voters.

Orchestrator–workers (supervisor and subagents)

A central lead agent breaks the task down, delegates subtasks to workers, and synthesises their results. It looks like parallelisation, with one difference: the subtasks are not predetermined. The lead decides at run time how many workers there are and what each does. This is the pattern Deep Agents implements, and the one Anthropic's research system uses.

Use when subtasks cannot be predicted in advance, such as research across an unknown set of sources or a code change spanning an unknown number of files, and when strong context isolation is wanted. Watch for the lead as a bottleneck, an extra model call for control, and vague briefs that cause duplicated work. Workers are usually stateless and rarely talk to the user.

Evaluator–optimiser

One agent generates and another evaluates, in a loop, until the evaluator approves or a budget runs out. It was described in chapter 2.9.

Use when criteria are clear and refinement measurably helps, such as translation refined through critique. Watch for loops with no budget, and an evaluator that shares the generator's context.

Handoffs

In the handoff pattern, agents transfer control to one another. A tool call updates a state variable, and that changes which agent is active, or which tools and prompt the same agent uses. The conversation moves with the control, and the user typically talks directly to whichever agent is active. This is also called a swarm.

A common use is a multi-stage conversation where each step has different tools and instructions. A support flow, for example, first collects the warranty status, then classifies the issue, then offers a resolution, and only the tools for the current step are available at each stage.

Use when the flow is conversational and sequential, and the user should interact directly with the specialist. It is stateful, so repeat requests are cheaper than with stateless patterns. Watch for no parallelism, because execution is sequential, and handoffs that bounce without progress.

Skills

A single agent loads specialised prompts and knowledge on demand and stays in control throughout. There are no other agents to coordinate; the specialisation is context, loaded when needed (chapter 2.5).

Use when tasks are focused and the user should interact with one agent throughout. Watch for accumulation: loaded skill context stays in the conversation, so tokens grow with each skill used, which is why this pattern can cost more than subagents on multi-domain requests.

Group chat

Several agents share one conversation thread, and a chat manager decides who speaks next. Each agent sees everything said so far. This suits debate and review: agents with different roles critique each other's contributions in the open.

Use when the value comes from agents building on or challenging each other's output. Watch for a shared context that grows quickly, conversations that wander, and the need for an explicit stopping rule.

Plan-driven orchestration

In the plan-driven (sometimes called magentic) pattern, a manager builds and maintains a task ledger: the goals, the facts known, and the plan. It assigns work to agents, records results, revises the plan when something fails and repeats. It is orchestrator–workers with an explicit, evolving plan as the central artefact.

Use when the problem is open-ended and there is no fixed plan to follow. Watch for planning overhead, and a plan that drifts from the goal if it is not checked.

Hierarchical teams

When a single lead cannot hold the whole problem, supervisors manage other supervisors. Each level delegates a part of the task and receives a summary. Hierarchy scales the number of agents, but each level adds latency and loses detail in summarisation, so keep it as shallow as the problem allows. The hierarchy topology earlier in this chapter shows the shape.

Custom workflows

When none of the above fits, you define the graph yourself, mixing deterministic steps, such as parsing, retrieval and validation, with agentic steps, where a model decides. The other patterns can be nodes inside it. This is the most flexible option, and the one where you take on the most design. It is built on a graph runtime such as LangGraph.

The graph runtime also provides the tools these workflows need: shared state with reducers, Send for run-time fan-out, Command for combined update-and-route steps, checkpoints and interrupts.

  • Fixed order: chaining. Classified input: routing. Independent work: parallelisation. Unpredictable subtasks: orchestrator–workers.
  • Refinement against criteria: evaluator–optimiser. Conversational stages: handoffs. One agent, many specialities: skills.
  • Shared thread: group chat. Evolving plan: plan-driven. Many levels: hierarchy. Anything else: a custom graph.
  • The same idea goes by different names across vendors. Compare patterns by their dimensions, not their labels.

  • Cost follows structure: stateless patterns repeat work, stateful ones save about half the calls on repeats, skills accumulate context, handoffs run in sequence.
  • Decide by asking whether steps are known, independent, and need separate context, and whether specialists talk to the user.
  • Patterns combine. Add structure only to fix a failure you have observed.

4.4Operating multi-agent systems

Building a multi-agent system is the easy half. Running one means living with failures that single agents do not have: errors that compound across steps, work that is duplicated or dropped, and costs that no single trace shows. This chapter collects the known failure modes and the operating practices that contain them.

Evaluating the system

Evaluate at the level you care about. For a multi-agent system that is the end result, not each step. Useful measures are task success against a rubric, cost per task, latency, tool error rate, and a per-agent breakdown of where tokens and failures come from. Start small, around twenty realistic cases, judge end states rather than exact paths because agents can reach a goal many ways, and keep human review in the loop for the cases an automated judge misses.

Operating practices

PracticeReason
Resume from checkpoints, not from scratchErrors in long stateful runs compound, and restarting wastes the work already done
Trace every agent and tool call, tagged by agentWithout it you cannot find which agent failed. Monitor decision patterns, not just conversations.
Roll out changes graduallyRunning agents are mid-task. Shifting traffic gradually, known as a rainbow deployment, avoids disrupting them.
Treat prompts as codeSmall prompt changes produce large behavioural changes. Test them against your cases.
Plan for asynchronous costsBackground workers add parallelism and also coordination, state-consistency and error-propagation problems

5.1A worked example: a research application

The earlier chapters each isolated one mechanism. This chapter assembles them into one application so you can see the roles fit together. The example is a research assistant: given a brief, it plans, delegates, collects evidence, reviews its own draft, asks permission before expensive follow-up, and produces a cited report. Nothing here is specific to research; the same skeleton fits any long-running, evidence-based task.

The task

A user submits a brief such as "Assess the impact of AI coding agents on software engineering jobs in a region: hiring trends, salary impact, company adoption, and credible evidence." The application should:

  1. understand the request and write a plan;
  2. split it into independent topics and delegate them;
  3. collect source metadata and detailed evidence;
  4. synthesise a draft report;
  5. have an independent reviewer challenge the draft;
  6. commission more research where gaps are found, with a person's approval;
  7. produce a final report with verifiable citations.

Architecture

One lead agent and three specialists. The lead owns planning, delegation, synthesis and the decision to continue. There is no separate planner, router or writer agent: those are the lead's jobs, and extra agents would add hops and lose context. The reviewer is separate for the reason in chapter 2.9, that it must challenge the lead independently.

Layers, not a call chain. Every agent reads and writes the workspace; the researchers call the tools.
