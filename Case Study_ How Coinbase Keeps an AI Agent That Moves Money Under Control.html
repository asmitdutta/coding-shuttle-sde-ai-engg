a case study

Who presses "send"? How Coinbase keeps an AI agent that can move money from moving the wrong money

An agent that can only talk is easy to trust. An agent that can sign a transfer is not: one bad instruction becomes a loss you cannot undo. Coinbase has been unusually honest about this, in its AgentKit toolkit, in a guardrails example, in how its engineers build agents as graphs, and in Agentic Wallets. The thread running through all of it: let the model propose, but never let it be the thing that presses send. Here is the story, and how to build a plan, validate, approve and execute agent yourself.

By Anuj Kumar Sharma about 16 minutes Module 4 · AI Agents & Orchestration
the story

story · 01Why this case study

Most "agent" case studies are about agents that retrieve or answer. This one is about an agent that acts, and the action is irreversible: an on-chain transfer can't be clawed back. That raises the stakes on a problem every agent has, and makes the design choices unusually clear.

The hard fact underneath it, stated plainly by Coinbase itself: large language models "do not reliably distinguish instructions from data".S2 If text the model reads can tell it what to do, and the agent holds a funded wallet, then text can move money. Coinbase's answer, across four sources from 2024 to 2026, is not to make the model trustworthy. It is to make sure the model is never the thing that decides.

what you will be able to do

Explain why a funded agent is a security surface, place guardrails where they actually stop a loss, design a state machine that pauses for a human on risky actions, and weigh per-transaction approval against limits set once in code.

story · 022024: give every agent a wallet

In November 2024 Coinbase launched AgentKit, a model-agnostic toolkit (OpenAI, Claude, Llama) built on its Developer Platform SDK, with LangChain support. It lets an agent deploy tokens, execute transfers and swaps, and call smart contracts.S1 The launch vision was openly autonomous: agents that "monitor and execute trades based on market conditions" and "manage smart contracts without human intervention".S1

What makes AgentKit worth studying is the risk notice in its own README. It is one of the clearest statements of the problem you will find from a vendor:

Coinbase, in the AgentKit README

A funded wallet, plus a fund-moving action (the wallet action provider is on by default), plus any surface that feeds the model text, "is sufficient for injected text to result in an onchain transfer." And: "AgentKit does not gate transfers behind human approval, enforce spend caps, or allowlist destinations."S2

Two kinds of surface feed the model text. Direct: a third party talks to the agent, through a public chatbot or API. Indirect: a tool pulls outside content into context, such as an action provider that returns social-media mentions or profile data, which the model then reads as if it were trustworthy.S2 Either one is an injection path straight to the wallet.

story · 03The fix in the example: a filter, then a human

AgentKit ships a guardrails example that shows the intended mitigations. It adds two layers around the same agent.S2

  1. A deterministic prompt-injection filter, before the model. A beforeModel hook scans each user message for known injection patterns (ignore previous instructions, "you are now…", jailbreaks). On a match it blocks the request and never calls the LLM, so the check is fast and free.S2
  2. Human approval for transfers. When the agent tries to transfer an ERC-20 token, execution pauses and a person can approve, edit the arguments, or reject. This uses LangChain's humanInTheLoopMiddleware, which needs a checkpointer to persist the paused run.S2

The shape is the key lesson. The cheap, certain check (pattern matching) runs first and deterministically. The expensive, judgment check (a human) runs only on the irreversible step. The LLM sits between them, proposing, never deciding.

story · 042025: agents are a software discipline

In December 2025 a Coinbase engineering post described how the company builds internal agents. It is not about on-chain execution, it automates institutional support, onboarding and legal review, but it states the mindset that the on-chain case needs.S3

Coinbase chose high-code graphs (LangGraph / LangChain patterns) over low-code tools for anything it wanted to run at scale. Low-code is good for prototyping, but "the more tools and instructions you load into a prompt, the more context noise you introduce", making outputs hard to reproduce and single steps hard to unit-test.S3 The result they describe is worth quoting:

Coinbase engineering, Dec 2025

"An agent graph where LLM calls are one node in a larger, testable, monitored system." Deterministic data steps are unit-tested; LLM steps are evaluated with datasets and spot-checked by a second LLM as judge; and every run writes an immutable audit record of the data used, the reasoning, and who approved the output.S3

The reported results were about speed and reuse, not accuracy: two automations in production saving more than 25 hours a week, two more built end-to-end, and the time to build a new agent cut from 12+ weeks to under a week once the shared patterns existed.S3 Their hosted LangSmith setup was then adopted across Coinbase's AI teams.S3

the one line to remember

"Agents are a software discipline." Treat the LLM as one node in a tested, observable, auditable system, and you can have speed where it helps and rigor where it matters.S3

story · 052026: move the guardrails into the wallet

Asking a human to approve every action doesn't scale to an agent that rebalances a DeFi position at 3am. So in February 2026 Coinbase launched Agentic Wallets, which take a different route: instead of a human in the loop each time, the owner sets limits once, and the infrastructure enforces them.S4

drawn by the author from S4 · the "3am rebalance, no approval needed" example is Coinbase's

The guardrails Agentic Wallets build in:S4

  • Session caps and per-transaction limits: a ceiling on each payment and on total spend per session.
  • Enclave isolation: private keys stay in secure Coinbase infrastructure and are "never exposed to the agent's prompt or LLM". Wallets are non-custodial, in Trusted Execution Environments.
  • KYT screening (Know Your Transaction): high-risk interactions are blocked automatically.

The payment rail underneath is x402, which Coinbase says is "battle-tested with over 50M transactions".S4 The design statement is explicit: autonomy "doesn't mean unlimited access".S4

story · 06The real decision: a human, or a limit?

Put the two 2026-era answers side by side and you have the design decision this whole case turns on. Both keep the model away from the signer; they differ on who says yes.

practice · 01The one rule: the model proposes, code decides

Every pattern in this case reduces to one rule: an LLM may propose an irreversible action, but a deterministic step must decide it. That gives you a checklist for any agent that can do something it can't undo. analysis

practice · 02Wiring it into your code

A small, working agent built on LangGraph, the framework in Coinbase's own examples. It parses with an LLM, then owns every irreversible decision in code: validate, pause for a human over a limit, execute once with an idempotency key, and audit. It is our implementation, not Coinbase's, and it moves no real funds: the chain and wallet are in-memory fakes, with no real keys, addresses, or network calls.

# pip install pydantic langgraph openai
import os

from openai import OpenAI

client = OpenAI()  # reads OPENAI_API_KEY from the environment


def llm(prompt: str) -> str:
    response = client.chat.completions.create(
        model=os.environ["LLM_MODEL"],  # a chat model your account can use
        messages=[{"role": "user", "content": prompt}],
        temperature=0,  # parsing and routing want repeatable output
    )
    return response.choices[0].message.content or ""

1 · The policy and a fake chain (no real money)

The owner sets limits once, like Agentic Wallets. The fake chain stands in for a wallet and network, and simulates the screening step. Notice the wallet re-enforces the limits itself at send time, so even a bug in the graph can't move funds outside the policy, a last line of defense independent of the checks above it.

import json
import re
import uuid
from collections.abc import Callable
from dataclasses import dataclass, field
from datetime import UTC, datetime
from decimal import Decimal
from enum import Enum
from typing import Literal, TypedDict

from langgraph.checkpoint.memory import MemorySaver
from langgraph.graph import END, START, StateGraph
from langgraph.types import Command, interrupt
from pydantic import BaseModel, ValidationError, field_validator

LLM = Callable[[str], str]


# ---------------------------------------------------------------- the wallet policy (owner-set, in code)
@dataclass(frozen=True)
class Policy:
    """Limits the wallet owner sets once, like Agentic Wallets' session and per-transaction caps."""

    auto_limit: Decimal  # at or below this, no human approval is needed
    per_tx_limit: Decimal  # a hard ceiling; nothing above this executes, approval or not
    session_cap: Decimal  # total that may leave the wallet this session
    allowlist: frozenset[str]  # destinations the agent may send to

# ---------------------------------------------------------------- the fake chain (no real funds)
class Denied(Exception):
    """A guardrail refused the action. It never reached the signer."""

@dataclass
class FakeChain:
    """Stands in for a wallet + network. Records sends and simulates the KYT screen.

    The wallet enforces its OWN limits at send time (like Agentic Wallets' infrastructure),
    so even a bug in the graph can't move funds outside the owner's policy. This is the last
    line of defense, independent of the app-layer checks in check_guardrails()."""

    balance: Decimal
    policy: Policy  # the wallet's own enforced limits
    flagged: frozenset[str] = frozenset()  # addresses KYT would block
    spent_session: Decimal = Decimal(0)
    sends: list[dict] = field(default_factory=list)
    _seen_keys: set[str] = field(default_factory=set)

    def screen(self, to: str) -> bool:
        return to not in self.flagged

    def send(self, to: str, amount: Decimal, idempotency_key: str) -> str:
        if idempotency_key in self._seen_keys:  # retries never double-spend
            return next(s["tx"] for s in self.sends if s["key"] == idempotency_key)
        # hard limits re-enforced at the execution boundary, after any approval
        if to not in self.policy.allowlist:
            raise Denied("destination not on the allowlist")
        if amount > self.policy.per_tx_limit:
            raise Denied("over the per-transaction limit")
        if self.spent_session + amount > self.policy.session_cap:
            raise Denied("over the session cap")
        if not self.screen(to):
            raise Denied("blocked by transaction screening")
        if amount > self.balance:
            raise Denied("insufficient balance at execution time")
        self.balance -= amount
        self.spent_session += amount
        self._seen_keys.add(idempotency_key)
        tx = "0xtx_" + idempotency_key[:16]
        self.sends.append({"to": to, "amount": amount, "key": idempotency_key, "tx": tx})
        return tx

2 · The only LLM step: propose a typed intent

The model fills a Pydantic model. Code validates it and never trusts it blindly; an invalid or malicious proposal is just data.

# ---------------------------------------------------------------- 1. parse: the ONLY LLM step
class Action(str, Enum):
    SEND = "send"
    TRADE = "trade"
    NONE = "none"

class Intent(BaseModel):
    """The structured proposal. The LLM fills this; code never trusts it blindly."""

    action: Action
    amount: Decimal = Decimal(0)
    to: str = ""
    note: str = ""

    @field_validator("amount")
    @classmethod
    def _non_negative(cls, v: Decimal) -> Decimal:
        if v < 0:
            raise ValueError("amount must be >= 0")
        return v

PARSE_PROMPT = """Turn the user's request into one action for a crypto wallet agent.
Only describe what the user asked; never invent a recipient or amount.
Return JSON: {{"action": "send|trade|none", "amount": <number>, "to": "<address or name>", "note": "<why>"}}

Request: {request}"""

def parse_intent(request: str, llm: LLM) -> Intent:
    raw = llm(PARSE_PROMPT.format(request=request))
    match = re.search(r"\{[\s\S]*\}", raw)
    if not match:
        raise ValueError(f"no JSON in LLM output: {raw[:120]!r}")
    try:
        return Intent.model_validate_json(match.group(0))
    except (ValidationError, json.JSONDecodeError) as exc:
        raise ValueError(f"bad LLM output: {exc}") from exc

3 · Validate: the guardrails live here, in plain code

# ---------------------------------------------------------------- the graph state
class ExecState(TypedDict, total=False):
    request: str
    intent: Intent
    checks: list[str]  # every guardrail decision, for the audit trail
    denied: str  # set if a guardrail refused
    approved: bool
    receipt: dict
    audit: list[dict]

def _audit(state: ExecState, event: str, **data: object) -> list[dict]:
    entry = {"ts": datetime.now(tz=UTC).isoformat(), "event": event, **data}
    return [*state.get("audit", []), entry]

# ---------------------------------------------------------------- 3. the guardrails (deterministic)
def check_guardrails(intent: Intent, chain: FakeChain, policy: Policy) -> list[str]:
    """Every rule that can refuse an action, in plain code. Injected text can't rewrite these.
    Returns the reasons to deny; an empty list means the action passed."""
    if intent.action is Action.NONE:
        return ["no actionable request"]
    reasons: list[str] = []
    if intent.amount <= 0:
        reasons.append("amount must be positive")
    if intent.to not in policy.allowlist:
        reasons.append(f"{intent.to or '(empty)'} is not on the allowlist")
    if intent.amount > policy.per_tx_limit:
        reasons.append(f"amount {intent.amount} exceeds the per-transaction limit {policy.per_tx_limit}")
    if chain.spent_session + intent.amount > policy.session_cap:
        reasons.append("would exceed the session spending cap")
    if intent.amount > chain.balance:
        reasons.append("insufficient balance")
    if not chain.screen(intent.to):
        reasons.append("destination blocked by transaction screening")
    return reasons

4 · The graph: pause for a human only over the limit

interrupt() pauses the run; a checkpointer saves the state so it can resume when a human answers, exactly as the AgentKit guardrails example does. The execute step re-runs the guardrails after approval, because the session cap or balance may have changed while the human was deciding: time-of-check is not time-of-use.

# ---------------------------------------------------------------- 4. the graph
def build_agent(llm: LLM, chain: FakeChain, policy: Policy):
    def parse(state: ExecState) -> ExecState:
        intent = parse_intent(state["request"], llm)
        return {"intent": intent, "audit": _audit(state, "parsed", action=intent.action.value)}

    def validate(state: ExecState) -> ExecState:
        reasons = check_guardrails(state["intent"], chain, policy)
        checks = reasons or ["all guardrails passed"]
        audit = _audit(state, "validated", passed=not reasons, reasons=reasons)
        if reasons:
            return {"denied": "; ".join(reasons), "checks": checks, "audit": audit}
        return {"checks": checks, "audit": audit}

    def needs_approval(state: ExecState) -> Literal["approve", "execute", "stop"]:
        if state.get("denied"):
            return "stop"
        return "approve" if state["intent"].amount > policy.auto_limit else "execute"

    def approve(state: ExecState) -> ExecState:
        intent = state["intent"]
        decision = interrupt(
            {  # pauses the run until a human answers
                "question": "Approve this transfer?",
                "action": intent.action.value,
                "amount": str(intent.amount),
                "to": intent.to,
            }
        )
        ok = isinstance(decision, dict) and decision.get("approved") is True
        audit = _audit(state, "human_decision", approved=ok, by=(decision or {}).get("by", "unknown"))
        if not ok:
            return {"denied": "rejected by human reviewer", "approved": False, "audit": audit}
        return {"approved": True, "audit": audit}

    def after_approval(state: ExecState) -> Literal["execute", "stop"]:
        return "stop" if state.get("denied") else "execute"

    def execute(state: ExecState) -> ExecState:
        intent = state["intent"]
        # re-validate at the execution boundary: the session cap or balance may have changed
        # while we waited for a human (time-of-check is not time-of-use)
        reasons = check_guardrails(intent, chain, policy)
        if reasons:
            return {"denied": "; ".join(reasons), "audit": _audit(state, "revalidated", passed=False, reasons=reasons)}
        key = uuid.uuid5(uuid.NAMESPACE_URL, f"{intent.to}|{intent.amount}|{state['request']}").hex
        try:
            tx = chain.send(intent.to, intent.amount, key)  # the wallet re-checks its own limits too
        except Denied as exc:
            return {"denied": f"wallet refused: {exc}", "audit": _audit(state, "wallet_denied", reason=str(exc))}
        receipt = {"tx": tx, "to": intent.to, "amount": str(intent.amount), "key": key}
        return {"receipt": receipt, "audit": _audit(state, "executed", tx=tx)}

    def stop(state: ExecState) -> ExecState:
        return {"audit": _audit(state, "stopped", reason=state.get("denied", "unknown"))}

    g = StateGraph(ExecState)
    for name, fn in [
        ("parse", parse),
        ("validate", validate),
        ("approve", approve),
        ("execute", execute),
        ("stop", stop),
    ]:
        g.add_node(name, fn)
    g.add_edge(START, "parse")
    g.add_edge("parse", "validate")
    g.add_conditional_edges("validate", needs_approval, {"approve": "approve", "execute": "execute", "stop": "stop"})
    g.add_conditional_edges("approve", after_approval, {"execute": "execute", "stop": "stop"})
    g.add_edge("execute", END)
    g.add_edge("stop", END)
    return g.compile(checkpointer=MemorySaver())

5 · Run it, or resume a paused run

# ---------------------------------------------------------------- a convenience runner
def run(agent, request: str, *, thread: str, decision: dict | None = None) -> ExecState:
    """Start a request, or resume a paused one by passing the human `decision`."""
    config = {"configurable": {"thread_id": thread}}
    if decision is not None:
        return agent.invoke(Command(resume=decision), config)
    return agent.invoke({"request": request, "audit": []}, config)

def is_waiting(agent, thread: str) -> bool:
    """True if the run paused at the human-approval interrupt."""
    snapshot = agent.get_state({"configurable": {"thread_id": thread}})
    return bool(snapshot.next) and "approve" in snapshot.next

practice · 03Rules of the road

Keep these in plain code, never in a prompt

  • Spend limits, the destination allowlist, and screening. Injected text can rewrite a prompt; it can't rewrite a validated rule.S2
  • An idempotency key per action, so a retry or a loop can't double-spend.
  • The hard limits re-checked at the execution boundary, after any human approval. State can change while a person decides, so a check at propose-time isn't a check at send-time.
  • An audit record for every run: inputs, checks, decision, result.S3

Let the model do only this

  • Turn a request into a structured, typed proposal, nothing more.

Watch out for

  • A funded wallet plus any text the model reads. That is the whole attack, per Coinbase.S2
  • The signing key anywhere near the model's context.S4
  • Approval fatigue: too many prompts and people stop reading them. Set a limit so routine actions don't ask.

analysis Rules without a citation are the author's engineering advice.

practice · 04When it breaks: symptoms, causes, fixes

Read a symptom, guess the cause, then open the card. analysis except where a card cites Coinbase.

Likely cause. Indirect prompt injection: external content the agent read contained instructions, and the model acted on them. Coinbase names this exact path.S2

Fix. Keep transfers behind a validated allowlist and a human or a limit. Treat all tool output as untrusted data.

Likely cause. No idempotency key, so each retry is a new transfer.

Fix. Derive a key from the action and dedupe on it, and add a session cap as a backstop.

Likely cause. The key was in the model's context, so injected text could extract it.

Fix. Keep keys in an enclave or signer the model never sees, as Agentic Wallets do.S4

Likely cause. Approval fatigue: the agent asks for approval on routine, low-value actions too.

Fix. Set an auto-limit so only risky actions ask, and reserve human review for those.

Likely cause. No checkpointer, so the interrupted run couldn't resume.

Fix. Use a persistent checkpointer; LangChain's human-in-the-loop middleware requires one.S2

Likely cause. No audit trail tying the output to its inputs and reasoning.

Fix. Write an immutable record per run: data used, checks, who approved, result.S3

practice · 05Put the graph in a safe order

These five nodes are shuffled. Order them so no irreversible step ever runs before its guard. Use the arrows, then check. example only

  1. Execute the transfer, which is irreversible
  2. Parse the request into a typed intent (LLM)
  3. Write the audit record
  4. Validate against guardrails (code)
  5. Human approves if over the limit

practice · 06Interview prep

Try answering before you open each one. documented = from Coinbase's sources, analysis = reasoning you would add.

securityWhy is a funded agent a security surface, even with a careful prompt?

documented Coinbase states that LLMs "do not reliably distinguish instructions from data", so a funded wallet plus any text-bearing surface "is sufficient for injected text to result in an onchain transfer".S2

analysis The prompt isn't the only input; tool output and retrieved content reach the model too. You can't prompt your way out of it.

designWhy put validation in code rather than asking the LLM to check the rules?

analysis A rule in code is deterministic, unit-testable, and can't be rewritten by injected text. An LLM asked to enforce a limit can be talked out of it, and you can't test it to a guarantee.

documented Coinbase separates deterministic, unit-tested data nodes from probabilistic LLM nodes for exactly this reason.S3

agentsWhat does interrupt() plus a checkpointer give you?

documented The AgentKit guardrails example pauses a transfer for human approve / edit / reject using human-in-the-loop middleware, which requires a checkpointer to persist the paused state.S2

analysis The checkpointer lets the run survive the wait, even across a process restart, and resume exactly where it paused.

tradeoffHuman approval or wallet limits, which should an agent use?

documented Coinbase shows both: human approval in the AgentKit example (S2), and limits in infrastructure in Agentic Wallets (session caps, per-transaction limits, screening) so agents act autonomously inside them (S4).

analysis Humans for rare, high-value, irreversible actions; limits for frequent, bounded ones. Most real systems use both.

securityWhy should the signing key never be in the model's context?

documented Agentic Wallets keep private keys in an enclave, "never exposed to the agent's prompt or LLM".S4

analysis If it isn't in context, injected text can't exfiltrate it, and a model mistake can't sign with it directly; the model can only request a signature through a gated path.

reliabilityHow do you stop a retry or a loop from double-spending?

analysis Give each intended action an idempotency key derived from its content, and dedupe on it at the signer, so a repeat is a no-op. Add a session cap as a backstop against a runaway loop.

processWhy does a money-moving agent need an audit trail?

documented Coinbase writes an immutable record per run, showing which data was used, the reasoning, and who approved, which it calls essential for legal and regulatory flows.S3

analysis It's also how you debug a bad payment after the fact, when the chain state can't be undone.

wrap-upConclusion: let it propose, never let it press send

Coinbase's agent work, from AgentKit's blunt risk notice to the graph discipline of 2025 to Agentic Wallets' limits, keeps arriving at the same place. The language model is powerful and untrustworthy at once, so you let it read and propose, and you put every irreversible decision, every limit, and the signing key itself behind deterministic code it cannot reach.

Four things to carry away

  • A funded agent plus any text it reads is an attack surface; you can't prompt your way out.
  • The model proposes; code validates, approves, executes, and audits.
  • Choose per-action human approval for rare high-value actions, wallet limits for frequent bounded ones.
  • Keep spend limits, the allowlist, idempotency, and the key in code, never in the prompt.
