RAG with LangChain

Build a RAG help desk for Zomato: turn its policy PDFs, wiki pages and FAQs into a question-answering system, one LangChain component at a time.

Zomato help deskLangChainQdrantOpenRouter

part oneWhat LangChain is, and what it is not

The big picture

RAG works in two steps: prepare your documents once, then retrieve the right pieces for every question and hand them to an LLM. This guide builds that system for real, for Zomato, the online food ordering platform. We will give Zomato's internal help desk an assistant that answers from the company's own knowledge, which is scattered across policy PDFs, scanned contracts, Markdown wiki pages and spreadsheets. We use LangChain for the plumbing and Qdrant as the vector database.

Start with the whole picture. Every source file is parsed, cut into chunks, turned into vectors and stored. Questions later search those vectors by similarity.

Now give each stage its LangChain name. Each of these components is covered below, in this order.

IndexingDocument loader→Text splitter→Embeddings→QdrantVectorStore
QueryingRetriever→Prompt template→Chat model→Output parser→Answer
Keep one rule in mind all the way through: a bad answer is almost always a retrieval problem, not a model problem. LangChain makes every stage visible, so you can inspect each one.

What is LangChain?

LangChain is an open-source framework that gives every part of an LLM application a standard interface. A PDF parser, an embedding API, a vector database and a chat model all come from different vendors with different SDKs. LangChain wraps each one in the same few shapes, so you can connect them like building blocks and swap any block without rewriting the rest. Read the diagram in two layers: the top row is what your code works with, and the stacks underneath are the providers that do the real work.

# the pipeline code stays the same ...
chunks = splitter.split_documents(docs)
store = QdrantVectorStore.from_documents(chunks, embeddings, url=URL)

# ... only the provider line changes
embeddings = OpenAIEmbeddings(model="text-embedding-3-small")           # hosted API
embeddings = HuggingFaceEmbeddings(model_name="all-MiniLM-L6-v2")       # local model, no API key

What it gives you

  • One interface per job, many providers behind it
  • Ready-made loaders, splitters and vector-store wrappers
  • A way to compose steps into a pipeline with |
  • Streaming, batching and tracing for free

What it is not

  • It is not RAG. RAG is the design, LangChain is a toolbox.
  • It is not a database. Qdrant stores the vectors.
  • It is not a model. OpenAI and OpenRouter do the AI.
LangChain is the orchestration layer. Qdrant stores, OpenAI embeds, OpenRouter generates.Once you see these four roles clearly, every line of code below has an obvious home.

The components map

Eight components cover almost everything a RAG application needs. The top row prepares your knowledge once. The bottom row runs for every question, reading from the same vector store.

ComponentJobExample

Text splitterCut Documents into retrievable chunksRecursiveCharacterTextSplitter, MarkdownHeaderTextSplitter
Embedding modelTurn text into vectorsOpenAIEmbeddings

RetrieverA simple "query in, Documents out" interfacevector_store.as_retriever()

The glue between them is the Runnable interface. Every component above can be called with .invoke(), and any two can be chained with the pipe operator |. That is called LCEL, the LangChain Expression Language, and it comes into play when we assemble the full chain.

How the packages fit together

LangChain is split into small packages so that you install only what you use. The mental model is a hub and spokes: langchain-core defines the shared interfaces, and every other package plugs into it.

This is why imports come from different places. Document and prompts live in langchain_core. Loaders live in langchain_community. A provider such as OpenAI or Qdrant ships its own small package. When an import fails, the fix is almost always "install the matching package".

part twoFrom files to Documents

The Document object

Before loading anything, meet the one object that travels through the entire pipeline. A LangChain Document is just two fields: the text, and a dictionary describing where the text came from.

from langchain_core.documents import Document

doc = Document(
    page_content=(
        "Full-time employees receive 24 days of paid annual leave per calendar year. "
        "Up to 5 unused days may be carried over into the next year."
    ),
    metadata={"filename": "employee_handbook.pdf", "page": 1, "area": "policies"},
)

print(doc.page_content)
print(doc.metadata)

Why bother with metadata? Because the vector store needs more than text. Metadata powers source citations ("see page 2 of the handbook"), filtering (search only the policies), tenant isolation, access control and debugging. Every later step, loading, splitting and storing, carries it along automatically.

Document loaders

A loader's only job is to read an external source and return a list of Document objects. The source can be a PDF, a text file, a CSV, a web page or a database. The shape of the output is always the same. What differs between loaders is how well they read a particular kind of file, and that is where your choice matters.

The next few sections walk through the main families, then compare the options that overlap, and finish with a decision guide. Browse the full loader catalogue when you meet a format not covered here. There are hundreds, and most live in langchain-community.

Loading text and Markdown

The simplest case is a plain file. TextLoader reads the whole file into one Document and records the path as source.

from langchain_community.document_loaders import TextLoader

notes = TextLoader("knowledge/wiki/onboarding.md", encoding="utf-8").load()

print(len(notes))                  # 1 file, so 1 Document
print(notes[0].metadata)           # {'source': 'knowledge/wiki/onboarding.md'}
print(notes[0].page_content[:200])
Always pass encoding="utf-8". On Windows the default encoding can corrupt accented characters and symbols.

For Markdown there is a second option, and the difference is worth knowing:

LoaderWhat you getChoose it when
TextLoaderThe raw text, # headings included, as one DocumentYou will split on those headings yourself (recommended, see the splitting part)
UnstructuredMarkdownLoaderCleaned text. In mode="elements" it returns titles, paragraphs and lists as separate DocumentsYou want element-level structure and accept the heavier unstructured dependency

For most Markdown, TextLoader plus a header-aware splitter is lighter, faster and keeps your headings exactly as written.

Loading a PDF

PDFs are what most real knowledge bases look like: handbooks, policies, contracts, manuals. A PDF loader returns one Document per page and fills metadata with the page number and whatever the file declares about itself. We start with PyPDFLoader, the most common entry point.

from langchain_community.document_loaders import PyPDFLoader

pages = PyPDFLoader("knowledge/policies/employee_handbook.pdf").load()

print(f"Pages loaded: {len(pages)}")
print(pages[1].page_content[:240])
print(pages[1].metadata)

PDF loaders compared

LangChain ships several loaders for the same job, because PDFs are the messiest format in business. They differ in speed, in how faithfully they preserve reading order, and in what extra they give you. Three cover almost every text-based PDF you will meet:

LoaderInstallStrengthsWeaknesses
PyPDFLoaderpypdfPure Python, trivial to install, page labels in metadataCan scramble columns and tables. Mid-range speed.
PyMuPDFLoaderpymupdfVery fast, good reading order, rich metadataNative dependency. Check the licence (AGPL) for commercial use.
PDFPlumberLoaderpdfplumberPrecise character positions, helpful when you later extract tables with the pdfplumber APISlower than the others

Do not pick by reputation. Run each candidate on your own hardest PDF and read the result. This small harness takes a minute and often settles the argument:

import time
from langchain_community.document_loaders import PDFPlumberLoader, PyMuPDFLoader, PyPDFLoader

path = "knowledge/policies/expense_policy.pdf"      # a PDF that contains a table
candidates = {"pypdf": PyPDFLoader, "pymupdf": PyMuPDFLoader, "pdfplumber": PDFPlumberLoader}

for name, loader_cls in candidates.items():
    started = time.perf_counter()
    pages = loader_cls(path).load()
    seconds = time.perf_counter() - started
    chars = sum(len(p.page_content) for p in pages)
    print(f"{name:>10}: {len(pages)} pages, {chars:,} characters, {seconds:.2f}s")
    print("            sample:", pages[2].page_content[:90].replace("\n", " | "))
What to look for in the sample: are table rows still readable, or did the amounts drift away from their labels? Is the left column read before the right column? Choose the loader whose output you would be happy to hand to an LLM.
Rule of thumb. Start with PyMuPDFLoader for speed and quality, fall back to PyPDFLoader when you need zero native dependencies, and try PDFPlumberLoader when tables matter. Scanned files need OCR, which the next section covers.

Scanned PDFs need OCR

Open a PDF and try to select a sentence with your mouse. If you cannot, the pages are pictures of text. A scanned contract is the classic example. Every loader above would return empty or garbage pages, because there is no text layer to read. You need OCR, optical character recognition, which looks at the pixels and guesses the letters.

Scanned PDF (images)→OCR engine→Recognised text→Document objects

How OCR works technically

When you set strategy="ocr_only", the unstructured library ignores text layers and treats pages as images. It orchestrates three steps:

  • Rendering: poppler or pdf2image converts PDF pages into image buffers.
  • Recognition: The Tesseract OCR engine (maintained by Google) scans pixels to identify characters and bounding boxes.
  • Partitioning: The library uses those boxes to group text into elements like Titles, NarrativeText, or Tables.

Note: System tools (tesseract and poppler) must be preinstalled on your OS for this to work.

pip install "unstructured[pdf]"
# OCR also needs system tools: tesseract and poppler (for example: brew install tesseract poppler)
from langchain_community.document_loaders import UnstructuredPDFLoader

scan = UnstructuredPDFLoader(
    "knowledge/scans/vendor_contract.pdf",
    mode="elements",            # titles, paragraphs and tables as separate Documents
    strategy="ocr_only",        # force OCR instead of reading a text layer
).load()

print(len(scan), "elements")
print(scan[0].metadata.get("category"), "|", scan[0].page_content[:80])
OCR is slower and makes mistakes (an "O" read as a zero, a missing comma). For contracts and financial documents, always spot-check the recognised text, and keep the original file as the source of truth for any legal question.

When PDFs are truly hard, with merged table cells, multi-column layouts or handwriting, teams often move to a managed parser such as LlamaParse, Azure Document Intelligence or Amazon Textract. They cost money but handle layouts that open-source tools cannot.

JSON: choose what becomes text

JSON has no natural text, so you tell the loader what to extract using a jq expression. Think of jq as a query language for JSON: you describe a path through the document and the loader turns each thing that path lands on into one Document.

A few rules cover almost every case you will need:

ExpressionWhat it does
.The whole document as one Document.
.productFollows one key. .billing.cycle walks into nested objects.
.plansThe whole array as a single Document.
.plans[]Every item in the array becomes its own Document. This is the one you want most of the time.
.plans[] | .namePipes the result onward, so each Document keeps only the name value.
.plans[] | {name, sso}Builds a smaller object per item, keeping just the fields you choose.

Compare each result below on the same file. text_content=False keeps the extracted JSON as text; leave it out to flatten the values into a plain string instead.

# pip install jq
from langchain_community.document_loaders import JSONLoader

# ".plans[]" -> one Document per plan (3 plans = 3 Documents)
plans = JSONLoader(
    file_path="knowledge/catalog/plans.json",
    jq_schema=".plans[]",
    text_content=False,          # keep each plan as JSON text
).load()

print(len(plans), "documents")   # 3
print(plans[0].page_content)     # the Starter plan, as JSON

# ".plans[] | {name, sso}" -> each Document keeps only those two fields
compact = JSONLoader(
    file_path="knowledge/catalog/plans.json",
    jq_schema=".plans[] | {name, sso}",
    text_content=False,
).load()

# ".billing" -> a single Document holding just the billing block
billing = JSONLoader(
    file_path="knowledge/catalog/plans.json",
    jq_schema=".billing",
    text_content=False,
).load()

# metadata_func: lift a field into metadata so you can filter on it later
def plan_meta(record: dict, metadata: dict) -> dict:
    metadata["plan"] = record.get("name")
    return metadata

per_plan = JSONLoader(
    file_path="knowledge/catalog/plans.json",
    jq_schema=".plans[]",
    text_content=False,
    metadata_func=plan_meta,
).load()
print(per_plan[1].metadata["plan"])   # Business
Keep one thing in mind while writing a jq path. A trailing [] explodes an array into many Documents; a named key keeps things together. When your loader returns "too few" or "too many" Documents, the fix is almost always the shape of that path.
A missing path does not raise an error, it silently yields nothing. If your JSON loader returns zero Documents, print the file and check the exact key names before assuming the loader is broken.

Loading a whole folder

Real projects have many files, not one. LangChain offers DirectoryLoader for the quick version: it scans a folder and applies one loader class to every file matching a pattern.

from langchain_community.document_loaders import DirectoryLoader, PyMuPDFLoader

loader = DirectoryLoader(
    "knowledge/policies",
    glob="**/*.pdf",
    loader_cls=PyMuPDFLoader,
    show_progress=True,
)
docs = loader.load()

That works until your folder mixes formats, and ours does. One loader class cannot read PDFs, CSVs and Markdown at once. A common design is a small registry: a dictionary from file extension to the loader that should read it. It stays readable, it is easy to extend, and one corrupt file cannot crash the whole run.

Walk the folder→Look up the loader by extension→Load→Tag area, filename, doc_type→Collect Documents
kb/loaders.py 
"""Turn the files in the knowledge folder into LangChain Documents."""
from pathlib import Path

from langchain_community.document_loaders import (
    CSVLoader, PyMuPDFLoader, TextLoader, UnstructuredPDFLoader,
)
from langchain_core.documents import Document

SCAN_FOLDERS = {"scans"}      # PDFs kept here are images, so they need OCR


def _pdf(path: Path):
    if path.parent.name in SCAN_FOLDERS:
        return UnstructuredPDFLoader(str(path), mode="elements", strategy="ocr_only")
    return PyMuPDFLoader(str(path))


LOADER_FOR = {
    ".pdf": _pdf,
    ".md": lambda p: TextLoader(str(p), encoding="utf-8"),
    ".txt": lambda p: TextLoader(str(p), encoding="utf-8"),
    ".csv": lambda p: CSVLoader(str(p), encoding="utf-8", metadata_columns=["product", "category"]),
}


def load_file(path: Path) -> list[Document]:
    docs = LOADER_FOR[path.suffix.lower()](path).load()
    for doc in docs:
        doc.metadata.update(
            filename=path.name,
            area=path.parent.name,                 # policies, wiki, faq, scans ...
            doc_type=path.suffix.lstrip(".").lower(),
        )
    return docs


def load_corpus(root: Path) -> list[Document]:
    docs, failed = [], []
    for path in sorted(root.rglob("*")):
        if path.suffix.lower() not in LOADER_FOR:
            continue
        try:
            docs.extend(load_file(path))
        except Exception as exc:                   # keep going, report at the end
            failed.append(f"{path.name}: {exc}")
    print(f"Loaded {len(docs)} documents from {root}")
    for line in failed:
        print("  skipped", line)
    return docs
from settings import KNOWLEDGE_DIR
from kb.loaders import load_corpus

docs = load_corpus(KNOWLEDGE_DIR)
Loaded 97 documents from knowledge
  skipped vendor_contract.pdf: tesseract is not installed

The output above is an example. The point of the design is that the skipped file is reported, not silently ignored and not fatal. Install the missing tool and run again.

part threeFrom Documents to chunks

Splitting into chunks

A page is still too big and too mixed. A handbook page about annual leave may also contain the first half of the sick-leave rules. We split documents into chunks small enough to be about one thing, because a retrieved chunk is exactly what the LLM will read. LangChain's most common splitter is RecursiveCharacterTextSplitter: it tries paragraph breaks first, then line breaks, then spaces, so chunks tend to end at natural boundaries.

from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=900,         # maximum characters per chunk
    chunk_overlap=120,      # characters shared between neighbouring chunks
    add_start_index=True,   # remembers where in the page each chunk began
)

chunks = splitter.split_documents(docs)

print(f"Split {len(docs)} documents into {len(chunks)} chunks")
print(chunks[0].page_content[:200])
print(chunks[0].metadata)

Use split_documents(), not split_text(). The first keeps the Document abstraction, so every chunk inherits its page's metadata automatically. With split_text() you get bare strings and lose the source, and then you cannot cite or filter.

The overlap repeats the end of one chunk at the start of the next, so an idea that straddles a boundary survives. With size 5 and overlap 1:

Splitters compared

The recursive splitter is a great default, but it is one of several. The splitters below solve different problems. The main differences are what they cut on and how they measure size.

SplitterCuts onSize measured inBest for
CharacterTextSplitterOne separator you choose, such as a blank lineCharactersText with one reliable delimiter, like log lines or numbered rules
RecursiveCharacterTextSplitterParagraph, then line, then space, as neededCharactersGeneral prose. The safest default.
Token-based (from_tiktoken_encoder, TokenTextSplitter)Token boundariesTokensWhen chunks must fit a model's token limit exactly
MarkdownHeaderTextSplitterMarkdown headingsSectionsWikis, docs and runbooks written in Markdown
HTMLHeaderTextSplitterHTML heading tagsSectionsWeb pages and exported help centres
RecursiveCharacterTextSplitter.from_language()Classes, functions and blocks of a languageCharactersSource code
RecursiveJsonSplitterJSON structureSerialised sizeLarge JSON documents
SemanticChunkerPoints where the meaning shiftsSentencesLong text with shifting topics and no clear structure

Let us see them work, starting with the three general-purpose ones on the same text.

from langchain_text_splitters import CharacterTextSplitter, RecursiveCharacterTextSplitter

text = open("knowledge/wiki/onboarding.md", encoding="utf-8").read()

# 1. cuts only at blank lines, then merges paragraphs up to the size limit
by_char = CharacterTextSplitter(separator="\n\n", chunk_size=500, chunk_overlap=50)

# 2. tries blank lines, then newlines, then spaces, so oversized paragraphs still get split
by_recursive = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)

# 3. sizes in tokens, matching what the embedding model actually counts
by_tokens = RecursiveCharacterTextSplitter.from_tiktoken_encoder(
    encoding_name="cl100k_base", chunk_size=120, chunk_overlap=15
)

for name, splitter in [("character", by_char), ("recursive", by_recursive), ("tokens", by_tokens)]:
    pieces = splitter.split_text(text)
    longest = max(len(p) for p in pieces)
    print(f"{name:>10}: {len(pieces):>3} chunks, longest = {longest} characters")
CharacterTextSplitter only cuts at its one separator. If a single paragraph is longer than chunk_size, it keeps that paragraph whole and the chunk silently exceeds your limit. That is the main reason the recursive splitter is the safer default.

What is a token?

A token is the small piece of text a language model actually reads. It can be a whole word, part of a word, a single character, a punctuation mark, or a space glued to the front of a word. A tokenizer cuts your text into pieces taken from a fixed vocabulary of tens of thousands of entries, and every piece has an integer ID. The model never sees letters. It sees a list of numbers.

Why do different encodings give different tokens?

Each encoding learned its own vocabulary from its own training text. The older r50k_base has about 50,000 entries, cl100k_base about 100,000 and o200k_base about 200,000. Look at what changed above: the same word, "unbelievably", is one token in two encodings and two tokens in the middle one, and the older encoding keeps " 24" as one piece while the newer ones split the space from the digits. A rare brand name like "Zomato" is cut into three pieces by all of them, because none of the vocabularies holds it as a whole. As a rough guide, one token is about four characters, or three quarters of an English word.

Why use tokens at all?

  • No unknown words. Any text, including new names, typos and code, can be assembled from known pieces, so the model never hits a word it cannot represent.
  • A sensible middle ground. Single characters would make every text very long and slow to process. Whole words would need a vocabulary of millions. Pieces of words keep common words short and rare words possible.
  • Numbers a model can use. Each token ID selects a learned vector from the embedding table, and that is where all the model's maths starts.

How LLMs use tokens

An LLM reads your prompt as a list of token IDs and predicts the single most suitable next token. It appends that token, predicts the next one, and repeats until the answer is complete, so a reply is a stream of tokens converted back into text. Because everything is counted in tokens, so are the limits and the bill: the context window (how much the model can read at once), the maximum reply length, the price per request, and the input limit of an embedding model.

Why this matters for RAG

The retrieved chunks, your prompt and the answer all have to fit in one token budget. The same text can cost a different number of tokens on different models, and non-English text, numbers and code often cost more than you would guess. When a limit matters, count with the tokenizer that belongs to your model instead of estimating from characters.

import tiktoken            # pip install tiktoken

enc = tiktoken.get_encoding("cl100k_base")      # the encoding used by text-embedding-3-small
ids = enc.encode("Zomato delivers unbelievably fast.")

print(ids)                                  # [57, 316, 4428, 28421, 40037, 89234, 5043, 13]
print([enc.decode([i]) for i in ids])       # ['Z', 'om', 'ato', ' delivers', ' unbelie', 'vably', ' fast', '.']
print(len(ids), "tokens")                   # 8 tokens

That is why the token-based splitter earlier exists: when you need a hard guarantee such as "never more than 300 tokens per chunk", size the chunks in tokens, not characters.

Header-aware splitting for Markdown and HTML

Structured documents already tell you where the topics change. A heading like "Restarting the payments service" is a far better boundary than "after 900 characters". MarkdownHeaderTextSplitter cuts at headings and, as a bonus, stores the heading path in metadata, so a chunk knows which section it belongs to.

from langchain_text_splitters import MarkdownHeaderTextSplitter, RecursiveCharacterTextSplitter

    headers_to_split_on=[("#", "h1"), ("##", "h2"), ("###", "h3")],
)

markdown = open("knowledge/wiki/onboarding.md", encoding="utf-8").read()

The best pattern is two stages: split on headings first, then run the recursive splitter on any section that is still too long. You get meaningful boundaries and a size cap.

from langchain_text_splitters import HTMLHeaderTextSplitter

Header metadata is gold for retrieval and for citations. You can show "Onboarding > Accounts and access > VPN setup" next to an answer, and you can filter for h2 == "Accounts and access" later.

Splitting code and JSON

Prose rules do badly on code. A function cut in half is useless. LangChain's recursive splitter can be told which language it is reading, and then it prefers to cut between classes and functions.

from langchain_text_splitters import Language, RecursiveCharacterTextSplitter

source = open("knowledge/wiki/retry_helper.py", encoding="utf-8").read()

code_splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.PYTHON,
    chunk_size=600,
    chunk_overlap=60,
)
code_chunks = code_splitter.create_documents([source])
print(len(code_chunks), "chunks, each ending near a function boundary")

Many languages are supported (Python, JavaScript, Java, Go, Markdown and more). JSON has its own splitter that keeps objects intact and only splits where a nested structure allows it.

import json
from langchain_text_splitters import RecursiveJsonSplitter

data = json.load(open("knowledge/catalog/plans.json", encoding="utf-8"))

json_splitter = RecursiveJsonSplitter(max_chunk_size=400)
json_docs = json_splitter.create_documents(texts=[data])
print(len(json_docs), "JSON chunks")
Match the splitter to the structure of the file. A code splitter on a handbook, or a prose splitter on source code, works but throws away the clues the file was giving you.

Semantic chunking

Every splitter so far cuts by position or structure. Semantic chunking cuts by meaning. It embeds each sentence, measures how similar neighbouring sentences are, and starts a new chunk where the similarity suddenly drops, which is where the topic changes.

Split into sentences→Embed each sentence→Compare neighbours→Cut where similarity drops→Chunks
pip install langchain-experimental
from langchain_experimental.text_splitter import SemanticChunker
from langchain_openai import OpenAIEmbeddings

semantic = SemanticChunker(
    OpenAIEmbeddings(model="text-embedding-3-small"),
    breakpoint_threshold_type="percentile",     # cut at the biggest drops in similarity
)

chunks = semantic.split_documents(docs[:5])
print(len(chunks), "semantic chunks")

Pros

  • Chunks follow topics, not character counts
  • Works on text with no headings

Cons

  • Costs an embedding call for every sentence
  • Chunk sizes are unpredictable
  • Lives in the experimental package
  • Often no better than headings plus recursive splitting

Treat it as an experiment to run when structure-based splitting gives poor answers, not as the default.

One chunking module for every document type

Our folder has several kinds of content, and each deserves its own treatment. Instead of one splitter for everything, route each document to the right one by its type. This is the pattern real projects settle on.

Document→Look at doc_type→Markdown: headers + recursive; PDF: recursive; CSV: keep rows→Chunks
kb/chunkers.py 
"""Turn Documents into chunks, using the splitter that suits each document type."""
from langchain_core.documents import Document
from langchain_text_splitters import MarkdownHeaderTextSplitter, RecursiveCharacterTextSplitter

_by_size = RecursiveCharacterTextSplitter(chunk_size=900, chunk_overlap=120, add_start_index=True)
_by_header = MarkdownHeaderTextSplitter(headers_to_split_on=[("#", "h1"), ("##", "h2"), ("###", "h3")])


def _split_markdown(doc: Document) -> list[Document]:
    sections = _by_header.split_text(doc.page_content)
    for section in sections:
        section.metadata = {**doc.metadata, **section.metadata}   # keep file info, add headings
    return _by_size.split_documents(sections)


def chunk_corpus(docs: list[Document]) -> list[Document]:
    chunks: list[Document] = []
    for doc in docs:
        kind = doc.metadata["doc_type"]
        if kind == "md":
            chunks.extend(_split_markdown(doc))
        elif kind == "csv":
            chunks.append(doc)                       # a row is already one answer
        else:
            chunks.extend(_by_size.split_documents([doc]))
    print(f"{len(docs)} documents became {len(chunks)} chunks")
    return chunks

Metadata and stable chunk IDs

Last stop before storing. Everything you attach now becomes searchable later. Two additions pay off immediately in real projects: a tenant or owner, so you can isolate customers, and a stable chunk ID, so re-running ingestion never creates duplicates.

The simplest stable ID is a hash of the chunk's own text plus its file name. The same text in the same file always yields the same ID, so storing it twice just overwrites it.

import hashlib
import uuid


def chunk_id(chunk) -> str:
    digest = hashlib.sha1(chunk.page_content.encode("utf-8")).hexdigest()
    return str(uuid.uuid5(uuid.NAMESPACE_URL, f"{chunk.metadata['filename']}|{digest}"))


for chunk in chunks:
    chunk.metadata["tenant_id"] = "zomato"

ids = [chunk_id(c) for c in chunks]
print(len(ids), len(set(ids)))       # equal, unless two chunks in one file are identical

uuid5 is a deterministic hash, so the same input always produces the same ID. That single property prevents a very common bug, as the re-ingestion section below shows.

part fourVectors and the vector store

Embeddings in LangChain

LangChain gives every embedding provider the same two methods. One embeds many texts at once for indexing. The other embeds a single question for searching. Because both come from the same object, the query and the documents always live in the same vector space.

from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")

texts = [
    "Full-time employees receive 24 days of paid annual leave.",
    "Client meals are reimbursed up to the per-person limit with a receipt.",
    "Restart the payments service from the runbook, never from the console.",
]

vectors = embeddings.embed_documents(texts)
print("Number of vectors:", len(vectors))        # 3, one per text
print("Vector dimension:", len(vectors[0]))      # 1536 for this model
print("First 5 values:", vectors[0][:5])

query_vector = embeddings.embed_query("How many vacation days do I get?")
print("Query vector dimension:", len(query_vector))

Notice the question says "vacation days" while the handbook says "paid annual leave". Embeddings match meaning, not exact words, and that is what makes semantic search feel smart.

Do not hard-code the dimension. Read it from a real vector, as above, whenever you create a collection. If you later switch embedding models the dimension changes, and Qdrant will reject mismatching vectors.

Similarity search

Before building the full chain, test the vector store by itself. Search is the heart of RAG, and it is easy to check by eye.

The first two hits are the leave policy. The third is an onboarding page that only mentions time off in passing. Scores here are illustrative. Your numbers will differ.

From vector store to retriever

A retriever is a thinner interface with a single job: query in, Documents out. The vector store knows about storage and search. The retriever hides all of that behind one method, which is why the rest of your chain does not change if you later swap in a smarter retrieval strategy.

retriever = vector_store.as_retriever(
    search_type="similarity",
    search_kwargs={"k": 4},
)

docs = retriever.invoke("What is the process for reimbursing a client dinner?")

for doc in docs:
    print(doc.metadata["filename"], doc.metadata.get("page"))

Filtering with metadata

Similarity alone is not enough in a real product. Maybe a user wants answers from the policies only, not the wiki. Or, in a multi-customer system, one tenant must never see another's documents. Qdrant lets you combine similarity with a filter on the metadata you stored. This is where the area and tenant_id fields you added earlier pay off.

from qdrant_client import models

only_policies = models.Filter(
    must=[
        models.FieldCondition(
            key="metadata.area",                      # LangChain stores metadata under "metadata"
            match=models.MatchValue(value="policies"),
        )
    ]
)

results = vector_store.similarity_search(
    "Can I expense a client dinner?",
    k=4,
    filter=only_policies,
)

for doc in results:
    print(doc.metadata["filename"], doc.metadata.get("page"))

You can also bake the filter into a retriever so the rest of the chain never has to think about it:

retriever = vector_store.as_retriever(search_kwargs={"k": 4, "filter": only_policies})
Index the fields you filter on, for example metadata.tenant_id, with client.create_payload_index(...) so filtered search stays fast on large collections.
A filter is your security boundary. Enforce it in code, from the signed-in user's identity. Never ask the LLM to "only use documents from this tenant".

The chat model

Retrieval is done. Now the generation side. In LangChain a chat model takes a list of messages and returns one message back. Messages have roles: a system message sets the rules, a human message carries the question, and the model answers with an AI message.

We use OpenRouter, a single API that reaches many models. LangChain has a dedicated integration, so prefer it over pointing ChatOpenAI at a custom URL.

from langchain_openrouter import ChatOpenRouter

llm = ChatOpenRouter(
    model="openai/gpt-4.1-mini",     # any model id from openrouter.ai/models
    temperature=0,                   # 0 keeps answers focused and repeatable
)

response = llm.invoke([
    ("system", "You are a concise assistant."),
    ("human", "Explain RAG in one sentence."),
])

print(response.content)
Because the model is behind an interface, switching is a one-line change. ChatGroq(model="llama-3.3-70b-versatile") from langchain_groq, or another OpenRouter model id, drops into the same chain without touching retrieval.

The RAG prompt

The model must receive two things: the retrieved context and the user's question. A ChatPromptTemplate is a reusable message list with named blanks to fill in.

from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    (
        "system",
        """You are Zomato's internal help-desk assistant.
Answer using only the context below.

Rules:
- If the answer is not in the context, say you don't know.
- Cite the sources you used as [1], [2], matching the numbers in the context.
- Never invent policies, amounts or procedures.

Context:
{context}""",
    ),
    ("human", "{question}"),
])

Those rules do real work. "Use only the context" and "say you don't know" are what turn an LLM from a confident guesser into a grounded assistant. Treat the prompt as code: version it, review it and test it.

Output parsers

A chat model does not return a plain string. It returns a message object, an AIMessage, which carries the text in .content together with metadata such as token usage. That is fine for a quick test, but real code usually wants something simpler or more structured: a clean string to show a user, a list of keywords, or a dictionary to branch on. An output parser is the last link in a chain that converts the model's message into exactly that.

ParserReturnsUse it for
StrOutputParserA plain stringThe final answer in a RAG chain. This is the one you will use most.
CommaSeparatedListOutputParserA Python list of stringsKeywords, tags, alternative search phrases
JsonOutputParserA dictionaryQuick structured replies where you do not need strict checking
PydanticOutputParserA validated Python object with typed fieldsAnything your code depends on: routing, extraction, query planning. The most important one for real applications.

StrOutputParser: just the text

Without a parser you must remember to dig the text out of the message every time. With one, the chain ends in a string.

from langchain_core.output_parsers import StrOutputParser

message = llm.invoke("Name one benefit of RAG in five words.")
print(type(message).__name__)         # AIMessage
print(message.content)                # the text, plus metadata we did not ask for

chain = llm | StrOutputParser()
answer = chain.invoke("Name one benefit of RAG in five words.")
print(type(answer).__name__)          # str
print(answer)

CommaSeparatedListOutputParser: a real Python list

Many parsers can also tell the model how to format its reply. You paste that into the prompt with get_format_instructions(), so the prompt and the parser always agree. Here the model suggests search keywords for a question, and we get back a list we can loop over.

from langchain_core.output_parsers import CommaSeparatedListOutputParser
from langchain_core.prompts import ChatPromptTemplate

list_parser = CommaSeparatedListOutputParser()

keyword_prompt = ChatPromptTemplate.from_template(
    "Give 3 short search keywords for this question.\n{format_instructions}\nQuestion: {question}"
).partial(format_instructions=list_parser.get_format_instructions())

keyword_chain = keyword_prompt | llm | list_parser

print(keyword_chain.invoke("How many days of paid leave do I get?"))
['paid leave', 'annual leave days', 'leave policy']

JsonOutputParser: a dictionary you can branch on

When your code needs to make a decision, ask for JSON. A common use in RAG is routing: let the model pick which part of the knowledge base a question belongs to, then search only there. This is the quick version. The next parser makes it safer.

from langchain_core.output_parsers import JsonOutputParser

json_parser = JsonOutputParser()

route_prompt = ChatPromptTemplate.from_template(
    "Decide which area of the Zomato knowledge base best answers the question. "
    'Reply with JSON containing "area" (policies, wiki, faq or catalog) and a short "reason".\n'
    "{format_instructions}\nQuestion: {question}"
).partial(format_instructions=json_parser.get_format_instructions())

route_chain = route_prompt | llm | json_parser

decision = route_chain.invoke("How do I restart the payments service?")
print(decision["area"])         # wiki
{'area': 'wiki', 'reason': 'This is an operational procedure from an engineering runbook.'}

That area value is exactly what you would feed into the metadata filter from the filtering section, so the search only looks inside the right documents. But a dictionary trusts the model completely, which is where the last parser comes in.

PydanticOutputParser: a typed, validated object

A dictionary is flexible, and that is its weakness. Nothing stops the model from returning "Area" instead of "area", a number where you expected text, or a value you never allowed. PydanticOutputParser closes that gap. You describe the result as a Pydantic model, with typed fields and rules, and the parser both tells the model the exact format to use and validates the reply against it. What you get back is a real Python object, not a loose dictionary.

Pydantic model→Format instructions in the prompt→Chat model reply→Parser validates it→Typed object
from typing import Literal

from pydantic import BaseModel, Field
from langchain_core.output_parsers import PydanticOutputParser


class QueryPlan(BaseModel):
    area: Literal["policies", "wiki", "faq", "catalog"] = Field(description="Where the answer lives")
    topic: str = Field(description="The topic in 2 or 3 words")
    needs_exact_numbers: bool = Field(description="True if amounts or dates are wanted")


plan_parser = PydanticOutputParser(pydantic_object=QueryPlan)

plan_prompt = ChatPromptTemplate.from_template(
    "Analyse the question.\n{format_instructions}\nQuestion: {question}"
).partial(format_instructions=plan_parser.get_format_instructions())

plan_chain = plan_prompt | llm | plan_parser

plan = plan_chain.invoke("What is the limit for client dinners?")

print(type(plan).__name__)          # QueryPlan, a real object
print(plan.area)                    # policies
print(plan.topic)                   # client dinner limit
print(plan.needs_exact_numbers)     # True

Look at what each part of the model does:

  • Types and choices. Literal[...] limits area to four allowed values. If the model invents a fifth, validation fails instead of passing a bad value into your code.
  • Field descriptions are instructions. The description texts are included in the format instructions sent to the model, so well-written descriptions give better results.
  • A usable object. You write plan.area with editor autocomplete, not plan["area"] and a hope that the key exists.
  • Reusable. The same model can describe an API response, a database record or a function's output elsewhere in your project.

The routing example from the JSON section becomes safer this way. The validated plan.area can go straight into the metadata filter, because you know it is one of the four real areas.

It is often more reliable than prompt instructions, but it needs a model that supports tool calling. The explicit RAG pipeline

Before using any clever composition syntax, write the pipeline by hand, one visible step at a time. This is the best version to learn from, because you can print and inspect everything in between.

One detail first. Different loaders produce different metadata. A PDF Document has a page, a Markdown chunk has headings, and a CSV row has a row number. So write one small helper that turns any Document into a human-readable citation, and use it everywhere.

def cite(doc) -> str:
    m = doc.metadata
    if "page" in m:
        return f"{m['filename']}, page {m['page'] + 1}"           # PDF: page is zero-based
    section = m.get("h3") or m.get("h2") or m.get("h1")
    if section:
        return f"{m['filename']}, section '{section}'"            # Markdown: heading path
    return m["filename"]                                          # CSV and others


def format_docs(docs) -> str:
    """Number each chunk and label it with its origin so the LLM can cite it."""
    return "\n\n---\n\n".join(
        f"[{i}] ({cite(d)})\n{d.page_content}" for i, d in enumerate(docs, start=1)
    )
explicit_rag.py 
question = "How many days of paid leave do full-time employees get?"

docs = retriever.invoke(question)                                   # 1. retrieve
context = format_docs(docs)                                         # 2. format
messages = prompt.invoke({"context": context, "question": question})  # 3. build the prompt
response = llm.invoke(messages)                                     # 4. generate

print(response.content)
Full-time employees receive 24 days of paid annual leave per calendar year, and up to
5 unused days can be carried over into the next year [1].

Every arrow of your pipeline is now a line of code. When something goes wrong, you know exactly which line to print.

The same pipeline as an LCEL chain

Once the explicit version is clear, LangChain lets you express it as a chain. Every component is a Runnable, and the pipe operator | connects them so the output of one becomes the input of the next. The first step is a small dictionary that builds the two prompt inputs in parallel.

from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

rag_chain = (
    {
        "context": retriever | format_docs,   # question -> Documents -> context string
        "question": RunnablePassthrough(),    # question -> question, unchanged
    }
    | prompt
    | llm
    | StrOutputParser()                       # AIMessage -> plain string
)

print(rag_chain.invoke("Which plan includes single sign-on?"))

Read it top to bottom as a data flow. The dictionary runs both branches on the same question. The prompt fills its two blanks, the model answers, and the parser strips the message wrapper. Because everything is a Runnable, you get extra methods for free:

# stream tokens as they are generated
for token in rag_chain.stream("How do I set up the company VPN?"):
    print(token, end="", flush=True)

# answer several questions at once
answers = rag_chain.batch([
    "How many days of paid leave do I get?",
    "Can I expense a client dinner?",
])
Do not memorise the syntax. Memorise the flow: question, then retrieve and format, then prompt, then model, then parse. The code is just that sentence written down.

Debugging a RAG pipeline

When an answer is wrong, do not tweak the prompt at random. Walk the pipeline in order and look at the real data at each stage:

question = "How do I restart the payments service?"

docs = retriever.invoke(question)
print("RETRIEVED")
for i, d in enumerate(docs, start=1):
    print(f"[{i}] {cite(d)}: {d.page_content[:120]!r}")

context = format_docs(docs)
print("\nCONTEXT LENGTH:", len(context), "characters")

messages = prompt.invoke({"context": context, "question": question})
print("\nPROMPT MESSAGES")
for m in messages.to_messages():
    print(f"- {m.type}: {m.content[:100]!r}")

print("\nANSWER")
print(llm.invoke(messages).content)

The order is deliberate. Retrieval problems are by far the most common cause, so check them first. A model can only answer from what it is given.

part sixPutting it together

The one mental model to keep

Do not think LangChain equals RAG. Think of RAG as a pipeline in which each stage is a swappable component, and each component has a clear owner:

Documents→Loader→Splitter→Embeddings→Qdrant→Retriever→Prompt→Chat model→Answer

LangChain

The orchestration layer. Loaders, splitters, retrievers, prompts and chains.

Qdrant

The retrieval store. Vectors, payload, filtering and fast search.

OpenAI

The embedding provider. Turns text into comparable vectors.

OpenRouter

The generation gateway. Writes the final grounded answer.

The biggest lesson of all: most of the quality in a RAG system comes from choosing the right loader and the right splitter for each kind of document, not from the chain at the end. Parse well, chunk along the document's own structure, and the rest is plumbing.

Self-test

Try to answer each question out loud before opening it.

A PDF loads as blank pages. What is wrong, and what do you do?
It is almost certainly a scanned PDF with no text layer. Use an OCR-capable loader such as UnstructuredPDFLoader with strategy ocr_only, install tesseract, and spot-check the recognised text.
Why is RecursiveCharacterTextSplitter a safer default than CharacterTextSplitter?
CharacterTextSplitter cuts only at one separator, so one long paragraph stays whole and the chunk can exceed your size limit. The recursive splitter falls back to smaller separators until the chunk fits.
Why split Markdown on headings before splitting by size?
Headings are the document's own topic boundaries, and the heading path is stored in metadata for citations and filtering. The size splitter then only handles sections that are still too long.
When would you size chunks in tokens instead of characters?
When you need a hard guarantee against a model's token limit. Characters only approximate tokens, and the ratio changes with language and symbols.
Why must ingestion use stable IDs?
Qdrant upserts by ID. With stable IDs a re-run overwrites the same points. With random IDs every run appends duplicates, and the same paragraph can be retrieved several times.
Why must a tenant filter be enforced in code, not in the prompt?
A filter is a security boundary. The LLM can be tricked or simply make a mistake. A filter applied by your code from the user's identity cannot be bypassed by the model.
An answer is wrong. What do you check first?
The retrieved Documents. If the right chunks are not there, no prompt or model will fix it. Then check the context formatting, the prompt and finally the model.
