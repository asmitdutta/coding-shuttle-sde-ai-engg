a case study

Read 100 answers before you write one eval: how Airbnb tests its GenAI features

An LLM feature that looks fine in a demo can still invent a refund rule, ramble, or refuse a fair question. Airbnb's answer is eval-driven development: read the outputs first, turn the mistakes you actually find into a few narrow checks, trust an LLM judge only after it agrees with people, and make the score itself repeatable. This is what Airbnb published, and how to build the same harness yourself.

By Anuj Kumar Sharma about 20 minutes Module 5 · AI Evaluation (Evals) & Observability
the story

story · 01Why this case study

Every case so far in this course ended with a number. Somebody had to produce those numbers, and with LLMs that is harder than it sounds: the output changes from run to run, "correct" is partly taste, and the grader is often another LLM with its own mistakes.

In July 2026 two Airbnb teams published how they evaluate their LLM features. It isn't a launch with a headline metric; it is a working method, and that is the part of an AI project you will do every week, whatever you build.

what you will be able to do

Turn a pile of model outputs into a short list of evals, decide which failures need code, a judge or a person, calibrate a judge before trusting it, tell a real improvement from evaluation noise, and estimate what running evals in production will cost.

story · 02The problem: "looks fine" is not a test

Airbnb's own LLM launches include review highlights, AI customer support, and smart communication features for guests and hosts.S1 Intro A shared infrastructure team provides evaluation tooling and best practices, and each product team adds its own criteria on top.S1 Intro

The difficulty is stated plainly: LLM outputs are non-deterministic, "correct" is subjective, so you often need an AI to judge an AI, and one interaction can chain retrieval, reasoning, tool calls and generation, any of which can fail on its own.S1 Intro Without a deliberate plan, the post says, three things tend to happen:S1 §1

  • False confidence. A generic "helpfulness" score looks good, you ship, and it never measured the failure people actually hit.
  • Undetected regressions. A prompt change quietly makes something worse that you weren't measuring.
  • Wasted effort. You scale a pipeline for metrics that don't track outcomes.

So the authors tell teams to expect a "meaningful share" of total project effort to go into evaluation, and they add that their advice is not meant to be prescriptive.S1 Intro, §1

story · 03The one rule: read the outputs first

The starting point Airbnb recommends to every team is almost embarrassingly simple: build the prototype, run it through 100 examples (synthetic is fine), and read the outputs. Read the traces, find the model's mistakes, categorise them, and build an eval for each category. "This single habit will do more for your product quality than any framework," the post says.S1 §1.1

Formalised, the habit is eval-driven development (EDD), the GenAI version of test-driven development: instead of predicting every failure upfront, you build the habit of discovering failures, encoding them as evals, and re-testing them on every change.S1 §1.2 Five principles anchor it:S1 §1.2

  1. Define goals and gates upfront, even if the data reveals them.
  2. Let real errors guide your metrics, not ones invented in a vacuum.
  3. Keep the evaluator set small: 3–5 well-calibrated LLM judges beat 20–30 noisy ones, one dimension each.
  4. Appoint a human decision-maker for when people disagree about "good".
  5. Collaborate continuously with product: "is X better than Y?", "what's wrong with this output?"

    story · 04Three layers of checks

    Every evaluation uses one, or a mix, of three methods, stacked from cheapest to most expensive: programmatic checks catch obvious failures fast, an LLM-as-a-judge (Airbnb calls these "virtual judges") catches quality problems, and human evaluation validates the edge cases and calibrates the whole stack.S1 §2 Which layer leads depends on the moment: Airbnb's table separates daily development, the pre-release gate and production monitoring.S1 §2.4

    story · 05A judge you can actually debug

    A virtual judge is a stronger LLM grading another LLM's output against a rubric, for qualities like tone, coherence, faithfulness and relevance, at a fraction of the cost of human review.S1 §2.2 The catch is the rubric. Airbnb's test: if a human can't apply it consistently, an LLM certainly can't.S1 §2.2

    The post's example judge scores one thing only: whether a short listing explanation reads cleanly. Condensed, it looks like this:S1 §2.2

    Score the readability of a listing explanation. 1 = reads cleanly: warm but professional, simple, grammatical. 0 = ANY of: wrong tone (jargon, slang, salesy, robotic) · internal terms · quotation marks, bullets or fragments · ends in "!" or "?" · needlessly complex words. Includes examples that pass and examples that fail. Return ONLY JSON: {"reason": "…", "score": 1 or 0}

    story · 06Calibrate before you trust it

    "A virtual judge that hasn't been calibrated is worse than no judge at all," the post warns, because it gives false confidence.S1 §2.2.1 The loop it recommends:S1 §2.2.1

    1. Build a golden set of 50–100 examples labelled by people. It must include bad examples, not only good ones.
    2. Run the judge on the golden set.
    3. Measure agreement. Aim for the high 80s to 90s percent, using Cohen's kappa or Krippendorff's alpha if you want chance-corrected numbers. Perfect agreement isn't achievable; even humans disagree.
    4. Read the disagreements, fix the prompt and the few-shot examples, and re-run until you reach the target.
    5. Recalibrate from time to time, because failure modes change.

    People stay essential: they create the ground truth, gate high-stakes cases such as discrimination, judge humour and brand voice, and break ties between a judge and a check.S1 §2.3 Start with 20–100 expert-labelled rows, and if the experts disagree with each other, resolve that before automating anything.S1 §2.4

    the walkthrough's calibration story

    In Airbnb's fictionalized walkthrough, a product manager labels 60 examples. The faithfulness judge agrees with the PM 78% of the time. Reading the disagreements shows it is marking accurate paraphrases as "unfaithful". A rubric fix and new few-shot examples take agreement to 88%, a 10-point gain. Only then does the team improve retrieval.S1 §4 These numbers illustrate the method; Airbnb does not report them as a measured product result.

    story · 07Evaluating an agent, not just its answer

    For agents, judging only the final answer is not enough: a correct answer can hide a broken reasoning path, wrong tool parameters, or a wasteful route.S1 §3 Airbnb evaluates three layers:S1 §3

    LayerThe questionFor example
    StepWas each tool call, retrieval or reasoning step correct?Right booking API, right dates?
    TrajectoryWas the whole path reasonable and efficient?Two steps or twelve for a simple question?
    SessionDid the conversation reach the person's goal?Was the issue resolved?

    The practical trick: an agent already writes traces and spans under one application root, with the agent type, any sub-agent, inputs, outputs and tools called. Store them, rebuild the tree in memory with a depth-first walk, and you can check that the right sub-agent ran at the right time with the right tools, or scope an eval to one sub-agent.S1 §3

    story · 08When the score itself is noisy

    The second Airbnb post starts where the first ends. F1 or BLEU give the same number for the same input; an LLM judge doesn't, and LLM-written reference answers come out as different strings each run. So a two-percent score movement could mean the model improved, the judge drifted, the references shifted, or all three.S2 Layer 1 In Airbnb's setting, the noise is the size of the signal:S2 Layer 1

    ~3 in 4LLM-generated references differ across labeling runs on identical inputsS2 Layer 1
    ~1%drift of the same judge across runs on the same datasetS2 Layer 1
    1–3%the size of the real improvement they were trying to detectS2 Layer 1

    The post names two kinds of uncertainty with different fixes: aleatoric (the task is ambiguous) and epistemic (the model or judge lacks knowledge). Some judge disagreements can be fixed; others belong to the task.S2 Layer 1

    The fix: cache, don't vote

    Majority-voting many judge runs only converges on the judge's habits, not the truth.S2 Layer 2 And when Airbnb measured, more than half of model outputs across candidates were identical strings: most of the noise came from the testing process itself. So it caches per sample: references keyed by sample and reference config, judge scores keyed by sample, output, judge config and metric. Identical inputs return the stored result, so runs are deterministic, cheaper and resumable; a job that fails at example 8,000 picks up from the cache.S2 Layer 2

    story · 09Production, and the seams between parts

    Evaluation doesn't stop at launch. For its production AI customer support agent, Airbnb periodically sends traffic through risk and performance judges, aggregates the scores per interval on dashboards, and samples flagged answers for privacy-gated human review.S1 §2.4 The walkthrough gives the loop numbers: sample 5% of de-identified live traffic daily, run checks and judges, and hold a weekly PM review that turns new failures into new evals.S1 §4 When comparing candidates, change one variable at a time (prompt, then model, then serving) with the same judges throughout.S1 §4

    Fast, deterministic evals are what let Airbnb ship small fixes the same day: a "micro adapter", a LoRA patch of rank under 50 on an 8-billion-parameter model, trained in under an hour on one GPU, behind two gates and a canary with automatic rollback.S2 Layer 3 And because each part can pass its own tests while the combination fails, a small representative set, seeded with past incidents, runs through the whole production path on every release candidate, catching seam bugs like a truncated field or a misread code-mixed input.S2 Layer 4

    the line to remember

    "The debt accumulates at the seams, not in the components."S2 Conclusion Evaluate the system, not just the model.

    practice · 01Wiring it into your code

    A small, working evaluation harness for a support bot: checks first, one judge per dimension, a per-sample cache, a calibration report, a production sampler and a trajectory check. It is our implementation, not Airbnb's code; Airbnb published the method, not an implementation.

    # pip install pydantic openai
import os

from openai import OpenAI

client = OpenAI()  # reads OPENAI_API_KEY from the environment


def make_llm(model: str):
    def llm(prompt: str) -> str:
        response = client.chat.completions.create(
            model=model,  # a chat model your account can use
            messages=[{"role": "user", "content": prompt}],
            temperature=0,  # grading wants repeatable output
        )
        return response.choices[0].message.content or ""
    return llm


generator = make_llm(os.environ["GENERATOR_MODEL"])  # writes the answers you are testing
judge_llm = make_llm(os.environ["JUDGE_MODEL"])  # grades them: a different model family or version

    1 · The cheap layer: checks with no LLM call

    The bot must return JSON that matches a schema. Anything else fails here, before you pay for a judge.

    import hashlib
import json
import random
import re
from collections.abc import Callable, Iterator
from dataclasses import dataclass, field
from pathlib import Path
from typing import Literal

from pydantic import BaseModel, ValidationError

LLM = Callable[[str], str]

# ---------- layer 1: programmatic checks (no LLM call) ----------
MIN_CHARS, MAX_CHARS = 20, 600

FORBIDDEN = re.compile(r"\b(listing_id|internal use only|as an ai language model)\b", re.IGNORECASE)

class SupportAnswer(BaseModel):
    """The structured output the bot must return. Free text fails the format check."""
    answer: str
    sources: list[str]

def programmatic_checks(raw: str) -> list[str]:
    """Return failure codes for one raw bot output; an empty list means it passed."""
    try:
        out = SupportAnswer.model_validate_json(raw)
    except ValidationError:
        return ["format"]
    failures = []
    if not MIN_CHARS <= len(out.answer) <= MAX_CHARS:
        failures.append("length")
    if FORBIDDEN.search(out.answer):
        failures.append("forbidden_term")
    if not out.sources:
        failures.append("no_sources")
    return failures

    2 · One judge per dimension, strict JSON out

    The verdict is parsed into a typed model that only accepts a 0 or a 1. A judge that replies in prose raises an error instead of being guessed at.

    # ---------- layer 2: one judge per dimension ----------
@dataclass(frozen=True)
class Judge:
    name: str  # the ONE dimension it scores, e.g. "faithfulness"
    rubric: str  # what passes, what fails, plus 2-3 good and 2-3 bad examples
    model: str  # must differ from the generator's model (models favour their own style)

class Verdict(BaseModel):
    reason: str
    score: Literal[0, 1]  # binary by default; anything else is a broken judge, not a score

JUDGE_PROMPT = """You are grading ONE thing: {name}.
{rubric}

Customer question: {question}
Policy text the answer must stick to: {context}
Answer to grade: {answer}

Return ONLY JSON: {{"reason": "<one sentence>", "score": 1 or 0}}"""

def run_judge(judge: Judge, llm: LLM, question: str, context: str, answer: str) -> Verdict:
    raw = llm(JUDGE_PROMPT.format(name=judge.name, rubric=judge.rubric, question=question,
                                  context=context, answer=answer))
    return Verdict.model_validate_json(raw)  # raises on free text instead of guessing a score

    3 · The per-sample cache

    The key includes the rubric and the judge model, so editing the rubric invalidates old scores, as recalibration should. Each score is written as it arrives, so a crash loses nothing.

    # ---------- per-sample cache: same inputs, same score, resumable runs ----------
class ScoreCache:
    """Judge scores keyed by sample, output and judge config, appended to a JSONL file as they arrive."""

    def __init__(self, path: Path):
        self.path = path
        self.scores: dict[str, int] = {}
        if path.exists():
            for line in path.read_text(encoding="utf-8").splitlines():
                row = json.loads(line)
                self.scores[row["key"]] = row["score"]

    @staticmethod
    def key(sample_id: str, output: str, judge: Judge) -> str:
        # Change the rubric or the judge model and every key changes: old scores no longer apply.
        blob = json.dumps([sample_id, output, judge.name, judge.rubric, judge.model])
        return hashlib.sha256(blob.encode("utf-8")).hexdigest()

    def get(self, key: str) -> int | None:
        return self.scores.get(key)

    def put(self, key: str, score: int) -> None:
        self.scores[key] = score
        with self.path.open("a", encoding="utf-8") as f:  # written now, so a crash loses nothing
            f.write(json.dumps({"key": key, "score": score}) + "\n")

    4 · The layered run

    Checks first, judges only on what passes them, and anything a judge fails goes to a human queue. It refuses to run a judge on the generator's own model.

    # ---------- the layered run ----------
@dataclass
class Sample:
    id: str
    question: str
    context: str
    output: str  # the bot's raw output, exactly as it returned it

@dataclass
class Result:
    sample_id: str
    failures: list[str]
    scores: dict[str, int] = field(default_factory=dict)
    needs_human: bool = False

def evaluate(samples: list[Sample], judges: list[Judge], llm: LLM, cache: ScoreCache,
             generator_model: str) -> list[Result]:
    """Checks first; judges only on outputs that pass them; judge failures go to a human queue."""
    for j in judges:
        if j.model == generator_model:
            raise ValueError(f"judge {j.name!r} uses the generator's model; use a different one")
    results = []
    for s in samples:
        failures = programmatic_checks(s.output)
        if failures:  # an obvious failure: don't pay for a judge call
            results.append(Result(s.id, failures))
            continue
        answer = SupportAnswer.model_validate_json(s.output).answer
        scores = {}
        for j in judges:
            k = cache.key(s.id, s.output, j)
            score = cache.get(k)
            if score is None:
                score = run_judge(j, llm, s.question, s.context, answer).score
                cache.put(k, score)
            scores[j.name] = score
        failed = [name for name, v in scores.items() if v == 0]
        results.append(Result(s.id, failed, scores, needs_human=bool(failed)))
    return results

    5 · Calibration and production

    Agreement and kappa against a golden set (which must contain bad rows), a reproducible daily sample that is de-identified before anyone reads it, and a depth-first trajectory check for agents.

    # ---------- calibration: is the judge trustworthy yet? ----------
def cohens_kappa(judge: list[int], human: list[int]) -> float:
    """Agreement corrected for chance, for binary labels."""
    n = len(human)
    observed = sum(a == b for a, b in zip(judge, human)) / n
    p_judge, p_human = sum(judge) / n, sum(human) / n
    expected = p_judge * p_human + (1 - p_judge) * (1 - p_human)
    return 1.0 if expected == 1 else (observed - expected) / (1 - expected)

def calibrate(judge_scores: list[int], human_labels: list[int]) -> dict:
    """Compare a judge with a human-labelled golden set; return agreement, kappa and the rows to read."""
    if len(judge_scores) != len(human_labels):
        raise ValueError("one judge score per golden row")
    if 0 not in human_labels:
        raise ValueError("the golden set has no bad examples, so it can't test the judge")
    agree = sum(a == b for a, b in zip(judge_scores, human_labels))
    return {
        "agreement": agree / len(human_labels),
        "kappa": cohens_kappa(judge_scores, human_labels),
        "disagreements": [i for i, (a, b) in enumerate(zip(judge_scores, human_labels)) if a != b],
    }

# ---------- production: sample live traffic, de-identify before anyone reads it ----------
def sample_traffic(records: list[dict], rate: float, seed: int,
                   deidentify: Callable[[dict], dict]) -> list[dict]:
    rng = random.Random(seed)  # seeded, so the same day's sample can be reproduced
    return [deidentify(r) for r in records if rng.random() < rate]

# ---------- agents: check the path, not only the final answer ----------
@dataclass
class Span:
    name: str  # e.g. "support_agent", "lookup_booking", "refund_tool"
    kind: Literal["agent", "tool", "llm"]
    children: list[Span] = field(default_factory=list)

def walk(span: Span) -> Iterator[Span]:
    """Depth-first walk over a trace, in the order the spans ran."""
    yield span
    for child in span.children:
        yield from walk(child)

def check_trajectory(root: Span, required_tools: list[str], max_steps: int) -> dict:
    tools = [s.name for s in walk(root) if s.kind == "tool"]
    return {
        "missing": [t for t in required_tools if t not in tools],  # step level: right tools?
        "steps": len(tools),
        "too_long": len(tools) > max_steps,  # trajectory level: 2 steps or 12?
    }

    practice · 05When it breaks: symptoms, causes, fixes

    Read a symptom, guess the cause, then open the card. analysis except where a card cites Airbnb.

    Likely cause. The rubric treats accurate paraphrases as "unfaithful", exactly the bug in Airbnb's walkthrough.S1 §4

    Likely cause. The judge drifts and references regenerate between runs.S2 Layer 1

    Fix. Cache references and judge scores per sample, so identical inputs return identical results.S2 Layer 2

    Likely cause. The judge and the generator are the same model, and models favour their own style.S1 §2.2

    Fix. Use a different model family or version for the judge, and enforce it in code.

    Likely cause. One prompt scores helpfulness, safety and tone together, so it can't be debugged.S1 §2.2

    Fix. Split it into one judge per dimension, each with its own rubric and calibration.

    Likely cause. The golden set had no bad examples, so a judge that passes everything looks perfect.

    Fix. Include bad examples; Airbnb says the golden set MUST have them.S1 §2.2.1

    Likely cause. The bug is at a seam: language detection, preprocessing or caching in combination.S2 Layer 4

    Fix. Run a small representative set, seeded with past incidents, through the full production path on every release candidate.S2 Layer 4

    practice · 06Interview prep

    Try answering before you open each one. documented = from Airbnb's posts, analysis = reasoning you would add.

    basicsWhy can't you unit-test an LLM feature the normal way?

    documented Outputs are non-deterministic, "correct" is subjective, and one interaction chains retrieval, reasoning, tools and generation that can each fail.S1 Intro

    analysis Keep unit tests for the deterministic parts, and add layered evals for the model's behaviour.

    processWhere should your first evals come from?

    documented Run the prototype on about 100 examples, read the outputs and traces, categorise the mistakes, and build an eval for each category.S1 §1.1

    analysis Metrics invented before you've seen failures tend to measure the wrong thing, which is the "false confidence" failure.

    judgesWhy several narrow judges instead of one quality score?

    documented One judge per dimension; 3–5 well-calibrated judges beat 20–30 noisy ones; at Airbnb a pipeline normally has 1–7.S1 §1.2, §2.2

    analysis A narrow judge tells you what got worse, and can be calibrated on its own.

    calibrationHow do you know a judge is trustworthy?

    documented A golden set of 50–100 human-labelled examples including bad ones; measure agreement (target high 80s–90s, kappa or alpha); fix the prompt from the disagreements; recalibrate periodically.S1 §2.2.1

    analysis Report kappa as well as raw agreement; a lazy judge can score high agreement on an unbalanced set.

    statisticsYour new prompt scores 0.819 against 0.812. Do you ship it?

    documented Airbnb found its judge drifted about 1% between runs while real gains were 1–3%. It made scoring deterministic with a per-sample cache and asks that a difference survive judge rotation and re-stratification.S2 Layers 1–2

    analysis Not yet. Re-score with cached, fixed judges, look at the rows that actually changed, and swap the judge before deciding.

    agentsHow do you evaluate an agent, not just its final answer?

    documented At step, trajectory and session level, by rebuilding the trace tree with a depth-first walk and checking which sub-agents and tools ran.S1 §3

    analysis A right answer reached in twelve tool calls is a cost and latency bug waiting to happen.

    productionWhat changes after launch?

    documented Live traffic goes through risk and performance judges on a schedule, scores go to dashboards, and flagged answers are sampled for privacy-gated human review.S1 §2.4

    analysis New failures found in production become new evals, which is how the loop stays closed.

    designYou have one week to set up evals for a new RAG bot. What do you do?

    analysis Day 1: run 100 questions and read every answer. Day 2: categorise failures and add schema and length checks. Days 3–4: write one judge per real failure and have an expert label 50–100 rows, including bad ones. Day 5: calibrate, add the cache, and set the release gate. Then sample production.

    wrap-upConclusion: measure what actually breaks

    Airbnb's method is less about tools than discipline. Let real mistakes choose the evals. Put cheap code before judges, and judges before people. Don't trust a judge until it agrees with people on a golden set with bad answers. Make the score repeatable, because a 1% wobble can swallow a 2% win. And keep evaluating after launch, where the new failures come from.

    Four things to carry away

    • Read about 100 outputs first; let the mistakes choose the evals.
    • Layer the checks: code, then one judge per dimension, then people.
    • Calibrate the judge on a golden set with bad examples before you trust it.
    • Cache scores per sample, so a gap you see is a gap that exists.

    referenceGlossary

    Eval-driven development
    Discovering failures, encoding them as evals, and re-testing on every change; the GenAI version of TDD.
    Virtual judge
    Airbnb's name for an LLM that grades another LLM's output against a rubric.
    Rubric
    The written criteria a judge applies, with what passes, what fails, and examples.
    Golden set
    Human-labelled examples, good and bad, used as ground truth.
    Calibration
    Checking and tuning a judge until it agrees with human labels.
    Cohen's kappa
    Agreement between two raters, corrected for agreement by chance (0 = chance, 1 = perfect).
    Programmatic check
    Deterministic code that tests an output, such as a schema or regex, with no LLM call.
    Trace / span
    A record of one request (trace) made of timed steps (spans) such as LLM and tool calls.
    Aleatoric uncertainty
    Uncertainty from the task itself being ambiguous.
    Epistemic uncertainty
    Uncertainty because the model or judge lacks knowledge.
    Per-sample cache
    Stored results keyed by input and config, so identical inputs give identical scores.
    LoRA adapter
    A small set of extra weights trained on top of a frozen model to change its behaviour.
    Canary deploy
    Releasing to a small share of traffic first, with automatic rollback if it misbehaves.
