a case study

One lead agent, many parallel subagents: how Anthropic's Research system beat a single agent by 90.2%

Ask Claude's Research feature a broad question and one agent doesn't do all the searching. A lead agent plans, splits the question into tasks, and hands them to subagents that search side by side in their own context windows. On Anthropic's internal research eval that setup beat a single agent by 90.2%, while using about 15 times the tokens of a chat. This is what Anthropic published about building it, and how to build the same orchestrator yourself.

By Anuj Kumar Sharma about 24 minutes Module 6 · MCP, Context Engineering & Multi-Agent Orchestration
the story

story · 01Why this case study

The agents earlier in this course work alone: one model, one loop, one context window. That works until the job is bigger than one context window, or slow because it does one search at a time. The obvious next step is more agents, and the obvious risk is a system that burns tokens and trips over itself.

In June 2025 Anthropic's engineering team published how it built the multi-agent system behind Claude's Research feature, and it is one of the most detailed public accounts of a production orchestrator: the architecture, the prompts that steer it, what it costs, how it was evaluated, what broke in production, and when not to use the pattern.S1 Anthropic also open-sourced example prompts from the system.S4

story · 02The problem: research doesn't follow a script

Claude's Research feature searches the web, Google Workspace and connected integrations to answer complex questions.S1 intro It launched in early beta in April 2025.S3 Research is the hard case for automation: you can't predict the steps in advance, because what you find changes what you look for next. A fixed pipeline, or a single retrieval step, can't follow leads like that.S1 Benefits

Anthropic contrasts this with classic RAG, which fetches the chunks most similar to the query once and answers from them. Research needs a multi-step search that adapts to what it finds.S1 Architecture A single agent can do multi-step search, but it does it in one long, sequential thread inside one context window. The post's example: asked for all the board members of the companies in the Information Technology S&P 500, a single agent failed with slow, sequential searches, while the multi-agent system found the answers by splitting the job across subagents.S1 Benefits

the idea in one line

"The essence of search is compression." Subagents explore different parts of the question in parallel, each in its own context window, and pass only the most important findings back to the lead.S1 Benefits

story · 03The architecture: a lead and its workers

Research uses an orchestrator-worker pattern: a lead agent coordinates the process and delegates to specialised subagents that run in parallel.S1 Architecture Anthropic's earlier guide defines the general pattern: a central LLM breaks a task down at run time, delegates the parts to worker LLMs, and synthesises their results. What separates it from a fixed parallel workflow is that the subtasks aren't predefined; the orchestrator decides them from the input.S2 Workflows

story · 05Why it works, and what it costs

Anthropic's internal research eval compared a multi-agent setup, with Claude Opus 4 as the lead and Claude Sonnet 4 subagents, against a single Claude Opus 4 agent. The multi-agent system did better by 90.2%.S1 Benefits Read that number carefully: it's a relative gain on an internal eval whose questions, metric and absolute scores aren't published, measured on the June 2025 Claude 4 models.

Why does it help? Anthropic's answer is blunt: "multi-agent systems work mainly because they help spend enough tokens to solve the problem". On BrowseComp, a benchmark of finding hard-to-find information by browsing, three factors explained 95% of the variance in performance, and token usage alone explained 80%. The other two were the number of tool calls and the choice of model.S1 Benefits Separate context windows let the system spend more tokens in parallel than one agent can. The model still matters: upgrading to Claude Sonnet 4 gained more than doubling the token budget on Claude Sonnet 3.7.S1 Benefits

So the pattern only pays off when the task is valuable enough to cover the extra tokens. Anthropic says it fits best for "valuable tasks that involve heavy parallelization, information that exceeds single context windows, and interfacing with numerous complex tools", and fits badly where all agents need the same context or depend on each other a lot. Most coding tasks, it notes, have fewer truly parallel parts than research, and LLM agents are "not yet great at coordinating and delegating to other agents in real time".S1 Benefits

story · 06Teaching the lead to delegate and to budget

Early versions misbehaved in ways that are easy to reproduce: spawning 50 subagents for a simple query, searching the web endlessly for sources that don't exist, and agents distracting each other with too many updates. Each agent is steered by its prompt, so prompt engineering was the main fix.S1 Prompting The team built simulations in its Console with the system's exact prompts and tools and watched agents work step by step, which exposed agents that kept going after they had enough, used overly long queries, or picked the wrong tool.S1 Prompting

A task description has four parts

The lead breaks the query into subtasks and describes each one to a subagent. Each description needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries. Without them, agents duplicate work, leave gaps, or miss what they were meant to find.S1 Prompting The post's example: a short instruction like "research the semiconductor shortage" was so vague that one subagent explored the 2021 automotive chip crisis while two others both investigated current 2025 supply chains.S1 Prompting You can recreate that in the delegation playground later on this page.

Scale effort to the question

Agents are bad at judging how much effort a task deserves, so the prompt carries explicit rules: simple fact-finding needs one agent with 3–10 tool calls, direct comparisons might need 2–4 subagents with 10–15 calls each, and complex research might use more than 10 subagents with clearly divided responsibilities. Over-investing in simple queries was "a common failure mode" of the early versions.S1 Prompting The prompts Anthropic open-sourced use different numbers, so treat neither set as a universal rule.S4 lead prompt Try both.

The other prompting lessons

  • Tool design matters as much as the prompt. An agent searching the web for something that only exists in Slack is "doomed from the start". With MCP servers, agents meet tools whose descriptions vary wildly in quality, so the prompt tells them to examine all tools first, match the tool to the intent, and prefer specialised tools.S1 Prompting
  • Let agents improve themselves. A tool-testing agent used a flawed MCP tool dozens of times and rewrote its description; later agents using the new description cut their task completion time by 40%.S1 Prompting
  • Start wide, then narrow. Agents default to long, specific queries that return little; the prompt asks for short, broad queries first.S1 Prompting
  • Think on purpose. The lead uses extended thinking to plan which tools fit, how complex the query is, how many subagents to create and what each one does; subagents use interleaved thinking after each tool result to judge quality and pick the next query.S1 Prompting

The overall strategy was "instilling good heuristics rather than rigid rules": the team studied how skilled people research (break hard questions into smaller ones, judge source quality, change approach after new information, choose between depth and breadth) and wrote those habits into the prompts, plus explicit guardrails to stop agents spiralling.S1 Prompting

story · 07Going parallel, and the slowest subagent

Early agents searched one thing at a time, which was "painfully slow". Anthropic added parallelism at two levels: the lead starts 3–5 subagents at once instead of one after another, and each subagent calls 3 or more tools at once. For complex queries, these two changes cut research time by up to 90%.S1 Prompting No before-and-after times are published, so treat "up to 90%" as the best case for complex queries, not a typical speed-up.

There is a catch the post states openly. The lead runs subagents synchronously: it waits for a whole set to finish before it continues. That keeps coordination simple, but the lead can't steer subagents mid-task, subagents can't coordinate with each other, and the whole system can be blocked waiting for one subagent that is still searching. Asynchronous execution would remove the wait, at the price of harder result coordination, state consistency and error propagation.S1 Production

story · 08How they evaluated a system that never takes the same path

A normal test assumes input X follows path Y to output Z. Multi-agent systems don't: from the same start, one run may search three sources and another ten, and both can be right. So Anthropic judged whether agents reached the right outcome by a reasonable process, rather than whether they followed prescribed steps.S1 Evaluation

  • Start small, right away. About 20 queries representing real usage were enough early on, because early changes have big effects; the post's illustration is a prompt tweak that "might" lift success from 30% to 80%.S1 Evaluation
  • One LLM judge with a rubric. Criteria: factual accuracy, citation accuracy, completeness, source quality and tool efficiency. A single call with one prompt, scoring 0.0–1.0 plus pass/fail, was more consistent and closer to human judgement than separate judges per criterion.S1 Evaluation
  • People still test it. Human testers found that early agents preferred SEO-optimised content farms over authoritative but lower-ranked sources such as academic PDFs; source-quality heuristics in the prompt fixed it.S1 Evaluation
  • Watch for emergent behaviour. Small changes to the lead can change how subagents behave in ways nobody predicted, so the best prompts are "frameworks for collaboration": division of labour, problem-solving approaches and effort budgets.S1 Evaluation
  • Judge the end state. For agents that change things over many turns, check that the final state is right, with a few checkpoints, instead of grading every step.S1 Appendix
two companies, two judge designs

Airbnb's evaluation guidance (case #08) prefers one judge per quality dimension; Anthropic found a single judge with a multi-criterion rubric most consistent for research reports. Both checked their judges against people. The lesson isn't "one judge" or "many judges", it's "measure which one agrees with humans on your task". analysis

claims you may see elsewhere

Summaries sometimes say multi-agent research is "90% faster" or "90% more accurate". The time figure is "up to 90%" for complex queries after two specific parallelism changes; the 90.2% is a relative gain on an internal eval with an unpublished metric. Nothing in the post says a multi-agent system is always better, or cheaper: it uses about 15 times the tokens of a chat and is a poor fit for tasks with shared context.

practice · 03Wiring it into your code

A small orchestrator in LangGraph: the lead plans and caps the subagents, LangGraph's Send fans the tasks out so the subagents run in parallel, each subagent has a tool-call budget and a time limit, the lead decides whether another round is needed, and a citation step adds sources. It is our implementation, not Anthropic's code; Anthropic published the design and example prompts, not its orchestrator.

    def llm(prompt: str) -> str:

1 · The contract: effort caps and a four-part task

The effort rules become hard caps in code, and a task that lacks any of the four parts fails validation instead of reaching a subagent.

import json
import operator
import re
import time
from collections.abc import Callable
from dataclasses import dataclass
from typing import Annotated, Literal, TypedDict

from langgraph.graph import END, START, StateGraph
from langgraph.types import Send
from pydantic import BaseModel, Field, ValidationError

LLM = Callable[[str], str]

Search = Callable[[str], list[dict]]  # each hit: {"url": ..., "text": ...}

# Effort rules, as caps. The post: 1 agent and 3-10 tool calls for fact-finding, 2-4 subagents with 10-15
# calls each for comparisons, more than 10 for complex research. 20 is the cap in Anthropic's published
# lead-agent prompt.
@dataclass(frozen=True)
class Effort:
    max_subagents: int
    calls_per_subagent: int

EFFORT = {
    "fact": Effort(max_subagents=1, calls_per_subagent=10),
    "comparison": Effort(max_subagents=4, calls_per_subagent=15),
    "complex": Effort(max_subagents=20, calls_per_subagent=15),
}

@dataclass(frozen=True)
class Limits:
    max_rounds: int = 3  # lead may send more subagents after reading results, but not forever
    total_calls: int = 120  # tool-call budget for the whole query, across every subagent
    subagent_seconds: float = 60.0  # one slow subagent must not hold the round hostage

DEFAULT_LIMITS = Limits()

# What every delegated task must say: an objective, an output format, tools and sources, task boundaries.
class TaskSpec(BaseModel):
    objective: str = Field(min_length=10)
    output_format: str = Field(min_length=3)
    tools: list[Literal["web_search"]] = Field(min_length=1)
    boundaries: str = Field(min_length=3)

class Plan(BaseModel):
    tier: Literal["fact", "comparison", "complex"]
    tasks: list[TaskSpec] = Field(min_length=1)

@dataclass(frozen=True)
class Finding:
    objective: str
    status: Literal["ok", "empty", "timeout", "failed"]
    summary: str
    sources: tuple[dict, ...]
    calls: int

2 · The lead plans, and the code keeps it honest

The model proposes the plan; code checks it, drops near-duplicate objectives and enforces the cap. A plan that doesn't parse falls back to one direct task rather than crashing.

def _words(text: str) -> set[str]:
    return set(re.findall(r"[a-z0-9]+", text.lower())) - {"the", "a", "an", "of", "and", "in", "for", "to", "on"}

def overlaps(a: str, b: str, threshold: float = 0.8) -> bool:
    """Two objectives that share most of their words would send two subagents on the same searches."""
    wa, wb = _words(a), _words(b)
    return bool(wa and wb) and len(wa & wb) / len(wa | wb) >= threshold

def drop_duplicates(tasks: list[TaskSpec]) -> list[TaskSpec]:
    kept: list[TaskSpec] = []
    for t in tasks:
        if not any(overlaps(t.objective, k.objective) for k in kept):
            kept.append(t)
    return kept

PLAN_PROMPT = """You are the lead researcher. Classify the query as "fact", "comparison" or "complex",
then split it into subtasks that do not overlap. For each subtask give: objective, output_format,
tools (["web_search"]) and boundaries (what NOT to cover).
Return ONLY JSON: {{"tier": "...", "tasks": [{{"objective": "...", "output_format": "...",
"tools": ["web_search"], "boundaries": "..."}}]}}
Query: {query}
{feedback}"""

def plan_tasks(lead: LLM, query: str, feedback: str = "") -> tuple[str, list[TaskSpec]]:
    """Ask the lead for a plan; validate it; cap and de-duplicate it. A bad plan falls back to one task."""
    try:
        plan = Plan.model_validate(json.loads(lead(PLAN_PROMPT.format(query=query, feedback=feedback))))
    except (json.JSONDecodeError, ValidationError):
        fallback = TaskSpec(objective=f"Answer directly: {query}", output_format="short answer with sources",
                            tools=["web_search"], boundaries="only this question")
        return "fact", [fallback]
    tasks = drop_duplicates(plan.tasks)
    return plan.tier, tasks[: EFFORT[plan.tier].max_subagents]

3 · A bounded subagent

Search, read, decide, until it is done or out of calls or time. A failing tool is reported back to the agent instead of killing the run, and a slow subagent returns what it has.

STEP_PROMPT = """You are a research subagent. Task: {objective}
Output format: {output_format}. Stay inside: {boundaries}
Tool calls left: {left}. Notes so far:
{notes}
Start with short, broad queries, then narrow down.
Return ONLY JSON, either {{"action": "search", "query": "..."}} or {{"action": "done", "summary": "..."}}"""

def run_subagent(worker: LLM, search: Search, task: TaskSpec, budget: int, deadline_s: float) -> Finding:
    """One subagent: search, read, decide, until done, out of budget, out of time, or out of luck."""
    start, calls, errors = time.monotonic(), 0, 0
    sources: dict[str, dict] = {}
    notes: list[str] = []
    while calls < budget:
        if time.monotonic() - start > deadline_s:
            return Finding(task.objective, "timeout", "; ".join(notes), tuple(sources.values()), calls)
        prompt = STEP_PROMPT.format(objective=task.objective, output_format=task.output_format,
                                    boundaries=task.boundaries, left=budget - calls, notes="\n".join(notes) or "-")
        try:
            step = json.loads(worker(prompt))
        except json.JSONDecodeError:
            errors += 1
            if errors >= 2:
                break
            continue
        if step.get("action") == "done":
            status = "ok" if sources else "empty"
            return Finding(task.objective, status, step.get("summary", ""), tuple(sources.values()), calls)
        calls += 1
        try:
            hits = search(str(step.get("query", "")))
        except Exception as exc:  # noqa: BLE001  any tool error: tell the agent and let it adapt
            notes.append(f"search failed: {exc}")
            errors += 1
            if errors >= 2:
                break
            continue
        for h in hits:
            sources.setdefault(h["url"], h)
        notes.append(f"{step.get('query')}: {len(hits)} results")
    status = "failed" if errors >= 2 else ("ok" if sources else "empty")
    return Finding(task.objective, status, "; ".join(notes), tuple(sources.values()), calls)

4 · The graph: fan out, merge, decide

The reducer on findings merges results from subagents that ran at the same time. The lead only plans another round inside the round and tool-call budgets.

class ResearchState(TypedDict, total=False):
    query: str
    tier: str
    round: int
    pending: list[TaskSpec]
    findings: Annotated[list[Finding], operator.add]  # parallel subagents append; the reducer merges
    report: str
    cited: str

WRITE_PROMPT = """Write a research report that answers: {query}
Use only these findings. Do not add citations; a separate step adds them.
{findings}"""

def build_graph(lead: LLM, worker: LLM, search: Search, limits: Limits = DEFAULT_LIMITS):
    """plan -> parallel subagents -> decide (another round?) -> write -> cite."""

    def plan(state: ResearchState) -> dict:
        tier, tasks = plan_tasks(lead, state["query"])
        return {"tier": tier, "pending": tasks, "round": 1}

    def fan_out(state: ResearchState) -> list[Send]:
        effort = EFFORT[state["tier"]]
        return [Send("subagent", {"task": t, "budget": effort.calls_per_subagent}) for t in state["pending"]]

    def subagent(payload: dict) -> dict:
        return {"findings": [run_subagent(worker, search, payload["task"], payload["budget"],
                                          limits.subagent_seconds)]}

    def decide(state: ResearchState) -> dict:
        used = sum(f.calls for f in state["findings"])
        gaps = [f for f in state["findings"] if f.status != "ok"]
        if state["round"] >= limits.max_rounds or used >= limits.total_calls:
            return {"pending": []}
        done = "\n".join(f"- {f.objective}: {f.status}" for f in state["findings"])
        feedback = f"Already researched:\n{done}\nFailed or empty: {len(gaps)}. Plan ONLY what is still missing."
        _, more = plan_tasks(lead, state["query"], feedback)
        tried = [f.objective for f in state["findings"] if f.status == "ok"]
        more = [t for t in more if not any(overlaps(t.objective, o) for o in tried)]
        return {"pending": more, "round": state["round"] + 1}

    def after_decide(state: ResearchState) -> list[Send] | str:
        return fan_out(state) if state["pending"] else "write"

    def write(state: ResearchState) -> dict:
        lines = "\n".join(f"- {f.objective}: {f.summary}" for f in state["findings"] if f.status == "ok")
        return {"report": lead(WRITE_PROMPT.format(query=state["query"], findings=lines or "(none)"))}

    def cite(state: ResearchState) -> dict:
        return {"cited": add_citations(lead, state["report"], all_sources(state["findings"]))}

    g = StateGraph(ResearchState)
    for name, fn in (("plan", plan), ("subagent", subagent), ("decide", decide), ("write", write), ("cite", cite)):
        g.add_node(name, fn)
    g.add_edge(START, "plan")
    g.add_conditional_edges("plan", fan_out, ["subagent"])
    g.add_edge("subagent", "decide")
    g.add_conditional_edges("decide", after_decide, ["subagent", "write"])
    g.add_edge("write", "cite")
    g.add_edge("cite", END)
    return g.compile()

5 · Citations that can't change the answer

Like Anthropic's citation agent, this step must not edit the report. Here the model only picks which source backs which sentence; code inserts the markers and checks the text is unchanged.

CITE_PROMPT = """For each numbered sentence, pick the source URL that directly supports it, or skip it.
Return ONLY JSON: [{{"sentence": <number>, "url": "..."}}]
Sentences:
{sentences}
Sources:
{sources}"""

def sentences(text: str) -> list[str]:
    return re.findall(r"[^.!?]+[.!?]+\s*|[^.!?]+$", text)

def add_citations(cite_llm: LLM, report: str, sources: list[dict]) -> str:
    """The model only chooses which source backs which sentence; code inserts the markers, so the
    report text cannot change. Unknown URLs and out-of-range sentences are ignored."""
    parts = sentences(report)
    urls = [s["url"] for s in sources]
    try:
        picks = json.loads(cite_llm(CITE_PROMPT.format(
            sentences="\n".join(f"{i}. {p.strip()}" for i, p in enumerate(parts)),
            sources="\n".join(f"{u}: {s['text'][:300]}" for u, s in zip(urls, sources)))))
    except json.JSONDecodeError:
        return report
    marks: dict[int, list[int]] = {}
    for p in picks if isinstance(picks, list) else []:
        i, url = p.get("sentence"), p.get("url")
        if isinstance(i, int) and 0 <= i < len(parts) and url in urls and urls.index(url) + 1 not in marks.get(i, []):
            marks.setdefault(i, []).append(urls.index(url) + 1)
    out = []
    for i, p in enumerate(parts):
        body, space = p.rstrip(), p[len(p.rstrip()):]
        out.append(body + "".join(f"[{n}]" for n in marks.get(i, [])) + space)
    cited = "".join(out)
    assert re.sub(r"\[\d+\]", "", cited) == report, "citation step changed the report text"
    return cited

def all_sources(findings: list[Finding]) -> list[dict]:
    seen: dict[str, dict] = {}
    for f in findings:
        for s in f.sources:
            seen.setdefault(s["url"], s)  # two subagents finding the same page count it once
    return list(seen.values())

practice · 08Interview prep

Try answering before you open each one. documented = from Anthropic's posts or prompts, analysis = reasoning you would add.

patternWhat is the orchestrator-worker pattern, and how is it different from a parallel workflow?

documented A central LLM breaks the task down at run time, delegates to workers and synthesises their results; in a parallel workflow the subtasks are fixed in advance.S2 Workflows Research uses it with a lead agent and parallel search subagents.S1 Architecture

analysis Choose a fixed workflow when you can list the subtasks yourself; it is cheaper and easier to test.

resultsWhy did the multi-agent system beat a single agent, and what's the catch?

documented It spends more tokens across separate context windows: token usage alone explained 80% of BrowseComp variance. It beat single-agent Opus 4 by 90.2% on an internal eval, but multi-agent systems use about 15 times the tokens of a chat.S1 Benefits

analysis Report the gain with the eval's limits: internal, relative, metric unpublished.

effortHow does the lead decide how many subagents to create?

documented Effort rules in its prompt: one agent with 3–10 tool calls for fact-finding, 2–4 subagents for comparisons, more than 10 for complex research. Without them, early versions spawned 50 subagents for simple queries.S1 Prompting The open-sourced prompt uses different tiers and caps subagents at 20.S4 lead prompt

analysis Also enforce the cap in code; a prompt is a request, not a limit.

delegationWhat makes a good subagent task description?

documented An objective, an output format, guidance on tools and sources, and clear boundaries; otherwise agents duplicate work or leave gaps, as with "research the semiconductor shortage".S1 Prompting

analysis Validate the four parts in code before any subagent runs.

fitWhen would you not use a multi-agent system?

documented When agents must share the same context or depend heavily on each other, as in most coding, or when the task isn't valuable enough for the extra tokens.S1 Benefits Start with the simplest solution.S2 When to use

analysis Try one agent first and measure; add subagents when the task is breadth-first or overflows one context.

latencyOne subagent is slow. What happens, and what would you do?

documented With synchronous execution the lead waits for every subagent in the set, so one slow subagent blocks the system; asynchronous execution adds coordination, consistency and error-propagation problems.S1 Production

analysis Time-box subagents, return partial results with a gap flag, and let the lead decide whether the gap needs another round.

evalsHow do you evaluate a system that takes a different path every run?

documented Judge outcomes and a reasonable process, not prescribed steps; start with about 20 real queries; one rubric judge scoring 0.0–1.0 with pass/fail; human testing; end-state checks for agents that change state.S1 Evaluation

analysis Add cost per query to the scorecard, next to quality.

productionYour research agent crashes 30 minutes in. What should happen?

documented Resume from where it failed, using checkpoints and retries; tell the agent when a tool fails; trace decisions without reading conversation contents; use rainbow deployments so releases don't break running agents.S1 Production

analysis Persist the plan and each subagent's result as they arrive, so a resume never repeats finished work.

wrap-upConclusion: spend tokens on purpose

Anthropic's Research system works because it spends many more tokens than one agent could, in parallel and in separate context windows, and pays for it with a much bigger bill. Most of the engineering is about spending them on purpose: clear task descriptions so subagents don't repeat each other, effort rules so simple questions stay cheap, parallelism where tasks are independent, and evaluation, tracing and careful deploys so a system that never runs the same way twice can still be trusted.

Four things to carry away

  • Use multi-agent for breadth-first work that overflows one context, not for tightly coupled tasks.
  • Every subagent needs an objective, an output format, tools and sources, and boundaries.
  • Scale effort to the question, and cap it in code.
  • Parallel rounds are only as fast as their slowest subagent.

referenceGlossary

Agent
An LLM that uses tools in a loop and decides its own next step.
Multi-agent system
Several agents working together on one task.
Orchestrator-worker
A lead model splits a task at run time, delegates the parts and combines the results.
Lead agent
The orchestrator: plans, writes task descriptions, decides whether more research is needed, writes the report.
Subagent
A worker agent with its own prompt, tools and context window.
Context window
The text a model can see at once; long runs must summarise or store what doesn't fit.
Synchronous execution
The lead waits for every subagent in a set before continuing.
Extended / interleaved thinking
Visible reasoning before acting, or between tool results.
MCP
Model Context Protocol: a standard way to give models access to external tools and data.
BrowseComp
A benchmark of finding hard-to-find information by browsing the web.
Rainbow deployment
Running old and new versions side by side and shifting traffic gradually.
End-state evaluation
Checking that the final result or state is right, not every step taken.
LangGraph Send
A way to start one node many times in parallel, each with its own input.
