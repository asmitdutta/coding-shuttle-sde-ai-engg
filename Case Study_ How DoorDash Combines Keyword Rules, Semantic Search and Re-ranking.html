a case study

"Vegan" is a rule, "Szechuan" is a vibe: how DoorDash's hybrid search cut null searches by 3.65%

Some food searches carry hard rules, and some carry only a mood. DoorDash needed one search system that never shows a chicken sandwich to someone who typed "vegan", and still finds good answers for "cozy date night dinner". This is the story of how it combined keyword rules, embeddings, an LLM reranker and an LLM judge, and how to wire the same pattern into your own pipeline.

By Anuj Kumar Sharma about 16 minutes Module 3 · Advanced RAG & Search
the story

story · 01Why this case study

"Hybrid search" usually means "BM25 plus vectors". DoorDash's version is more useful to study, because each part exists for a reason you can name. Keyword retrieval with attribute rules handles the queries where a wrong result is unacceptable. Embedding retrieval handles the queries that have never been typed before. A reranker orders the short list that survives. And an LLM judge checks whether any of it is working.

DoorDash wrote about these pieces across three engineering posts between November 2024 and May 2026.S1S2S3 Together they show how a real search team adds one stage at a time.

what you will be able to do

Explain when keyword rules beat embeddings and when they don't, merge two ranked lists with Reciprocal Rank Fusion, put a cross-encoder reranker in front of your results, and evaluate search per facet instead of with one blended score.

story · 02The problem: rules and vibes in one search box

Rules. DoorDash users often type precise queries that combine several requirements. For "vegan chicken sandwich", a system based only on document similarity could return vegan sandwiches, vegetarian sandwiches, chicken sandwiches, and vegan chicken sandwiches. Only the last group matches exactly, and the preferences aren't equal: someone might accept any vegan sandwich, but never a chicken sandwich that isn't vegan. Dietary restrictions usually outrank other attributes.S1 intro

Vibes. Other searches carry intent that keywords can't capture: a mood ("cozy date night dinner"), a situation ("food for a sick friend"), discovery ("surprise me"), or several constraints at once ("gluten-free fast spicy affordable").S3 intro Rare and new queries also have no click history to learn from.S2 Semantic search

the ceiling

"If a relevant store/item never enters the candidate set, no downstream ranker can recover it."S2 Retrieval decides what the reranker is even allowed to see.

story · 04Stage 1: turn the query into rules

DoorDash had already built knowledge graphs for restaurant and retail items. Items carry metadata such as dietary preference, flavour, product category and quantity.S1 Knowledge graph The job of query understanding is to map a query onto the same concepts.

  1. Segment with a controlled vocabulary. Instead of asking an LLM for free-form segments, DoorDash asks it to put each meaningful segment under one of its taxonomy categories. "small no-milk vanilla ice cream" becomes Quantity: small, Dietary_Preference: no-milk, Flavor: vanilla, Product_Category: ice cream. The hallucination rate of this step is under 1%.S1 Segmentation
  2. Link segments to real concepts. Embeddings and an approximate nearest-neighbour (ANN) search retrieve the 100 closest taxonomy concepts for each query, and the LLM may choose only from that list. So "no-milk" links to "dairy-free" instead of to an invented label.S1 Entity linking
  3. Retrieve with rules. Linked concepts drive retrieval directly, for example dietary restrictions as a MUST condition and flavours as a SHOULD condition.S1 Entity linking
  4. Audit. Post-processing removes hallucinated output, and annotators review a statistically significant sample of each batch.S1 Evaluations

memorization vs generalization

Running an LLM over a fixed list of queries in batch is accurate but doesn't cover new queries, and its outputs go stale. DoorDash pairs it with methods that generalize, such as embedding retrieval, statistical methods like BM25, and heuristics.S1 Trade-offs

story · 05Stage 2: semantic recall, switched on by default

In 2026 DoorDash described the other half. LLMs write standard profiles for merchants and items at scale (ingredients, preparation, cuisine, dietary attributes); for items with photos, a vision-language model describes the image first. The profiles are embedded and refreshed only when the underlying content changes.S2 Profiles

Choosing the embedding model taught a lesson worth remembering. For item-to-item similarity, measured against LLM-judge reference rankings:S2 Table 1

DoorDash chose gemini-embedding-001 at 256 dimensions, using Matryoshka Representation Learning (MRL), which lets the vector be truncated with little loss. It uses different task types for queries and documents.S2 With these embeddings, semantic retrieval went from "selectively enabled" to default-on. For "Szechuan", the new retrieval found a range of Chinese restaurants where production search had shown a single Sichuan one.S2 Semantic search

story · 06Stage 3: items, and a reranker that reads both sides

Searches often name a dish, not a store. So DoorDash added item-level embedding retrieval alongside the store-level retrieval, then a fine-tuned Qwen 3 Rerank model. For each candidate store it reads the search query, the profiles of the top-k most relevant items in that store, and the store profile.S2 Item RAG The relevant item's photo then decorates the result card.

drawn by the author · Qwen3-Reranker scores query and document together in one input (S4)

Qwen3-Reranker puts the query and the document in one prompt and scores how likely the answer is "yes", the same way a cross-encoder scores a pair.S4 The trade-off: it is more accurate than comparing two separate vectors, but it needs one model call per candidate, so it only sees the short list.

Against the store-level-only baseline, the upgraded pipeline (item retrieval plus reranker) improved search relevance (nDCG) by 7.8% for dish queries and 1.4% for cuisine queries.S2

story · 07Stage 4: measuring it with an LLM judge

Natural-language queries create an evaluation problem: "cozy date night dinner" has no click history to check against. Human labelling took 2–5 days per cycle.S3 Motivation Worse, when DoorDash fine-tuned a Qwen3-based reranker on those human labels, it reached an AUC of 0.56 (0.5 is random).S3 The model wasn't the problem; the labels were.

  • In an audit, 19 of 35 manually reviewed human ratings were wrong after adjudication.S3 Diagnosis
  • Across 6,824 query–store judgments, disagreement was above 30% for "mostly relevant", "partially relevant" and "irrelevant", exactly the boundary cases a ranker learns from.S3 Diagnosis

The fix was to change the question. Instead of "rate this store 0 to 1", the rubric asks separate yes/no questions. For "healthy cheap tacos": Does it serve tacos? Are there items under $12? Are there health-conscious options?S3 Phase 1 An LLM judge is calibrated against adjudicated human answers, then runs daily on live searches and on every pull request that touches search.S3 Phases 2–3

why per facet

One blended NDCG made a speed failure look like a dietary failure. Scored per facet, cuisine and price were strong while speed and location were broken: the pipeline lacked real-time ETAs and the user's current location.S3 Failures

story · 09What we don't know

  • How keyword and embedding results are merged (the fusion method and weights), and how many candidates each retriever returns.
  • Which Qwen3 reranker size is used, what it was fine-tuned on, and how much latency it adds.
  • Whether BM25 is used in production. DoorDash names it only as an example of a method that generalizes.
  • Which LLMs do the query segmentation and linking.
claims you may see elsewhere

Some summaries of this case say DoorDash merges results with Reciprocal Rank Fusion, that its cross-encoder adds "~15 ms", or that top-3 conversion rose "over 12%". None of these appear in DoorDash's posts (S1–S3). This page uses only what DoorDash published, and teaches RRF in the practice section as a general technique.

DoorDash's own limits: LLM text profiles work for items and stores, but not for consumers, whose preferences live in behaviour and change with the situation.S2 Limitation The judge had blind spots too: it missed item-level prices and customizable spice levels, and didn't round ratings the way the app does.S3

practice · 03Wiring it into your code

A small, working version in Python: constrained query linking, MUST filters, BM25 and embedding retrieval, RRF and a cross-encoder reranker. It is our implementation, not DoorDash's, which hasn't been published.

# pip install numpy rank-bm25 sentence-transformers openai
import os

from openai import OpenAI

client = OpenAI()  # reads OPENAI_API_KEY from the environment


def llm(prompt: str) -> str:
    response = client.chat.completions.create(
        model=os.environ["LLM_MODEL"],  # a chat model your account can use
        messages=[{"role": "user", "content": prompt}],
        temperature=0,                  # parsing and routing want repeatable output
    )
    return response.choices[0].message.content or ""

2 · Link the query, but only to concepts you retrieved

The LLM chooses from the nearest concepts (DoorDash uses 100). Code then drops anything not in the list and forces dietary concepts to MUST, whatever the model said.

@dataclass(frozen=True)
class LinkedQuery:
    must: frozenset[str]                # hard constraints, e.g. dietary restrictions
    should: frozenset[str]              # soft preferences, e.g. flavours
    text: str                           # the original query, still used for retrieval

LINK_PROMPT = """Link each part of the food search query to concepts from the CANDIDATES list only.
Never invent a concept. Put dietary restrictions in "must"; everything else in "should".
Return JSON: {{"must": [...], "should": [...]}}

Query: {query}
CANDIDATES:
{candidates}"""

def candidate_concepts(query: str, concepts: Sequence[str], concept_vecs: np.ndarray,
                       embedder: Embedder, k: int = 100) -> list[str]:
    """Nearest taxonomy concepts to the query (DoorDash retrieves the closest 100 with ANN).
    Exact search here; use an ANN index (FAISS, HNSW) when the taxonomy is large."""
    q = embedder.embed([query], kind="query")[0]
    order = np.argsort(-(concept_vecs @ q))[:k]
    return [concepts[i] for i in order]

def link_query(llm: LLM, query: str, candidates: Sequence[str],
               must_prefixes: tuple[str, ...] = ("dietary:",)) -> LinkedQuery:
    """Ask the LLM to choose from the candidates, then enforce it in code:
    unknown concepts are dropped, and dietary concepts are always MUST whatever the model said."""
    allowed = set(candidates)
    try:
        raw = llm(LINK_PROMPT.format(query=query, candidates="\n".join(candidates)))
        match = re.search(r"\{.*\}", raw, flags=re.DOTALL)
        out = json.loads(match.group(0)) if match else {}
    except json.JSONDecodeError:
        out = {}
    picked = {str(c) for c in [*out.get("must", []), *out.get("should", [])] if str(c) in allowed}
    must = frozenset(c for c in picked if c.startswith(must_prefixes))
    return LinkedQuery(must=must, should=frozenset(picked - must), text=query)

3 · Two retrievers, both filtered by MUST first

# ---------------------------------------------------------------- 2. retrieval
@dataclass
class HybridIndex:
    items: list[Item]
    embedder: Embedder
    vectors: np.ndarray = field(init=False)
    bm25: BM25Okapi = field(init=False)

    def __post_init__(self) -> None:
        if not self.items:
            raise ValueError("cannot index zero items")
        self.vectors = self.embedder.embed([i.text() for i in self.items], kind="document")
        # attributes are indexed as words too, so "dietary:vegan" can match the token "vegan"
        self.bm25 = BM25Okapi([tokenize(i.text() + " " + " ".join(i.attributes)) for i in self.items])

    def _eligible(self, q: LinkedQuery) -> np.ndarray:
        """MUST constraints filter BEFORE ranking: a non-vegan item can never be retrieved for a
        vegan query, however similar its text is."""
        return np.array([q.must <= i.attributes for i in self.items])

    def keyword(self, q: LinkedQuery, k: int = 20) -> list[str]:
        tokens = tokenize(q.text) + [t for c in q.should for t in tokenize(c)]
        scores = np.where(self._eligible(q), self.bm25.get_scores(tokens), -np.inf)
        return [self.items[i].item_id for i in np.argsort(-scores)[:k] if np.isfinite(scores[i]) and scores[i] > 0]

    def semantic(self, q: LinkedQuery, k: int = 20) -> list[str]:
        qv = self.embedder.embed([q.text], kind="query")[0]
        scores = np.where(self._eligible(q), self.vectors @ qv, -np.inf)
        return [self.items[i].item_id for i in np.argsort(-scores)[:k] if np.isfinite(scores[i])]

4 · Fuse with RRF

# ---------------------------------------------------------------- 3. fusion
def rrf(rankings: Iterable[Sequence[str]], k: int = 60, top_n: int | None = None) -> list[tuple[str, float]]:
    """Reciprocal Rank Fusion: score(d) = sum over lists of 1 / (k + rank). Uses ranks only, so
    BM25 scores and cosine similarities never need to be put on the same scale.
    k=60 is the value from Cormack et al. (2009); a smaller k favours each list's top hits."""
    if k <= 0:
        raise ValueError("k must be positive")
    scores: dict[str, float] = defaultdict(float)
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] += 1.0 / (k + rank)
    fused = sorted(scores.items(), key=lambda kv: (-kv[1], kv[0]))
    return fused[:top_n] if top_n else fused

5 · Rerank the short list with a cross-encoder

# ---------------------------------------------------------------- 4. re-ranking
class SentenceTransformersCrossEncoder:
    """Adapter for a real cross-encoder (query and document read together by one model)."""

    def __init__(self, model_name: str = "cross-encoder/ms-marco-MiniLM-L6-v2") -> None:
        from sentence_transformers import CrossEncoder

        self.model = CrossEncoder(model_name)

    def predict(self, pairs: list[tuple[str, str]]) -> Sequence[float]:
        return [float(s) for s in self.model.predict(pairs)]

def rerank(query: str, candidate_ids: Sequence[str], items_by_id: dict[str, Item],
           scorer: PairScorer, top_k: int = 10) -> list[tuple[str, float]]:
    """Score only the short fused list: cross-encoders cost one model call per (query, item) pair."""
    ids = [i for i in candidate_ids if i in items_by_id][:top_k]
    if not ids:
        return []
    scores = scorer.predict([(query, items_by_id[i].text()) for i in ids])
    return sorted(zip(ids, (float(s) for s in scores), strict=True), key=lambda kv: -kv[1])

@dataclass(frozen=True)
class SearchResult:
    linked: LinkedQuery
    keyword: list[str]
    semantic: list[str]
    fused: list[tuple[str, float]]
    ranked: list[tuple[str, float]]

def search(query: str, llm: LLM, index: HybridIndex, concepts: Sequence[str], concept_vecs: np.ndarray,
           scorer: PairScorer, k: int = 20, rrf_k: int = 60, rerank_top: int = 10) -> SearchResult:
    linked = link_query(llm, query, candidate_concepts(query, concepts, concept_vecs, index.embedder))
    kw, sem = index.keyword(linked, k), index.semantic(linked, k)
    fused = rrf([kw, sem], k=rrf_k, top_n=rerank_top)
    by_id = {i.item_id: i for i in index.items}
    return SearchResult(linked, kw, sem, fused, rerank(query, [d for d, _ in fused], by_id, scorer, rerank_top))

6 · Evaluate per facet, with yes/no questions

# ---------------------------------------------------------------- 5. evaluation: binary facets
FACET_PROMPT = """You check one search result against ONE question. Use only the item text.
Query: {query}
Item: {item}
Question: {question}
Answer JSON: {{"answer": "yes" or "no", "reason": "<one sentence>"}}"""

@dataclass(frozen=True)
class Facet:
    name: str                           # e.g. "dish match", "dietary", "price"
    question: str                       # a yes/no question answerable from the item

def judge_facets(llm: LLM, query: str, item: Item, facets: Sequence[Facet]) -> dict[str, bool]:
    """One yes/no call per facet. Anything other than a clear yes/no raises, so a broken judge
    cannot silently pass results."""
    out: dict[str, bool] = {}
    for f in facets:
        raw = llm(FACET_PROMPT.format(query=query, item=item.text(), question=f.question))
        match = re.search(r"\{.*\}", raw, flags=re.DOTALL)
        answer = str(json.loads(match.group(0)).get("answer", "")).strip().lower() if match else ""
        if answer not in {"yes", "no"}:
            raise ValueError(f"judge gave no yes/no for facet {f.name!r}: {raw[:80]!r}")
        out[f.name] = answer == "yes"
    return out

def per_facet_precision(judgements: Sequence[dict[str, bool]]) -> dict[str, float]:
    """Share of results that pass each facet. Report these separately: an average across
    facets hides which one is failing."""
    if not judgements:
        raise ValueError("no judgements")
    names = judgements[0].keys()
    return {n: sum(j[n] for j in judgements) / len(judgements) for n in names}

practice · 05Rules of the road

Keep these in plain code

  • MUST filters (diet, permissions, region) applied inside every retriever.
  • Checking that every concept the LLM returns exists in your vocabulary.
  • The size of the list the reranker sees, and a timeout that falls back to the fused order.

Mind what you send

  • Letting an LLM invent labels. DoorDash restricts it to concepts already in the knowledge graph.S1
  • Adding raw scores from different retrievers. Their scales don't match.

Calibrate, then watch

  • Audit your training labels before blaming the model; DoorDash's reranker scored AUC 0.56 on noisy labels.S3
  • Track null-search rate: it shows recall problems that relevance scores on returned results can't.
  • Report metrics per facet, not one blended number.

practice · 07When it breaks: symptoms, causes, fixes

Read a symptom, guess the cause, then open the card. analysis except where a card cites DoorDash.

Likely cause. Dietary terms are matched by similarity, not enforced. Embedding retrieval returns "close" items.S1

Fix. Link "vegan" to a concept and make it a MUST filter in every retriever.

Likely cause. Only embedding retrieval runs, and embeddings blur rare exact strings.

Fix. Add keyword search for exact tokens and fuse the two lists.

Likely cause. The best item never made the fused short list. A reranker can only reorder what retrieval gives it.S2

Likely cause. The prompt let the model name any concept.

Fix. Give it the nearest candidates only, as DoorDash does with 100 ANN candidates, and drop anything else in code.S1

Likely cause. Noisy training labels, especially on the boundary cases. DoorDash saw AUC 0.56 for this reason.S3

Fix. Audit labels with a second rater or an LLM judge, and switch to yes/no facet questions.

Likely cause. One blended score hides a failing facet. DoorDash found speed and location failing behind a good average.S3

designWhy not use pure vector search for "vegan chicken sandwich"?

documented Similarity can return vegetarian or chicken sandwiches; only vegan chicken sandwiches match, and dietary restrictions outrank other attributes. DoorDash describes keyword-based retrieval combined with document and keyword understanding to enforce rules like "only vegan".S1

analysis Similarity is a ranking signal, not a constraint. Constraints belong in filters.

llmHow do you stop an LLM from inventing entity labels?

documented DoorDash retrieves the 100 nearest taxonomy concepts with ANN and asks the LLM to choose only from them, then post-processes and audits samples.S1

retrievalBi-encoder vs cross-encoder: why use both?

documented DoorDash retrieves with embeddings and reranks with a fine-tuned Qwen3 reranker that reads the query with item and store profiles.S2

fusionHow would you merge keyword and vector results?

documented DoorDash doesn't publish its method.

metricsNull search rate fell 3.65%. Why does semantic retrieval help exactly there?

documented DoorDash links it to tail queries, where semantic retrieval maps rare or new phrasing to meaningful results without engagement history.S2

wrap-upConclusion: rules for precision, meaning for recall

DoorDash didn't choose between keyword and semantic search. It used an LLM to turn queries into rules it could enforce, made semantic retrieval the default for everything those rules can't express, added a reranker for the short list, and rebuilt evaluation around yes/no facet checks when human labels proved too noisy.

Four things to carry away

  • Hard constraints are filters, applied before ranking, in every retriever.
  • Constrain LLMs to your own vocabulary, and validate in code.
  • Retrieval sets the ceiling; reranking only reorders what it is given.
  • Evaluate per facet, and audit your labels before you train on them.

BM25
A classic keyword ranking function that weights matching terms by how rare they are.
Bi-encoder
Embeds query and document separately and compares vectors; fast and precomputable.
Cross-encoder
Reads query and document together and outputs one relevance score; accurate but costly.
RRF
Reciprocal Rank Fusion: adds 1 / (k + rank) from each list to merge rankings.
Knowledge graph
Entities and their relationships, e.g. items with dietary and flavour attributes.
Entity linking
Mapping a piece of text ("no-milk") to a known concept ("dairy-free").
ANN
Approximate nearest neighbour search over vectors.
MUST / SHOULD
A required condition vs a preference that only boosts ranking.
nDCG
Normalised discounted cumulative gain: rewards relevant results placed higher.
Null search rate
Share of searches that return nothing useful.
MRL
Matryoshka Representation Learning: embeddings that can be shortened with little quality loss.
